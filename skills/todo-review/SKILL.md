# Daily Task Review (Life Automation)

A daily stand-up over the user's Trello board with two ways to start: **Quick** (no scanning of Gmail, Calendar or Google files: it shows the saved brief and checks Trello only) and **Full** (scans everything first). After that the two are the same: card by card, each card's block is the closing reply of its turn and ends with a typed menu, and the user can do ANYTHING on a card (email, meeting, file, snooze, mark done). Skip, snooze and mark done are kept as fast as possible, so the rarely used rules live in two helper skills that are loaded with the Skill tool only when needed: `todo-review-actions` (emails, meetings and travel events, past-meeting and cleanup questions, card content checks, proposal triage) and `todo-review-scan` (the Full scan, waking cards on replies, linked-file checks). Load each at most once per run; its text then stays in front of you. A third helper, `todo-review-rules`, holds the rules this skill points to by name (**Write queue**, **Card cache**, **Snoozing**, **Snoozed buckets**, **Deadlines**, **Card metadata format**, **Comments rule**, **Stated done is the go-ahead**, **Showing progress between cards**, **Learnings**, **Step 3.2: Building the menu**). Meeting rules are in `todo-review-meetings` (**Meetings and travel**, **Meeting cleanup**, **Keeping the Events list short**, Step 2a), loaded by `todo-review-actions` when a meeting is involved. Debug logging is in `todo-review-debug`. Offline jobs (`#offline`) are in `todo-offline`, loaded only when the user types `#offline` or when jobs are queued at the wrap-up.

In this skill "the user" is the person running the review. Write to them as "you".

## Flow at a glance
1. **Quick or full** (see **Quick or full**): a one-line question when the last full check is older than 20 minutes, otherwise Quick without a question.
2. The saved brief is shown, then a short `Peeking at Trello` label while the reads run (Full: `todo-review-scan` runs the scan here).
3. If stale meetings or proposed tasks are waiting, they are handled first, one question at a time (`todo-review-actions`).
4. Card by card: each card's block is the closing reply of its turn and ends with a typed menu of up to 4 numbered options. No list of all cards first, no "ready?" question.
5. The user can stop at any time. Then the wrap-up.

## Hard rule: never leave a card on your own
A card is finished only when the user chooses a finishing option in the check-in ("Mark it done 🎉", a snooze or "Skip", see Step 3.3), or when a Skip or Snooze pick on the menu (or slot 1, when it fully completes a single-part card) ended it, or when the user typed a clear snooze or a clear mark done (see **Clear snooze**), or when the user said to stop the review (see **Stopping the review**). If the user typed anything on a card beyond a bare menu number (extra words after the number count, and so does an "Other" answer or a normal chat message), or asked a question, or reacted to a draft, finish with the check-in (see Step 3.3) before showing the next card. The one exception is a clear snooze or a clear mark done, which ends the card by itself with no check-in. This applies in every session and overrides any other step that says to go on to the next card.

## Before anything else: load settings
1. Read `/areas/life-automation.md` (time zone, plan type, board name, sheet name, `Log sheet ID`, `Board ID`, the `List IDs` line, `Last review check`, `Last prep`, `Last quick check`, `Board marker`) in one parallel batch, unless the router already read it in this session (it does, in its first batch). Read `/areas/life-automation-learnings.md` in the first batch after the user's answer to the Quick or full question (with the rules, see item 5), or in the run's first batch when there is no question, and follow everything in it.
2. If the settings file is missing or has no board name, stop and say in one line: "I can't find your Life Automation settings. Type /todo setup and I'll set things up."
3. Time zone: the saved zone; "today" and all dates are in it. Board: the saved name.
4. **Saved IDs are a shortcut, never a trusted fact.** The `List IDs` line is `TO DO=<id>; In Progress=<id>; Done=<id>; Proposed=<id>; Snoozed/Waiting this week=<id>; Snoozed/Waiting next week=<id>; Snoozed/Waiting later=<id>`. **The Trello tools accept list ids only in the long form `ari:cloud:trello::list/workspace/<workspaceId>/<listId>`** (the same shape as the saved `Board ID`); a plain id fails with a validation error and costs a whole retry turn. If the saved line holds plain ids, build the long form from each plain id and the workspace id noted at the end of the line (`(workspace <workspaceId>)`), or from the workspace part of the saved `Board ID`; never send a plain id to a Trello read or write. Read the lists you need straight by ID in that long form; each read must come back with the expected list name. If any read fails, returns a different name or is empty by mistake, find the board and lists by name (trelloSearch, `trelloReadList list_by_board`), read again and save the fresh IDs (memory_str_replace, in a turn that does other work). Never write a list or card by a saved ID without having read that list in this run. Log sheet: read by the saved `Log sheet ID` (the Brief tab read doubles as the check); if that fails, find "Life Automation Log" by title with Drive search and save the new ID.

5. **Load the rules and read the learnings after the question, never before it.** Load `todo-review-rules` with the Skill tool (once; it stays loaded) and read the learnings file (item 1) in the first batch after the user's answer to the Quick or full question (Quick: LAST in the peek batch (batch 2 of the Quick order), after the reads; Full: together with `todo-review-scan`), and, when there is no question, in the run's first batch. The router does not load it and the question needs nothing from it. It holds the rules below that this skill points to by name.

## Setup facts
- Task list: the user's Life Automation Trello board; Trello is the only task list.
- Seven lists, left to right: `Snoozed/Waiting later`, `Snoozed/Waiting next week`, `Snoozed/Waiting this week`, `TO DO`, `In Progress`, `Done`, `Proposed`. Names are exact; never rename them. If a Snoozed list is missing, create it with the exact name.
- Working lists: `TO DO` and `In Progress`. Never read `Done`. `Proposed` is read in both modes (proposal triage, see `todo-review-actions`). The three Snoozed lists are read only in Full mode, and only when `todo-review-scan` says so.
- Tools: Trello, Google Sheets, Claude memory, SendUserMessage; Gmail, Google Calendar and Google Drive are used only by the two helper skills.

## Showing text (so it isn't collapsed)
- Everything the user must read as a message (the brief chunks and the wrap-up) is sent with the SendUserMessage tool. If it is deferred, load it at the start of the run (ToolSearch `select:SendUserMessage`). The card blocks, the notes, the check-ins and every question are written in plain chat text as the reply of their turn and are never also sent with SendUserMessage.
- Reading material that belongs to a question is part of that same closing reply, above the menu.
- **No narration.** The only text before card 1 is: `Rolling up my sleeves for your daily review…` (sent by the router), the brief, the `Peeking at Trello` label, and `Preparing card Y of N: <card name>...` when a card needs live prep. No plans, no explanations between tool calls. Thinking stays silent.

## Time format (12-hour with AM/PM)
Every clock time the user reads (the brief, card bullets, notes, questions, email drafts) is written in 12-hour form with capital AM or PM, a space before it, and no leading zero: `8:14 AM`, `1:25 PM`, `10:30 AM`. A range is `1:25–2:00 PM`; one that crosses noon carries both: `11:30 AM–12:15 PM`. Never write `08:14`, `13:25`, `22:00`, `a.m.` or lowercase `am`. Times that programs read stay in 24-hour form: the `Events:` lines in the card metadata (`YYYY-MM-DD HH:MM`), calendar and Trello fields, and sheet timestamps. When such a time is shown to the user, convert it.

**Always show times and dates in the user's time zone.** Gmail, Trello and the sheets give times in UTC. Convert before showing, and take the date from the converted time: an email sent at 9:00 PM UTC on Oct 21 is shown as `Oct 22, 12:00 AM` for a user in UTC+3.

## Choices (typed, inline, never popups)
- Every choice is typed in the style of the card menu. Never use AskUserQuestion, never a popup.
- A question is the closing reply of its turn: the facts first, one short question line when needed, a blank line, the menu line, a blank line, the prompt line (see **The card menu**).
- Up to 4 options. The recommended option goes first, with no tag. The last option is `Skip` (changes nothing, the question comes back next time) or, for yes/no, the "no" answer. Yes/no questions have exactly two options and no Skip.
- Question lines are short and never repeat an option label. A number that is not on the line gets one line (`There are only 3 options.`), changes nothing and waits. Reading the reply works as for the card menu.

## The card menu (typed, up to 4 numbered options)
The card question is typed, like every choice in the review (see **Choices**). The menu line, followed by the prompt line below it, ends the card's message (see **Card blocks**), in plain text with no code formatting, and the user answers by typing a number.

One line, up to four options in this order (the cards with a deadline have their own labels, see Step 3.2):

① <the work, at most 8 words> · ② Snooze 7d (<Mon D>) · ③ Snooze 30d (<Mon D>) · ④ Skip

**Label style.** Keep every label short and the same shape:
- A snooze is always `Snooze <N>d (<Mon D>)`: N is the number of days from today to that date, and the date is the month name and day number with no weekday (`Snooze 7d (Oct 29)`, never `Snooze to Thu Oct 29`).
- A pick that also sets or moves the due date starts with `Due date to <Mon D> + ` and then the snooze, for example `Due date to Nov 7 + snooze 16d (Nov 6)`.
- Labels are in sentence case: the first word starts with a capital letter, month names are capitalized, and everything else is lower case unless it is a name. Never write dates with a weekday anywhere in the menu or in the card header's deadline (`due Oct 31`). Notes may carry the weekday (`until Mon Oct 26`); menu labels never do.
- Slot 4 is always called `Skip`, never "Leave as is" or any other wording.

**The numbers.** The options are numbered with the circled digits ①, ②, ③, ④ (and ⑤ onward if ever needed). Each is ONE character (U+2460 and the next ones), so nothing can get lost when the skill is saved or copied. Never use the keycap emoji (a digit followed by invisible characters), a bare digit or a bold digit in their place. The user can still answer by typing 1, 2, 3 or 4.

Under the menu line, after one blank line, comes ONE fixed prompt line, always exactly: `Type 1–<N>, or just tell me what you have in mind.`, where N is the number of options on the line (usually 4). Never reword it, and never add a card number or any other line after it. The menu line and the prompt line are the last two lines of the card's message.

- **Roles and numbers.** Each option has a role: the work, the first snooze, the second snooze, Skip. Elsewhere in this skill "slot 1, 2, 3, 4" names the role (work, first snooze, second snooze, Skip), not the typed number. The typed number is the option's position on the line, counted from 1 with no gaps, and Skip is always last. The work comes first on purpose, to push the user to work on the card. There is no star and no "Recommended" label: the position does that.
- **Options are shown whenever they can be filled.** When a snooze would not fit before the card's deadline, or the due date can't move because it is a fixed date (see Step 3.2), that option is left out and the options after it move up, so the numbers always run 1, 2, 3 (or 1 to 4) in a row and the prompt line shows the real count. Never write a dash or a placeholder, and never leave a gap in the numbers. If the user types a number that is not on the line, answer with one line (`There are only 3 options.`), change nothing and wait for a new answer.
- **How to read the reply:**
  - Just a number from the line (also "1.", "#1" or the number emoji) picks that slot.
  - The number as the first word, then more words, picks that slot plus an extra instruction for it ("1 and cc Sam", "2 but make it Friday"). A different snooze date typed this way is the user's choice; check it against the deadline rules. If it is unclear ("2 weeks" could be slot 2 or a duration), confirm in one line instead of guessing.
  - "stop", "that's enough" and the like end the review (see **Stopping the review**).
  - A reply that contains `#offline` queues the rest of the text as an offline job and goes on with the card: load `todo-offline` (once) and follow **Queueing a job** there. Nothing runs during the walk.
  - Anything else is the user's own instruction on this card (what the "Other" box used to be): do it, then run the check-in in Step 3.3. The exception is a clear snooze or a clear mark done (see **Clear snooze**): it ends the card by itself, with no check-in. This includes "change the due date to ..." after a due date was set for the user: do it (the Trello due date is queued, see **Write queue**), and say what it was before in a one-line note (Step 3.5).
- The past-meeting question, the cleanup question, stale meetings, proposal triage, the snooze date after an email and the check-in after a card all use the same typed style (see **Choices**, Step 2c and Step 3.3).

## Speed rules (every interactive run)
These keep the waits short. They never change what the review does, only how fast.
- **No thinking on card turns.** On a turn from an answer to the next card, do not deliberate or re-check the menu rules. Use the answer, copy the next card's cached block, fill the date templates and write it at once. A note (when there is one, see Step 3.5) and the card are the whole reply. Deliberate only when the card has no usable cache row, or the answer is not a plain number, snooze, mark done or skip.
- **One pass from answer to next card (for every answer: snooze, skip, mark done, the work, anything typed).** After the user answers, ONE reply does everything: a one-line note about the previous card (only when something failed or Claude changed what the user asked for, see Step 3.5; otherwise nothing) is written as the first line of that same reply, then a blank line, then the next card or question. That turn has NO tool calls (in debug mode only, it starts with one timestamp call, see **Debug mode**): no SendUserMessage for the note, no TaskUpdate, no call for queue notes (the queue lives in your notes), no timestamp call, no reads and no sheet writes. TaskUpdate calls wait for the next turn that has tool calls for another reason (an email, live prep, a sheet write) or for the wrap-up, so the task list may lag a card or two. Most answers have no note, so their reply is the next card alone. The only exception is real work the answer needs before the next card (an email, a calendar event, live prep for a card with no cache row): that turn has its calls, and a slow one sends the one `Preparing card Y of N: <card name>...` line first.
- **Show first, fetch after.** In any batch that shows the user something (SendUserMessage), put those calls FIRST, then any reads, sheet writes and logging. Never put a read or a sheet write ahead of the message in the same batch: the user would wait for it. A card, check-in or question is the reply of its turn, and a turn that only moves on to the next card has no calls before it at all: no reads, no sheet writes, no timestamp (Bash) call and no background write. When the turn also has a background write to start (an email send, a calendar removal, a Google file change), the message goes ALONE in the first batch and the background step is started in a second batch of the same turn.
- **Reuse the list reads.** The first reads (see **Quick or full**) read the lists separately, never the whole board in one call, and never the Snoozed lists in Quick mode or when the prep rows cover them in Full mode, because a whole-board read is about 84,000 characters and is saved to a file. Keep every working card's description, comments, due date, labels and list from those reads. If a result is saved to a file because it is large, pull those fields out with one jq or python call and keep them in your notes. Do not read a card again with `get` unless the user acted on it in this review, or it changed during the review (see Step 2b, item 6). The list reads do not reliably include checklists: read the checklists of all working cards in one parallel batch of trelloReadChecklist calls during the card prep.
- **Latest comments only.** When a card's comments must be read again, use trelloReadCard `list_comments` with `limit: 3`, not `get` (which always returns up to 25 comments). Use `get` only when you need the description and don't already hold it.
- **Live prep is the only wait.** The prep normally leaves a cache row for every working card, so the next card is ready. If a card has no usable row (it changed since the prep, it has no row, or its row is in an old format), prep it live and send the one line `Preparing card Y of N: <card name>...` first (see **Showing progress between cards**). Nothing else may delay a card.
- **Side jobs before the cards.** The Brief tab rewrite, creating a missing tab, reading the Card cache tab and similar jobs happen before the first card block is sent or after the wrap-up, never in a batch with a card's question. The writes that belong to the user's answer on a card are not side jobs.

## Card blocks (prepped upfront, shown one at a time)
All cards are written once, in the background right after the brief, so each card appears at once when its turn comes. There is no up-front list of all the cards: the user sees only the card they are on.
1. **Which cards:** every card in `In Progress` and `TO DO` (including cards woken today), in Step 0 order. Snoozed cards are never in the review. Proposed tasks are triaged AFTER the last card (see **Step 2c** in `todo-review-actions`); a proposal the user answers Add is not part of today's walkthrough: it is written to the board at the wrap-up and comes up in tomorrow's review.
2. **Prep:** prep every one of those cards (Step 2b). Reuse the **Card cache** for every card whose fingerprint matches; write fresh only the cards that changed or have no cache row.
3. **Show one at a time:** do NOT send a "Today's cards (N)" message or any message holding several cards. **Each card is written in plain chat text as the reply of its turn. Never send it with SendUserMessage, and never both: the card text exists exactly once.** The card is: the header line `**X/N. [card name](link)** · list · due <Mon D> if any`, its 1–2 bullets (Step 3.1), a blank line, the menu line from Step 3.2, a blank line, and the prompt line (see **The card menu**). That reply is the question: there is no AskUserQuestion for the card, no separate question text and no reminder line. The note about the previous card, when there is one (Step 3.5), is the first line of the same reply, above the header line. Anything that finished while this card was being prepared (a calendar event, a note, a queued write) goes into that recap. Nothing can follow the prompt line: no summary, no copy of the card, no text about an earlier card. If a write finishes after this card was shown, its result goes into the next note, only if it failed. Card 1 goes out as soon as the closing lines of the brief are sent. If the last turn had a reason to make tool calls anyway (for example live prep), the TaskUpdate calls for the cards go in that turn, never in a turn of their own.
4. **The user answers by typing** (see **The card menu**). Nothing else is sent until they do.
5. **Later changes:** if something done on an earlier card, or a new email, changes a card still to come, put the change into that card's block when you show it (a first bullet starting `Update:`), and change its menu if needed.
6. If the user stops, the blocks not yet shown are simply never shown (see **Stopping the review**).

## Step 0: Prioritize cards
Whenever you go through cards in any step, order them like this:

The order is **the order the user's eyes follow on the Trello board**, so the walkthrough matches what they see on screen. Do NOT re-sort by due date, label or anything else.

1. **Lists, right to left.** Use the lists from the saved-ID reads (see **Board**), or, when there are no usable saved IDs, read the board's lists with `trelloReadList list_by_board`. Sort the lists by `position`, ascending (left to right on screen). Keep only the working lists (`In Progress`, `TO DO`). Start at the working list **closest to `Done` on its left** (`In Progress`) and move left (`TO DO`).
2. **Within each list, top to bottom,** by the card's `position` (smallest first). Finish a list completely before moving to the next list on its left.
3. **Due dates do not change the order.** The prioritizer helper already puts due cards at the top of each list. Deadlines are surfaced in the ⏰ section of the brief and in each card's summary (see **Deadlines**), not by reordering.

Cards in the Snoozed lists are only handled under **Snoozing**. Cards in `Proposed` are only handled in Step 2c (`todo-review-actions`).

## Reference point: your last review
R is the `Last review check` line (the last Full review), P is the saved brief's `prepared_at` (the auto daily run; the first row of the Brief tab), Q is the `Last quick check` line. U, the last time Gmail, Calendar and Trello were all checked, is the later of R and P. B, the last time the user was shown a brief, is the later of R and the run the last Quick check showed (the `showed run` time in the Q line; a Q line without it counts as no shown run). B decides the 🆕 header and which items count as news; it never changes what is scanned. A Quick run never moves R: it writes only Q (and the `Board marker`, see **Quiet-board shortcut** in `todo-review-rules`), in the first parallel batch after the first card is shown that has tool calls for another reason (an email, live prep, a sheet write), or in the wrap-up batch when there is none (never in the batch that holds the reads before the first card: writing it out delays the first card), in the form `Last quick check: <UTC time, ISO> (showed run <P, UTC ISO>)`, where P is the `prepared_at` of the saved brief this run showed (memory_str_replace on the `Last quick check` line, memory_append of the line when there is none). A Full run writes R (see `todo-review-scan`). The time is taken from a call already running (Bash `date -u +%FT%TZ` or the current_time tool), never from a turn of its own. If the write fails, say nothing and carry on. Times shown to the user follow **Time format** (`H:MM AM/PM` when today, `<Mon D>, H:MM AM/PM` for an earlier day). What counts as "new" is defined in `todo-review-scan`.

## Quick or full
The prep helper saves the daily brief to the **Brief** tab of the Google Sheet "Life Automation Log". Always call it "your last brief". Never write "the morning brief", "today's brief" or a brief's clock time.
- **Format:** header `line_no, kind, text, prepared_at, prepared_date`. Row 2 is the meta row (`kind=meta`; `text` is the status `ok`, `partial` or `failed`; `prepared_at` is UTC; `prepared_date` the user's date). The rows after it are the brief, in order (`kind=line`, or `blank`).
- **When it is read.** The question needs only R (the settings the router already read) and P (the meta row of the Brief tab). When the settings hold a `Last prep` line from today with status `ok` or `partial` (written by the prep when its task may write the settings file), the router takes P from it, reads no meta row and sends the question alone in its second turn; otherwise it reads just that row (`A2:E2`) in its second turn and sends the question alone in its third turn. It reads the whole Brief tab (`A2:E200`) in the turn right after the question, while the user reads it. When there is no question, it reads the whole tab in the turn after the decision.
- **Usable** only if `prepared_date` is today (user's time zone) and the status is `ok` or `partial`; decided from the `Last prep` line or the meta row before the question. A missing row, an older date, a `failed` status or an unreadable tab means not usable: send one line `No saved brief from today, so I'm doing a full review.` and run Full (item 3 below); `todo-review-scan` builds the brief. If the full Brief read that follows the question shows something different from the meta row, do what the previous sentence says right after the user's answer, whatever they picked.
- **The question.** The router normally sends this question itself, in its third turn, with the same wording; its fourth turn reads the Brief tab and has no closing text (`Your pick, 1 or 2?` is the last line of the question); when it did, start at the user's answer and do not send it again. If the router did not send it and it is due, do it as described here. If U was 20 minutes ago or less, there is no question and the run is Quick, and the first chunk of the brief (see item 1) starts with one line: `Your last full check was only <N> min ago, so I took the quick lap (no Gmail or Calendar scan).` Otherwise the next turn is ONE batch with the question block below as a SendUserMessage (and `Rolling up my sleeves for your daily review…` first when the router has not sent it yet); the turn after it reads the Brief tab (`A2:E200`) and has no closing text. The question block is: the line `Life Automation last swept everything at <U> (<N> min ago).` (`<H> h <M> min ago` from an hour on; `<Mon D>, <time>` for an earlier day; when P is later than R: `Life Automation did its morning rounds at <P> (<N> ago).`), a blank line, `Quick lap or full tour?`, a blank line, `① Quick lap: I skip Gmail and Calendar, so I might miss anything new since <U>` on one line, `② Full tour: I check everything first, takes a little longer` on the next (the numbers are the circled digits, see **The numbers**), then a blank line and the prompt line `Your pick, 1 or 2?` as the last line, and nothing after it. A 1 or "quick" is Quick. A 2 or "full" is Full. Anything else is answered and the question asked again. In debug mode this turn carries the one `ask` stamp call (see **Debug mode**).
- **Both modes allow every action on every card.** The only difference is whether the scan runs first. Never tell the user that something is not available in Quick mode.
1. **Quick mode order (brief first, alone).** TWO batches in the same turn, the second written right after the first returns. **Batch 1 holds only the brief** (no stamp, no skill, no read, nothing else: the calls of a batch start only once it is written, so anything else in it would delay the brief) (the brief rows are already read: in the router's fourth turn, or in its third turn when there was no question; no sheet read for them here), calls in this order: (a) the saved brief **in chunks, one SendUserMessage call per chunk, all in this batch, in screen order, never the whole brief as one message** (chunk 1: the title line, the one-line `I went Quick` note when the question was skipped (see **The question**), and the 🆕 section; then one chunk per section that has bullets; single-line sections go with the next chunk or the previous one when last), exactly as saved, without the divider and ▶️ lines. The saved 🆕 section is kept as saved when P is later than B (the user has not seen this run's news yet), and left out when B is P or later (they already saw it). No other refresh. (b) as the LAST message of the brief batch, before the reads, one SendUserMessage with the label `🔎 Peeking at Trello to see what's moved since <time>…` (`<time>` = the latest of R, Q and P, 12-hour format per **Time format**); **Batch 2, the peek batch** (the user reads the brief meanwhile), calls in this order: (c) the reads (by saved list ID in the long form, see **Before anything else**), the board FIRST (trelloReadBoard `get`; its `due` field is the board's last-activity time, see **Quiet-board shortcut** in `todo-review-rules`), the Card cache tab (range `A2:I500`) next, then the three lists. Read the `In Progress`, `TO DO` and `Proposed` lists cheap: trelloReadList `get` for each (ids and names in position order, a small answer). **Prefetch (in batch 2):** also add the early reads described in **Prefetch** in `todo-review-rules` (the cards the settings line `Expiring today` says expire within 15 minutes, up to 3, and the heavy `Proposed` read, always, in place of the cheap `Proposed` read). LAST in batch 2, (b2): the Skill call that loads `todo-review-rules` and the read of the learnings file; they are only needed to show card 1, so they go after the reads. The rules skill is loaded in this same batch, so write the reads above in it too. When the `Board marker` line exists, do NOT read the board's activity in this batch: it (trelloReadBoard `list_activity`, board ID from settings, limit 5, no type filter; further pages follow the paging rule in **Activity check**) is read in the next turn, only when the **Quick decision checklist** sends the run to the **Activity check** in `todo-review-rules` (that path takes one more turn than before; the shortcut path, which is most runs, saves the call). With no `Board marker` line, read the three lists heavy (`trelloReadCard` `list_by_list`) as before. **The brief comes before the reads, never after:** a read listed before it delays the brief. The user sees only the brief until it is on screen. Quick mode never searches Gmail, Calendar or Drive (reading one known thread by ID for a **Newest message bullet** is allowed), never reads the Snoozed lists or the Review prep tab, and never wakes a card on a reply.
2. **Quick mode, next turn (the reads are back), ONE parallel batch:** first work through the **Quick decision checklist** in `todo-review-rules`: five questions answered in order with plain comparisons, no thinking and no text, giving one of three results (shortcut, Activity check, normal path). Cards the prefetch already read are never read again in this batch. If it applies, the walk is the cheap list reads in their order with their Card cache rows: no list reads, no checklist reads and no change check (the cached fingerprints stand). If it does not apply, run the **Activity check** (`todo-review-rules`; with a `Board marker`, its activity read is the first call of this turn and the touched cards are read in the turn after its answer): when it gives a usable list of touched cards, this batch holds only the reads for those cards (trelloReadCard `get` and trelloReadChecklist for each) and the heavy read of the `Proposed` list when it is not empty, then the change check below. When it gives no usable list (no marker, marker older than 2 days, more than 8 touched cards), this batch holds the heavy list reads (`trelloReadCard` `list_by_list`, all at once) and the checklists of all working cards (trelloReadChecklist, all at once; the card IDs come from the cheap reads, so both go in this batch), then the change check below. If batch 1 already read the lists heavy, this batch holds the checklists as before. In every case the batch holds, as the LAST call, one SendUserMessage holding the spacer line, the divider, a second spacer line and the two lines below. No text about what changed is sent. **Change check (silent, mechanical, no deliberation):** compare each working card with its Card cache row. A card changed if its list, latest comment date, due date, checklist done/total or metadata `Last updated` differs from its Card cache row (ignore the `flags`, the helpers' own comments such as `Health label added automatically` and Snoozed-list moves). A changed card gets live prep (its cached block is not reused). Do this as a plain comparison, then act; no thinking and no text.
3. **Full mode order.** Load `todo-review-scan` and `todo-review-rules` with the Skill tool and read the learnings file as the first calls after the user picks 2 (or at once when there is no usable saved brief), together with the ToolSearch call it names, and follow it for everything up to and including the closing lines of the brief: the brief, the check for anything new (Gmail, Calendar, linked Google files, Trello), reply-based wakes, the Snoozed lists and live prep of changed cards. From the closing lines on, Quick and Full are the same.
4. **Closing lines of the brief:** after the 😴 line one blank line, then a spacer line (the single character U+2800 alone on its line, never a space), a blank line, the divider `⬇️ ───── Now let's go through your active cards ───── ⬇️`, a blank line, a second spacer line, a blank line, then two lines directly under each other (end the first with two spaces): `▶️ N cards lined up for you.` (`1 card to go through` for one; with proposed tasks waiting: `▶️ N cards lined up for you, then M task ideas to judge at the end.` (the proposals are triaged AFTER the last card, never before, see item 5 and Step 2c, so never say they come first); M is new plus older proposed tasks, the same total as the 📥 lines of the brief; N counts every card in `In Progress` and `TO DO` plus any card a reply woke in this run, whose wake is still queued so the list reads do not show it yet) and `ℹ️ Tip: keep your [Trello board](<board url>) open beside me. Chrome's side panel is perfect for it.` Take the board URL from the list reads. One blank line after the second line.
5. **Before card 1** (nothing happens here when there is nothing to ask, and no turn is added): (a) Full mode only, if the scan found stale future meetings, the one question from `todo-review-meetings` (Step 2a); (b) nothing about proposals: the `Proposed` list is triaged after the last card (Step 2c in `todo-review-actions`), unless there are no working cards, in which case triage starts here. Card 1 comes right after the closing lines of the brief. N counts only the working cards.

## Step 2b: Start right away, and prep while the user reads
Do not ask whether the user is ready. Right after the closing lines of the brief the review starts with card 1.
1. In the batch that sends the closing lines of the brief (and the checklist reads), no other prep call is needed (Full mode: the scan skill says what is prepped). In the NEXT turn, if any working card has no usable Card cache row (changed fingerprint, no row, old format), prep all of them at once, in parallel and in review order, so each is ready before the user reaches it. Use subagents on a faster model (for example Haiku) when the Agent tool lets you choose one; otherwise batch independent calls in one message. Do not hold back card 1: if card 1 is a cache hit, show it at once and prep the others while the user answers.
2. Prep is read-only. In Quick mode it covers the card itself: its description, comments and checklists from the reads, its deadline (see **Deadlines**), a past meeting from its `Events` lines with no recorded outcome and cleanup candidates it shows itself (see `todo-review-actions`), and the block and menu (Step 3.1 and 3.2). No Gmail, Calendar or Drive searching in Quick mode (Full mode: see `todo-review-scan`). Email drafts are written when the user picks the email option, never in prep. Prep never changes anything (the one exception is the missing due date, which is queued when the card is shown).
3. If more than 30 minutes have passed since the list reads when a card is due, re-read that card's list once (`list_by_list`) and put an `Update:` bullet into the block of any card that changed.
4. Then show card 1 (Step 3).

## Step 3: Card by card
Take the user through the cards one at a time in the Step 0 order. Never show the next card until the current one is answered and handled (for Snooze, Skip and Mark done: queued). Each card's block ends with its menu and is the closing reply of its turn (see **Card blocks**). For each card:

1. **Card block.**
   - `**X/N. [card name](link)** · list · due <Mon D> if any`
   - 1–2 bullets on where it stands (a third only for a bullet required below): the latest comment, what it's waiting on, money or dates involved, the user's own next step. Only a future meeting counts as upcoming.
   - **Newest message bullet.** When the card has a new reply or email (its flags include `new_email`, or it was woken by a reply, or its prep row has a `gist:` note), the FIRST bullet is `<Name> replied <Mon D, H:MM AM/PM>: <what it says, as facts: numbers, dates, yes or no, the question asked, at most 20 words> [email](link)`, and the Recommendation bullet uses those facts. The facts come from the saved gist (the cached summary, or the Review prep `gist:` note); with no saved gist, read that one thread by ID (get_thread, a read of a known thread, allowed in Quick mode too) and write it. Never write only who replied and when, and never `read the email` as the content.
   - **Looks done bullet:** when the card shows its own task is already done (a receipt, a confirmation, a reply that says it's handled), the FIRST bullet is `Looks like this one is done: <what shows it, in a few words> [email](link)`, slot 1 is `Mark done`, and the recommendation says so. Never close a card on your own.
   - **Due date bullet** when the review set the due date (the card's comment `Due date set to ...` has today's date), the last bullet before the recommendation: `I set the due date to <Mon D> (<reason, for example Halloween>). Want a different one? Just say so below.` Never explain the menu. When an outside date is earlier than the due date the user chose: `Heads up: <source> says <Mon D>, which is earlier than the due date <Mon D>.`
   - **Label bullet:** a comment `Health label added automatically` dated today gives `Added the Health label, since this looks like a medical card.` before the due date bullet.
   - **Past meeting or cleanup question:** a card whose block has a bullet `Past meeting: <title>, <date and time>`, or whose cached `reminder` is not empty, ends its closing reply with the question from `todo-review-actions` (**Past meetings**, **Cleanup check**) instead of the menu; the regular menu follows in the next closing reply, after the answer, except after Skip on the past-meeting question (Skip skips the whole card) and after option 1 of the past-meeting question (it marks the card done): then there is no regular menu and the next card is the closing reply. Load `todo-review-actions` first.
   - **Links in bullets:** a bullet that mentions an email, a meeting or a file ends with its link in brackets (`[email](URL)`, `[event](URL)`, `[doc](URL)`) taken from the card's Emails, Events and Documents lines. No known link: say nothing about it.
   - **Recommendation bullet, always the LAST bullet:** `Recommended: <option 1, in the words of its menu label, with its date> because <reason in a few words>.` When option 1 is a snooze add `The card wakes up early if <Name> replies.` (names from the wake list; leave the clause out when the list is empty). Never write a recommendation that differs from what option 1 does.
   - Then a blank line, the menu line (Step 3.2), a blank line and the prompt line.

2. **Show the menu.** The menu line, followed by the prompt line, ends the card's message (see **The card menu**, including its label style). The slots are built by the rules in **Step 3.2: Building the menu** in `todo-review-rules`.

3. **Act on the answer:**
   - **Slot 1 (the work):** if it is a card update (mark done, tick a checklist item, rename, set a due date, a comment), queue it. For anything else (an email, a calendar or travel event, a meeting, a linked Google file, a document, a reminder, a website sign-in, a cleanup) load `todo-review-actions` with the Skill tool (once; it stays loaded) and follow it, then carry on with the check-in and snooze rules here. If the task isn't finished, leave the card unsnoozed.
   - **Snooze picks** (slots 2 and 3, or a snooze in slot 1): follow **Snoozing**. Picks that start with `Due date to` also queue the Trello due date and use the matching comment from **Snoozing**.
   - **Skip:** change nothing on the card; move on at once with no acknowledgement line. A due date the review set stays in the queue.
   - **Stop / that's enough:** follow **Stopping the review**.
   - **A clear typed snooze or mark done:** follow **Clear snooze**, no check-in.
   - **Anything else typed:** treat it as a conversation about this card. Do what they asked (load `todo-review-actions` for anything beyond a card update), apply **Stated done is the go-ahead** if they say something is done, then run the check-in. If the same message also holds a clear snooze or mark done (for example `send the email and snooze 7 days`), do the work first, then queue the snooze or mark done as in **Clear snooze** and go straight to the next card, with no check-in. Never move to the next card on your own.

   **Check-in** (whenever the user wrote anything themselves, or the card still has parts left; never after a clear snooze or mark done, also when it was typed together with other work). ONE closing reply in plain chat text: any note (Step 3.5), then the Recommendation bullet as the LAST bullet, a blank line, the check-in line, a blank line, the prompt line. The check-in line is the card menu without the work option, built with the same icons: `Mark it done 🎉` first, only when the work looks finished (nothing open, no unchecked checklist items, no reply awaited, no upcoming meeting ahead); then the two snoozes filled like the first and second snooze of Step 3.2 (or the deadline labels for a card with a deadline in the next 31 days), leaving out any that doesn't fit; `Skip` last. If no snooze fits, the line is `Mark it done 🎉 · Skip (stays in <list>)`. **After an email or request was sent in this review** the card now waits on someone: the check-in is the date options of `todo-review-actions` (**After an email was sent**), not this line. The prompt line is exactly `Type 1–<N>, or just tell me what you have in mind.` Skip and snooze picks never get a check-in. Never label an option plain "Done" or "Finish" unless it moves the card to Done.

4. **Update the card** (not when skipped): metadata goes into the card's queue entry, and a comment only under the **Comments rule**. Move it back to `In Progress` when something new needs the user; move it to `Done` when the task is finished (check its checklists first).
5. **No recap; notes only.** What the user asked for is never repeated back: no recap bullets for an email sent, a meeting booked, a checklist item ticked, a rename, a snooze, a mark done or a skip. Gmail (Sent), Calendar and the card's comments are the record, and the wrap-up lists what changed. Write a note only in two cases, one short line each, as plain text at the top of the same reply that holds the next card (never SendUserMessage, no tool call), then a blank line:
   - **It failed or did something unexpected:** `Oops, the email to Sam didn't go out: Gmail refused the attachment.`, `Couldn't book that meeting: the slot is already taken (<title>, 3:00 PM).`
   - **Claude changed what the user asked for:** `Snoozed to Nov 9 instead, so it wakes up before the Nov 10 deadline.` (the days the user typed would have passed the deadline or the next meeting), or `Snoozed 7d (Nov 11).` when the user typed a snooze with no length.
   Never list bookkeeping such as comments, metadata, cache or queue writes, and never write a `Queued:` line. If a check-in follows, the note goes above the Recommendation bullet in that same reply and nothing is repeated afterwards.
6. Note what the user accepted, snoozed, skipped, changed or rejected: candidate learnings for Step 5.
7. Go to the next card.

When all the cards are done, never list the cards the user skipped and never ask about them: a skipped card stays where it is and comes back in tomorrow's review (count the skips for the wrap-up line `⏭️ Skipped`). Then, if the `Proposed` list has cards (and the interactive run is not stopped), proposal triage follows (Step 2c in `todo-review-actions`): the first proposal is the closing reply of the last card's answer turn. After the last proposal answer go to the learnings and the wrap-up (Step 5).

## Stopping the review
The user may not have time to go through everything, so they can stop at any time, during the proposed-task triage or the card-by-card part.

- **How they stop:** by typing something like "stop", "that's enough", "wrap up", "I'm out of time" or "pause", in the "Other" box or as a chat message, on any card or proposal, including right after the brief. Use judgment: if the text is about a card action (e.g. "stop, don't send that email"), it is about that card, not the review.
- **When they stop:**
  1. Stop showing proposals and cards and stop any running prep. Throw the prepped drafts away. Flush the **Write queue** (the answers the user already gave are real and are applied).
  2. Finish nothing new on the card or proposal in front of them. If an action was only proposed or drafted (an email draft, a meeting, a snooze without a date the user chose), it did NOT happen: say so in one line. Anything already done and confirmed stays as it is.
  3. **Cards and proposals not yet reviewed are left untouched.** No snooze, comment, metadata or list change. Unreviewed proposals stay in `Proposed`. Everything comes back in tomorrow's review.
  4. Don't ask any "anything else?" or "want to continue?" question.
  5. Go straight to **Step 5**, with one extra line: "Reviewed X of N cards and Y of M proposals. Not reviewed: <card links, top few, then 'and K more'>." If they stop before anything was reviewed, just reply with one line ("OK. Say 'let's go through my tasks' anytime to pick this up.") and skip Step 5.
- If the user says they want to continue later in the same chat, pick up with the next unreviewed proposal or card (redo any stale prep first).

## Step 4: Execute what the user chose
Trello updates (comments only under the **Comments rule**, form `**YYYY-MM-DD:** what happened / next`; checklist ticks, list moves, due dates, renames) are queued in an interactive run (see **Write queue**). Emails, meetings, documents, reminders, website sign-ins and every other action follow `todo-review-actions` (**Step 4: Execute**). Never post on social media or message anyone except by an email the user approved.

## Step 5: Wrap-up (one icon line per item)
**The wrap-up message goes first and alone**, as its own turn with no other tool call, so the user reads it while the rest happens. Send with SendUserMessage. It folds in the result of the last card's action.
**Layout:** a first line `Review done, X of N cards. Nice work!`, then one line per item below, each starting with its fixed icon, with a BLANK LINE between lines (no item runs over two lines, no paragraph). A line is shown only when it has something to say. No bookkeeping detail (for example that something was already on the card): say only what the user did and what is being written.
- `✅ Done: <what changed today: cards marked done, snoozed (until when), due dates set>`.
- `📨 Sending: <email to Name>, right now. Please keep this window open until it says sent.`: one line per queued email, with the person's name and a few words on what (the closing message then says Sent or Not sent).
- `🔄 Trello: tidying up now (<the queued changes, one short clause each, for example 3 snoozed, 1 done>)` whenever anything was queued: ONE line, exactly what is being written.
- `🌙 Offline: <each job, one short clause>, once we're done here` when jobs were queued (see `todo-offline`).
- If the user stopped early, the first line is instead `⏸️ Paused at X of N. Still waiting for you: <card links, top few, then 'and K more'>`.
- `📥 Proposals: A added, B merged, C dismissed, D already handled, E already on the board, F skipped` (only if there were any).
- `⏭️ Skipped: <N> cards, back tomorrow` (`1 card` for one): the cards the user skipped with Skip, in the menu or in a check-in; only when there were any and the review was not stopped early (a stop uses the `⏸️` line instead). No card links.
- `🎯 Tomorrow's focus: <1–3 focus items as card links>`.
- **Learnings come before the wrap-up message:** propose 0–2 new learnings from today (a correction, a rejected action, a pick other than the recommended one) while the last card is still on screen, one at a time, typed: the learning is in that reply and the closing reply is `Save this learning?` with the menu `1 Remember it · 2 Skip`. Save only what the user confirms (memory_append `- [stated] <learning>` to `/areas/life-automation-learnings.md`). Nothing is asked after the wrap-up message.
- **Last line of the wrap-up message, always:** `🎉 Done and dusted! Trello is updating itself. Catch you tomorrow, or sooner.`

**Next step (one parallel batch, right after the wrap-up message):** start the email steps first, one background Agent step per queued email (see **Emails** in `todo-review-actions`), together with the flush of the **Write queue** in the background (the Agent call, which leaves out the cards that have an email step), rewrite the **Card cache** tab (changed rows only, and every row without a `valid_until`; skip the write when nothing changed; a card the user acted on that is still in `In Progress` or `TO DO` gets a NEW row built from what the review knows about it, see **Writing it** in `todo-review-rules`), write the `Last quick check` line if a Quick run has not written it yet, save the `Board marker` once the flush report is in (**Quiet-board shortcut** in `todo-review-rules`), in Full mode refresh the Review prep tab as `todo-review-scan` says, and TaskUpdate. Keep a `Save changes` task open until the flush report is in.

When offline jobs are queued, start the one scheduled task from `todo-offline` as soon as the flush report is in, before the closing message, and add its line there if it has one.

Then the **closing message** (see **Write queue**) once the flush report is in.

## Debug mode (only when started with /todo debug or /todo-logged)
Debug mode is ON only when the run was started with `/todo debug` or through `todo-logged`, which pass "Debug mode: ON". In that case `todo-review-debug` is loaded by the router (in its second turn, or in the turn after the question on the fast path; load it yourself with the Skill tool if it is not in front of you) and follow it for the whole run: it holds the logging rules, the timestamps and the timing summary. In every other run, ignore this section and do not load it. Debug mode must not change how the review runs.

## Style
- Concise. Status first, no narration of process.
- **No narration between tool calls.** Only the fixed lines listed under **Showing text** are written before the first card (see there).
- **Show first, fetch after** (see **Speed rules**).
- **Batch independent calls.** Calls that don't depend on each other (a description update, a list move, a comment) go out as parallel calls in one message, never one per turn.
- Suggestions first, then a typed numbered menu for every choice (no popups).
- Link to Trello cards, Gmail threads and Drive files instead of pasting content.
