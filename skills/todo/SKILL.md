# /todo: Life Automation router

This skill only decides where to go. It does no review work itself.

## Step 1: Find the saved config

1. Read the memory file "Life Automation settings" (path: /areas/life-automation.md). It holds: review time, days, time zone, email lookback, home address (optional), plan type (scheduled or manual), Trello board name, log sheet name, log sheet ID. Keep what you read for the rest of the session: `todo-review` uses it and does not read the file again.
   **Daily review route (nothing typed after /todo, or only the word `debug`): the first turn is ONE parallel batch, kept as short as possible.** Before any call, write the opening line (see **Opening line**) as plain chat text. Then the calls, in this order: (a) ToolSearch `select:SendUserMessage,mcp__Google_Sheets__get_values` and nothing else; (b) memory_read of `/areas/life-automation.md`; (c) LAST, a Bash call `date -u +%FT%T.%3NZ` (the clock for the minutes in the question; in debug mode it is also Router done). In debug mode the batch is, in this order: a Bash `date -u +%FT%T.%3NZ` (the Debug start stamp, see **Debug mode**), the ToolSearch, a Bash `date -u +%FT%T.%3NZ` (the Settings start stamp), the memory_read, and the LAST Bash `date -u +%FT%T.%3NZ` (Router done). The three stamps are calls of this one batch, never a call or a turn of their own; the middle one only exists so the log can time the settings read. Load no skill, no other tool and no other file in this batch (the review reads the learnings file after the user answers). For the other routes (card, settings, pause, resume, uninstall, setup) read only the settings file, with no tool search and no opening line.
   **Fast path (the `Last prep` line).** If the settings hold a line `Last prep: <ISO UTC time> <status>` whose time falls on today's date in the user's time zone and whose status is `ok` or `partial`, then P is that time and the brief is usable: skip the meta-row read and go straight to the **fast second turn** below. When the line is missing, is from an earlier day or has another status, take the normal path (second turn: the meta-row read).
   **Fast second turn (decide and ask, no read).** Same as the third turn below, but it is the second turn: U is the later of `Last review check` and P; if U was more than 20 minutes ago, this turn is ONE batch holding only ONE SendUserMessage with the question block (in debug mode also the two stamp calls; the debug skill is loaded in the next turn, not here). The next turn is the fourth turn below, and it also holds the Skill call for `todo-review-debug` in debug mode. If the question is not due, this turn holds the three calls of the fourth turn (Brief read `A2:E200`, `todo-review`, tool search), and `todo-review` takes over as described below. If the full Brief read then shows a missing, older-dated or `failed` meta row, `todo-review` does what its **Quick or full** section says for an unusable brief.
   **Daily review route, second turn (normal path, no `Last prep` line from today): ONE short parallel batch.** Only the get_values read of the Brief tab's first rows, range `A2:E2` (the meta row: status, `prepared_at`, `prepared_date`), of the log sheet (the saved `Log sheet ID`). In debug mode the batch also holds the Skill call for `todo-review-debug`, with a Bash `date -u +%FT%T.%3NZ` as the FIRST call of the batch and another as the LAST. Nothing else goes into this batch: no skill, no tool search, no other read, so it is written and answered as fast as possible.
   **Daily review route, third turn: decide and ask.** P is the meta row's `prepared_at`, usable only if its `prepared_date` is today (user's time zone) and its status is `ok` or `partial`. U is the later of `Last review check` (from the settings) and P. **If P is usable and U was more than 20 minutes ago, the question is due:** this turn is ONE batch holding only ONE SendUserMessage with the question block: the line `Life Automation last swept everything at <U> (<N> min ago).` (`<H> h <M> min ago` from an hour on; `<Mon D>, <time>` for an earlier day; when P is later than `Last review check`: `Life Automation did its morning rounds at <P> (<N> ago).`), a blank line, `Quick lap or full tour?`, a blank line, `① Quick lap: I skip Gmail and Calendar, so I might miss anything new since <U>` on one line, `② Full tour: I check everything first, takes a little longer` on the next (the numbers are the circled digits ① and ②, one character each), then a blank line and the prompt line `Your pick, 1 or 2?` as the last line, and nothing after it; times are in the user's time zone, 12-hour, with a space before AM or PM and no leading zero (`8:14 AM`); the minutes use the clock from the first batch's Bash `date`. In debug mode the batch also holds a Bash `date -u +%FT%T.%3NZ` as the FIRST call and another as the LAST. Nothing else goes into this batch, so the question is sent as early as possible.
   **Daily review route, fourth turn (right after the question, while the user reads and types): ONE parallel batch** holding (1) get_values of the Brief tab, range `A2:E200`; (2) the Skill call for `todo-review`; (3) ONE ToolSearch with a comma-separated `select:` list of every other tool the review needs (the Google Sheets update_values, append_values, batch_clear_values and get_spreadsheet tools; the Trello read and write tools; the Gmail search, get and thread tools; the Google Calendar list and search tools; the Google Drive search tool), never one ToolSearch call per tool. That turn has no closing text (the prompt line `Your pick, 1 or 2?` is already the last line of the question), and `todo-review` takes over at the user's answer.
   **If the question is NOT due** (U was 20 minutes ago or less, or the meta row is not usable or could not be read), send no question: the third turn holds the three calls above (and in debug mode the stamps), and `todo-review` decides what happens next (Quick without a question and the one-line note, or, when the brief is not usable, its own notice and a Full review). Do not load `todo-review-rules` here: the review loads it after the user answers.
2. If you cannot read memory at all because memory is turned off (no memory tools, or they report it is off), do not look further and do not run the daily review batch above: invoke `todo-setup` at once. Its connectors screen explains how to turn memory on. Otherwise, if the file has a `setup_stage` that is not `done` (setup was interrupted, for example by a message limit), invoke `todo-setup` to resume it. Otherwise, if the file has a board name and a sheet name, treat the user as configured. If a configured user's settings have no `Log sheet ID`, find the log sheet by its title with the Drive search tool, use it, and save its ID in the settings file in a turn that does other work.
3. If the file is missing or incomplete, first check which connectors exist (one ToolSearch each for "trello", "drive" and "sheets", in one parallel batch, each with `max_results` 1 so no tools are loaded). If Trello, Google Drive or Google Sheets is not connected, skip the lookup below, because it cannot work: invoke `todo-setup` at once. Its welcome screen explains what is needed and its connectors check shows the user what to connect. Otherwise run the lookup fallback before concluding they are new:
   - Trello: search for a board named "Life Automation" (trelloSearch).
   - Drive: search for a sheet titled "Life Automation Log".
   - If BOTH are found, rebuild the memory file with what you can recover (names, plus anything visible in existing scheduled tasks via list_triggers), tell the user in one line that you restored their settings, and treat them as configured.
   - If only one is found, or neither, invoke the `todo-setup` skill. Pass along what was found so setup reuses it instead of creating duplicates.

**Never stop here with a message of your own.** This skill only routes. If there are no saved settings, the answer is always `todo-setup`, even when connectors are missing: do not tell the user to connect something and come back, and do not run any Trello or Drive call that you already know cannot work.

**Tool names.** The ToolSearch `select:` lists in this plugin use the usual connector tool names. If a name is not found, search by keywords instead (for example "google sheets get values") and use the tool that comes back; never stop because a name did not match.

**Optional tools.** Bash, the Agent tool, task lists (TaskCreate/TaskUpdate), and SendUserMessage are extras, not requirements. If one is not available in this session, do that step yourself in sequence, send the message as a normal reply, and skip the progress list. Never stop or tell the user a tool is missing because of one of these. Only the Trello, Gmail, Google Drive and Google Sheets connectors (and memory) are required.

## Step 2: Route

Look at what the user typed after /todo.

| Input | Action |
|---|---|
| nothing | Not configured: invoke `todo-setup`. Configured on a paid plan: send the opening line (see **Opening line** below), then continue with `todo-review` (loaded in the third or fourth turn). Configured on a non-paid plan (settings say manual): send the opening line, then first run the discovery and prioritizer steps inline (see Manual runs below), then continue with `todo-review` (loaded in the third or fourth turn). |
| `card`, or "this card" / "just this card" / "review this card" | Not configured: invoke `todo-setup`. Configured: invoke `todo-card` straight away. No helpers, no brief, no board walkthrough. |
| `settings` | Show the current settings in plain language. Ask what to change. Apply changes to the memory file, and if time, days or time zone changed on a paid plan, update the three helper tasks and the review task (see Timing below). |
| `pause` | Paid plans: disable the four scheduled tasks. Record "paused" in memory. Say how to resume. |
| `resume` | Re-enable the four scheduled tasks. Record "active". |
| `uninstall` | Explain what will happen first, then wait for a clear yes: scheduled tasks are deleted; the Trello board, the log sheet and the memory file are NOT deleted unless the user asks for each one by name. Delete only what they confirm. |
| `debug` | Same as the `nothing` row, with Debug mode ON (see **Debug mode**). |
| `setup` | Invoke `todo-setup` even if configured, in repair mode (it checks what exists and only creates what is missing). |

## Opening line
When a configured user starts the daily review (the "nothing" row above), the very first thing the user sees is this line, exactly: `Rolling up my sleeves for your daily review…`. **Your reply must begin with these exact words, before any tool call and before any other text, in every run, including debug runs.** Never skip it, never replace it with a sentence of your own such as "Starting the debug run…", and never put it after a tool call. Write it as plain chat text at the very start of the first turn, so the screen is never blank while the review loads. It is a line of the first turn, never a turn of its own, and it is not sent again with SendUserMessage. It is the only text this skill writes for that route. Do not write it for any other route. If `todo-logged` already wrote this line as its first text (it does), do not write it a second time.

## Timing (paid plans)

The review runs at T. The helpers run before it, in this order, because discovery and prep read the Card index tab that the prioritizer writes:
- prioritizer at T minus 75 minutes
- discovery at T minus 60 minutes
- prep at T minus 45 minutes

## Manual runs (non-paid plans)
There is no schedule, so before the review do the helpers' work inline, in this order: (1) invoke `todo-prioritizer` to rank the cards and refresh the Card index tab, (2) invoke `todo-discovery` to scan Gmail (it picks its own window: since the last review, 1 to 7 days) and fill the Proposed list. Skip prep. After the opening line, tell the user in one line that this takes a minute or two, then start the review. This does not apply to the single-card route (`todo-card`), which never runs the helpers.

## Debug mode
Debug mode is ON when the user typed `/todo debug`, or when `todo-logged` invoked this skill with `debug`. It must feel exactly like a normal `/todo` run: no extra line, no extra turn, no extra question; it only adds logging. Route exactly as above (the daily review route, whichever way it goes), and in the first batch add the three stamps in the order given in Step 1: the **Debug start** stamp as the FIRST call (it fires when the batch is sent, so the opening line written before it is not counted), the **Settings start** stamp between the tool search and the settings read, and the LAST call as **Router done**. All three belong to that one batch: never take a stamp in a call or a turn of its own before the batch, and write nothing before it except the opening line. Pass "Debug mode: ON", **Debug start: <the first stamp>**, **Settings start: <the middle stamp>** and **Router done: <the last stamp>** on to `todo-review` and `todo-review-debug`. Never take them in a turn of their own. Do not pass any of this on to another skill, and ignore it for card, setup, settings, pause, resume and uninstall.

## Rules

- Never start a review for a user who is not configured.
- Never delete the user's board, sheet or memory without a named, explicit yes.
- Speak in plain words. Do not mention skills, memory files or tool names unless the user asks.
- **Route silently.** Never write anything about the settings, the plan type, arguments, routing or which skill you are invoking (for example "Configured, paid plan, no argument, routing to the daily review"). The user sees nothing from this skill except the opening line above and the one-line notes the rules above ask for (restored settings, the manual-run minute or two). Go straight to the review, so the first thing the user reads after the opening line is the brief. **Write no text at all except the opening line and the one-line notes the rules above ask for.** Never write a plan or a summary of what you are about to do: not the settings, not the plan type, not a timestamp, not a batch, not which skill comes next. Never write a sentence like "Configured, paid plan. Send opening line, take timestamp, invoke review in one batch." The tool calls carry the work; the user sees the opening line and then the brief.
