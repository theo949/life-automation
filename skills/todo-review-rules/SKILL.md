# Daily Task Review: the rules (helper)

This helper is loaded with the Skill tool by `todo-review` (and `todo-card`) at the start of a run, once. It is not started by the user. It holds the rules the core skill points to by name. Everything in the core skill still applies (typed menus, no narration, no recaps, 12-hour times). Where a rule here says "the core", it means `todo-review`.

## Write queue (card changes are applied together, at the end)
In an interactive run the Trello card writes are not made while the user moves through the cards. They are collected in a queue (kept in your notes) and written together by ONE background step. Nothing the user does waits for them.

- **Every card write goes into the queue:** snooze, mark done, a due date the review sets or the user types, dated comments, checklist ticks, renames, list moves, metadata changes. One entry per card, holding the CHANGES, never the card's description (writing a description out costs about 4.4 s per KB): the card ID; the metadata keys to set (for example `Snoozed until: 2026-11-03`, `Snoozed from: In Progress`, `Wake on reply from: a@x.com`, `Watching since: 2026-11-03T13:04Z`, `Snooze type: plain`) and keys to remove; any exact line to add to a section; the target list ID; any due date; any dated comment; checklist item IDs to tick; any new title; any archive. `Last updated` is set by the flush, so it is not in the entry. Keep each entry to a few hundred bytes. A newer value for the same key replaces the older; comments are appended.
- **No answer line:** a queued answer is never announced: no `Queued:` bullet and no recap (see Step 3.5 in `todo-review`). The wrap-up lists what changed. Never say "Snoozed" or "Moved" for something that is only queued, except in a Step 3.5 note about a date Claude changed.
- **Later cards:** treat a queued change as already true: a card with a queued snooze is not shown again; use the description you already hold with the changes applied in your head, and never write the result out.
- **Emails are queued too, but sent first:** an approved email is an entry of its own (the approved text, recipient, cc, thread and the card's changes) that the wrap-up sends before the flush (see **Emails** in `todo-review-actions`). **Not queued:** calendar and travel events and changes to Google files happen at once, and a card where something has already left the system gets its comment and metadata written at once by a background step started in the same turn, after the reply the user is waiting for has been shown, which the user does not wait for (see **Write at once** in `todo-review-actions`).
- **When it is flushed:** once, at the wrap-up (the first action of Step 5, after the wrap-up message; proposal answers are in the same flush, nothing is flushed between the last proposal and the wrap-up); when the user stops; or before any step that needs the live card. Never by count in the middle of the run.
- **How:** start ONE background step with the Agent tool (run_in_background true), description `Tidying up N card changes`. Its prompt holds, per card, the entry as queued. Tell it, for each card: (1) read the card once (trelloReadCard `get`); (2) in the `--- 🤖 Claude metadata ---` block set and remove exactly the listed keys, add exactly the listed lines, set `Last updated` to today and leave every other character unchanged (create the block per **Card metadata format** if the card has none); (3) then update the description, move the card to the given list ID, set the due date, add the comments, tick the items, rename, archive when asked. Cards are independent: work on all at once. A card with an email entry is left out of this step: its email step (started in the same batch) sends the email and applies that card's queued changes in one description update. Read each card only once, retry a failed call once, finish with one line per card: `done` or `failed: <reason>`. If the Agent tool is not available, make the same writes yourself in one parallel batch.
- **Results:** read the report before the closing message. For a failed card try its writes once yourself; if they still fail, list it as unchanged. Include the reports of the at-once background writes (see **Write at once** in `todo-review-actions`); one that failed is listed as `Not applied: <what>`. Never report a queued change as applied before its report says so.
- **Closing message** (SendUserMessage, after the Card cache rewrite is done and the flush report is in): `✅ All saved. Trello is fresh and up to date.` or `K of N card changes applied. Not applied: <card name> (<short reason>). Say "retry" and I'll give it another go.` After an email step, the closing message also says `📨 Sent: email to <Name>, on its way!` or `Not sent: <Name> (<reason>)`. Never tell the user to keep the window open, except in the `📨 Queued` and `📨 Sending` lines while an email is waiting to be sent.
- Unattended runs queue nothing.

## Card cache (reuse cards that didn't change)
Most cards do not change from one run to the next, so their block and menu are saved and reused.
- **Where:** the **Card cache** tab of the Google Sheet "Life Automation Log". Header: `card_id, fingerprint, summary_md, reminder, options_json, written_at, written_date, source, valid_until`. Keep text cells as plain text (apostrophe prefix).
- **What is saved:** `summary_md` is the card's block as shown without the menu and prompt lines (the header line with `X/N` written literally, and its bullets). `reminder` is empty, or holds the cleanup candidates the prep found, written as `cleanup: <what> | <reason>`, several separated by ` ;; ` (see **Cleanup check** in `todo-review-actions`). `options_json` is `[{"slot": 1, "label": "<the work, at most 8 words>"}, {"slot": 2, "label": "Snooze 7d ({+7})"}, {"slot": 3, "label": "Snooze 30d ({+30})"}, {"slot": 4, "label": "Skip"}]` with date templates in place of dates (`{+7}`, `{+30}`, `{+3}`, `{+14}`, `{after_meeting}`, `{deadline-1}`, `{deadline+6}`, `{deadline+7}`, `{meeting_day}`, `{follow_up}`, `{deadline}`). A slot that can't be used is not in the list. Fill the templates at show time: dates as `Mon D` in the user's time zone, the `<N>d` count from today. Never store a finished date or day count.
- **Fingerprint:** `list | latest comment date | metadata Last updated | checklist done/total | Trello due date | flags`. `flags` is a sorted comma list of calendar-dependent states: the deadline bucket (`none`, `over31`, `within31`, `within7`, `today`, `overdue`), `fixed_deadline`, `outside_deadline`, `meeting_today`, `past_meeting_no_outcome`, `missing_travel`, `waiting_7d`, `new_email`, `woken_today` (the metadata `Woke on` date is today), `labeled_today`, and the Review prep row's `suggested_action` when there is a trusted row (Quick mode does not read the Review prep tab: leave that part out when you cannot know it, and treat a fingerprint that differs only by it as a match; Full mode follows `todo-review-scan`). Never use Trello's last-activity time in the fingerprint (the board-level time is used only by the **Quiet-board shortcut** below).
- **Using it:** read the tab in the first reads batch. For each working card compute today's fingerprint; equal to the row's: reuse `summary_md` and `options_json` (fill the dates), do not re-think the card; different or no row: prep the card fresh. A row is never reused when it is in an old format (`summary_md` contains `→ Suggested:`; `options_json` has `description` keys; a label has a weekday or the words `Snooze to`; slot 4 is not `Skip`; a 24-hour time such as `13:25`; written before 2026-10-23T14:00:00Z), or when its slots 2 and 3 are plain snoozes for a card that now has a deadline in the next 31 days, or offer `Snooze 30d` for a card that now has a future meeting.
- **Writing it:** at the wrap-up (also after a stop), rewrite the tab once: one batch_clear_values on `'Card cache'!A2:I500`, one update_values. A row without `valid_until` counts as changed: rewrite it with the value, keeping its text when its fingerprint still matches. One row per card still in `In Progress` or `TO DO`, with the fingerprint and text it had when shown. Cards that left the working lists (marked done, snoozed, archived, moved) get no row. A card the user acted on that is still in `In Progress` or `TO DO` (an email sent, a due date set, a rename and so on) gets a NEW row built from what the review knows about it after its queued changes: the new fingerprint, `summary_md` and `options_json` per **Card blocks** and Step 3.1 and 3.2, and `valid_until`; when the new state cannot be built without a read, leave the row out (the review preps it live). **Never drop the row of a working card just because it was not shown in this run:** keep every row you read at the start for a card still in a working list, unchanged, and add or replace only the rows of cards prepped live in this run. Create the tab with the header if it is missing. This write is a tool call in the parallel batch that follows the wrap-up message (with the flush Agent call), changed rows only, and skipped when nothing changed.
- **Why:** a card without a usable row is prepped live while the user waits, the one wait the user feels after a skip, snooze or done. So as soon as the brief is on screen, prep ALL cards without a usable row at once, in parallel and in review order (Step 2b). In debug mode the brief row's note says `cache N of M`, and each `card_show` row says why a card was not a hit.
- **Privacy:** only text the user already sees: no email bodies, no account numbers.
- **`valid_until` (column I):** the earliest UTC moment at which a calendar-dependent flag of the row could change by itself, or `none`. Take the earliest future one of: the start and the end of a meeting on the card; the next midnight in the user's time zone when the flags include `woken_today`, `labeled_today` or `meeting_today`; for a card with a deadline, each local midnight at which its deadline bucket changes (31 days before, 7 days before, the deadline day, the day after); 7 days after the start of a wait for `waiting_7d`. When unsure, use the next local midnight. Prep (STEP 5c) and the wrap-up rewrite write it.

## Quiet-board shortcut (Quick mode only)
A Quick run normally re-reads every list and checklist, even when nothing changed. This shortcut skips those reads when the board's own last-activity time is unchanged since the last run ended.
- **Board activity time:** the `due` field of trelloReadBoard `get` (Trello's last-activity time of the board; the connector does not name this field, so it is never trusted blindly: see the guards below). It moves when any card on the board changes, including description, label and checklist-item edits.
- **Board marker:** the settings line `Board marker: <that time, ISO> (saved <UTC ISO>)` in `/areas/life-automation.md` (memory_str_replace, memory_append when there is none).
- **It applies only when ALL of these hold** (otherwise do what a Quick run did before; in debug mode the note says `shortcut no: <first failing condition>`): (1) the board value is present, parses as a timestamp and equals the marker's time exactly; (2) the marker's saved time is no more than 2 days ago (an older marker always reads everything, as the check against drift); (3) each cheap list read returned fewer than 25 cards (25 may mean cut off); (4) every working card has a usable Card cache row (see **Using it**) with a `valid_until`, except up to 3 cards without a row, which are read with trelloReadCard `get` and prepped live in batch 2; more than 3 means the normal path; (5) every row's `valid_until` is `none` or later than now, except the rows of cards the **Prefetch** already read in batch 1 (those count as read live). A Proposed list that is not empty is read heavy in batch 2 as before; it does not stop the shortcut.
- **Working in shortcut mode:** card texts and menus come from the Card cache rows (dates filled at show time). Before any action on a card beyond Skip, Snooze or Mark done, read it with trelloReadCard `get` in the turn that starts the action, because only cached text was shown. Queued changes are read by the flush as always.
- **Saving the marker:** after the closing message (the user is not waiting), only when the flush report had no failed card and the run did not stop early: when anything was queued, read the board again (trelloReadBoard `get`) and save that time, else save the time read at the start of this run. Include `saved` = now (UTC). In Full mode the same rule applies at the end of the run. A failed or skipped save is silent: the next run simply reads everything.

## Prefetch (Quick mode, the first read batch)
Cards that will need a live read anyway are read in the first read batch, so the second batch has little or nothing left to read.
- **Expiring cards:** the settings line `Expiring today: <date> <card_id>=<UTC time>, ...` (written by `todo-prep`). Use it only when `<date>` is today (user's time zone) and the line parses. Take the cards whose time is at or before now plus 15 minutes (now = the clock the router took), at most 3; with more than 3, or no usable line, prefetch nothing (batch 2 catches expired rows as before). For each such card add to the first read batch: trelloReadCard `get` and trelloReadChecklist `list_by_card` (card ID in the long form, built like the list IDs, see **Before anything else** in `todo-review`). A prefetched card is prepped live like a changed card (its cached block is not reused), and it is never read again in batch 2, whether or not the Activity check also names it.
- **Proposed list:** always read the `Proposed` list heavy (`trelloReadCard` `list_by_list`) in the first read batch, in place of its cheap read, with no check of the saved brief first (an empty list answers in a moment). Batch 2 never reads it again, and the Quick decision checklist and the Activity check count it as already read. The `In Progress` and `TO DO` lists keep their cheap reads.
- **Debug mode:** the note says `prefetch: N cards, proposed: yes or no`.

## Quick decision checklist (Quick mode, batch 2)
A fixed checklist, answered in order with plain comparisons: no thinking, no text, no re-reading the rules. Inputs: B (board `due` value), M (marker time) and S (marker `saved` time), N (now), P (the brief's `prepared_at`), the cheap list reads, the Card cache rows.
1. B present, parses, and equals M exactly? If no: go to the Activity check.
2. S within 2 days of N? If no: normal path (all heavy reads).
3. Every cheap list read returned fewer than 25 cards? If no: normal path.
4. Every working card has a usable Card cache row with a `valid_until` (at most 3 without a row)? If no: normal path.
5. Every row's `valid_until` is `none`, later than N, or belongs to a prefetched card? If no: go to the Activity check.
All five yes: the **Quiet-board shortcut** (walk the cards with their cached rows; batch 2 holds only the closing lines, any live prep for prefetched or rowless cards, and the Proposed read when not already prefetched). A "go to the Activity check" answer means: T = the later of S and P, the touched cards are the events after T plus the cards named in the Activity check rules, and batch 2 reads only those cards (not the prefetched ones) plus the closing lines. In debug mode the note says `shortcut no: <number of the first failing question>` or `shortcut yes`.

## Activity check (Quick mode, when the Quiet-board shortcut does not apply)
Instead of re-reading every card, ask Trello what moved. The board's activity list (trelloReadBoard `list_activity`, newest first, about 500 bytes an event, read first in the turn after the **Quick decision checklist** sends the run here, not in the peek batch) names every card that had a move, comment, due date change, checklist change, attachment or creation.
- **Baseline T:** the later of the marker's `saved` time and P (the saved brief's `prepared_at`). The marker's `saved` time comes after the last review's own writes, so the review's own snoozes, moves and comments are never counted again. Events dated after T count. With no marker, or a marker older than 2 days, there is no usable baseline.
- **Touched cards:** the card IDs of events after T. **Paging:** the first page is 5 events (read in that turn). If the last event of a page is still after T, read the next page with the cursor, one page per call because each answer decides the next. The page sizes are 5, 5, 3, 3 and then 3 each time. Stop at the first page whose last event is at or before T; events at or before T are ignored. Stop as soon as the events after T name more than 8 different cards (no usable list, see below). Then add every card in the cheap list reads that is not in the Card cache, has no usable Card cache row, sits in a different list than its row says, or has a `valid_until` that has passed (a card the **Prefetch** already read in batch 1 is not added again). If the touched cards are more than 8, there is no usable list: use the normal path.
- **Hidden cards:** the list reads can leave out a card whose position Trello cannot sort (the daily `todo-prioritizer` fixes such a position, but a card moved today can still be hidden). The events you already read show where a card ended up (`listAfter`). A card whose latest move after T ended in `In Progress` or `TO DO`, and that is not in the cheap list reads, is a hidden card: add it to the touched cards, so it is read in batch 2 and walked at the end of its list. This makes no extra call. Debug mode adds `hidden: N` to the note.
- **What happens next:** touched cards are read in batch 2 (trelloReadCard `get` and trelloReadChecklist) and go through the change check; every other working card keeps its Card cache row and its cached text. The `Proposed` list is read heavy when it is not empty, as before.
- **Known gap:** a change to only a card's description may not show as an event, so the cached text stays until the next Full review. A comment, a move, a due date change, a checklist change, a new card or an attachment is always caught.
- **Debug mode:** the note says `activity: N events after T, M touched cards, hidden: H, pages: P`. Always write `hidden: H` (0 when no card was hidden), so the check shows in the log.

## Comments rule
Add a Trello comment only when it carries information the skill or the user will need later and the card does not already show. Never for bookkeeping. Comments feed the Card cache fingerprint, so a needless comment forces fresh prep next time.
- No comment: a plain snooze, a plain mark done (the move to Done is the record), a skip.
- Comment, as a marker the skill reads later: `Health label added automatically`, `Due date set to <date> (<reason>)`, `Already completed`, `Dismissed`, `Keeping … (user)`. A wake-up is never a comment: the `Woke on` line in the metadata records it.
- Comment on mark done: only when the user gave a reason.

## Learnings (stored in Claude memory, not Trello)
What this review learns about how the user likes things done is kept in Claude memory, in the file **`/areas/life-automation-learnings.md`**.

- **At the start of every run,** read that file (memory_read, in the first parallel batch with the settings, see **Before anything else**) and follow everything in it. If it doesn't exist yet, carry on without it.
- **Learnings are things the user said or confirmed,** never guesses. Examples:
  - "Prefers Claude reminders, not Google Calendar events."
  - "Writes to the city office in French + English."
  - "Doesn't want health cards brought up unless asked."
  - "Usually picks 'nudge by email' over 'wait' for cards waiting 7+ days."
  - "Gmail discovery: don't propose emails from <sender>."
- **Gmail discovery learnings:** lines that start with `Gmail discovery:` are also read by the discovery helper to decide what NOT to propose. Keep that exact prefix on them.
- **How new learnings get added:** in Step 5, propose 0–2 learnings from today's session, e.g. when the user corrected a suggestion, rejected an action, picked something other than the recommended option, or dismissed several proposals of the same kind. Ask the user to confirm. Only save what they confirm.
- **Missed self-notes (learned from the user's own cards):** in Step 5, before proposing other learnings, look at the Proposals tab rows with status `miss-candidate` (discovery wrote them when the user made a card from a note they had sent themselves that discovery had skipped). Ask about at most 2 per run, one at a time, typed: a reply with one line `I skipped your note "<the user's own words from the email, at most 12 words>" ([email](link)), but you made a card from it anyway. Should I propose notes like this from now on?`, the menu `1 Yes · 2 No`, and the prompt line. Read the thread by ID to quote the note. On Yes: queue a learning line `Discovery miss: self-sent note, <how it arrived, e.g. link with a short instruction>, skipped as no intent, user's words: "<the words>"` for the wrap-up flush, and set the row's status to `miss-confirmed`. On No: set it to `miss-declined`. Skip (typed `skip` or no answer) leaves it for the next run. The sheet row changes are made in the wrap-up batch. This is the only case where a learning is proposed from something the user did rather than said, and it is saved only after they answer Yes.
- **If the user states a preference directly** during the review ("don't do X", "always do Y"), save it right away.
- **`remember: <rule>`, typed at any prompt** (on any card, question or check-in): the user is teaching a rule, so do not ask first. Add it to the write queue as a learning to append to the learnings file, saved in the wrap-up flush (also when the user stops early), so the card in progress is not delayed. Reply with one short line (`Got it, I'll remember that.`), then show the card or question the user was on again, unchanged, with its menu and prompt line last. Do not count it as an answer to that card.
  - **Specific** (names who or what, and what to do: `tasks with Sam get the family label`, `don't propose emails from <sender>`): save it as typed. A rule about labels is saved with the prefix `Label:`, a rule about what not to propose with `Gmail discovery:`.
  - **Vague** (no concrete who, what or action: `be shorter`, `do better`, `remember that`): do not save it as typed. Say `That's a bit too broad for me to remember. Try something more specific, for example "remember: <a concrete example built from what they said>".` and ask typed `1 Save it as typed · 2 I'll reword it`.
  - **Existing cards** are not relabeled by a `Label:` rule. Only when the same message asks for it (`and relabel the current ones`), queue those label changes for the wrap-up flush as well.
- **`Label:` learnings:** lines that start with `Label:` (for example `Label: tasks with Sam get the family label`) are read by the discovery helper, which adds the named label to the proposals it creates. Keep that exact prefix on them.
- **Saving:** read the file first, then memory_append one line per learning in the form `- [stated] <learning>`. If a new learning contradicts an old one, replace the old line (memory_str_replace) instead of adding a conflicting one. Create the file with memory_write if it doesn't exist, with frontmatter: name `life-automation-learnings`, a one-line description ("How the user likes the daily Trello task review run: confirmed preferences and learnings"), sources [cowork].
- Keep the file short. Merge similar lines rather than piling them up.
- Never store health details, finances or other sensitive personal details as learnings.

## Deadlines
The Trello due date is the one place a card's deadline lives.
- A card's **deadline** is its Trello due date.
- **Outside deadlines:** while reviewing a card you may find a real deadline that is not in the due date: a bill or statement due date, a filing deadline, an appointment, a holiday or party date, a latest delivery date, an RSVP date. Say where it came from (for example "from the card comments" or "from the supplier's email").
  - **The card has no due date:** the review sets the Trello due date to that date by itself, when it shows the card (this is a queued write, see **Write queue**; it goes into the same queue entry as whatever the user picks next). The card's last bullet says so in the wording of Step 3.1. The queued comment is `**YYYY-MM-DD:** Due date set to YYYY-MM-DD (was: none). Source: <where it came from>`. From then on the date is the card's deadline for every rule below, and the card gets the normal deadline menu (Step 3.2). Never do this when the user has just told you not to, or when nobody is there to answer (unattended runs change nothing, so they only mention the date).
  - **The card has a due date and the outside deadline is earlier:** the review does not change the due date by itself, because the user chose it. The outside date counts as the deadline for the snooze rules, the card gets a bullet ("Outside deadline: Oct 28 (supplier's email), earlier than the due date Oct 31"), and the menu offers `Due date to <Mon D> + snooze ...` (see Step 3.2). Picking it is the user's yes, and the comment is `**YYYY-MM-DD:** Due date moved from YYYY-MM-DD to YYYY-MM-DD. Source: <where it came from>`.
  - **The card has a due date and the outside deadline is later:** ignore the outside date.
  - If the user answers "change the due date to X" after the review set it, queue the new date (see **Write queue**) and add `**YYYY-MM-DD:** Due date changed from YYYY-MM-DD to X (user request)`.
- **Fixed date or movable.** Decide for every card with a deadline in the next 31 days whether the date can slip, from the reason for it:
  - **Fixed:** the date is set by an event that will not move: a holiday or party (Halloween, a birthday), an appointment or meeting, an RSVP for an event, a trip or flight, a delivery that must arrive before such an event. Moving the due date would only hide the real deadline.
  - **Movable:** the user could simply do it later: a bill, a filing, a renewal, a task the user gave themselves, or a due date the user typed on the card without an event behind it.
  - A due date the review set itself takes the kind of its reason. When unsure, treat it as movable. A fixed date never gets a `Due date to <later date> + snooze ...` pick (see Step 3.2). The user can still type a new date themselves.
- **A snooze must never hide a card past its deadline.** A snooze is only allowed if the card comes back **at least 1 day before** the deadline. The one exception is the deadline move in slot 3 of the menu (see Step 3.2): it moves the due date first, and the snooze is then checked against the new date.
- Cards with a deadline in the next 7 days show up in **every** daily brief under ⏰ until they're done, unless the user snoozed them to a date before the deadline.

## Card metadata format
Metadata lives in the card's description field, inside this exact block:

```
--- 🤖 Claude metadata ---
Last updated: YYYY-MM-DD
Woke on: YYYY-MM-DD (date reached | reply from Name | date reached, waiting on Name)   (only present on a card the prioritizer or prep woke; replaced at the next wake, removed when the card is snoozed again)
Snoozed until: YYYY-MM-DD   (only present while the card is snoozed)
Snoozed from: <list name>   (only present while snoozed: the list the card returns to)
Wake on reply from: email@example.com   (every snooze that has contacts to watch, see "Every snooze wakes on a reply")
Watching since: YYYY-MM-DDTHH:MM:SSZ   (only present with `Wake on reply from`: the UTC time of the newest message the user has seen or sent on the card; a reply sent after it counts as new, see **Watching since**)
Snooze type: plain   (only present with a snooze made when the card is NOT waiting on someone)
## People
- Name <email>, role (e.g. translator, accountant)
## Documents
- Title: Drive / Docs / Sheets / Slides / Forms / Claude artifact URL
## Events
- YYYY-MM-DD HH:MM: event title | calendar event URL   (a past event's line ends with (done), (not done) or (didn't happen) once its outcome is known)
## Emails
- Who or topic: Gmail thread URL
## Others
- Description: URL, or a plain note   (websites, Trello cards, Claude chats, videos, phone reminders)
--- end ---
```

Sections:
- **Fixed order:** People, Documents, Events, Emails, Others. A section with nothing in it is left out. Never write an empty header. **Every section title is a large markdown heading on its own line** (`## People`, `## Documents`, `## Events`, `## Emails`, `## Others`), never a plain `People:` line. When you next write a block that still has plain titles, convert them to `##` headings. The header lines above People (Last updated, Woke on, Snoozed until and the rest) stay plain.
- **Put each item in the section by what the item is, not by where it came from.** Use judgment; it won't be perfect, and that is fine:
  - **People:** only a person, or an organization, practice or service the user deals with, who has an email or phone. One line, `Name <email>, role` (phone instead of email if that is all there is), with a role of at most 5 words. No history or status in a People line (`invited Oct 13, RSVP yes` belongs in the RSVP sheet or a dated comment). Someone with no contact details is not listed; the fact goes to the relevant sheet or a comment.
  - **Documents:** anything stored as a file or document: Drive files and folders, Google Docs, Sheets, Slides and Forms, Claude artifacts. A document with no link yet is described in words. **One short line per document, 12 words or fewer, in the shape `<What it is> (<kind>): <link>`** (for example `RSVP responses (Sheet): <link>`). Never put dates, counts, names or statuses in a Documents line (they go in a dated card comment or the status instead). Before adding a document, check whether its link is already listed: if so, update that line, never add a second one.
  - **Events:** meetings, appointments, errands and calls that have a date and time. The event's calendar link goes at the end of the same line after ` | `, never on a line of its own. A calendar link with no known date goes on a line `Calendar event (date not recorded) | URL`. Sort by date, oldest first. A new in-person travel event is still not added (see **Meetings and travel** in `todo-review-actions`), but a travel event link already in a block stays, as `YYYY-MM-DD HH:MM: Travel: <meeting title> | URL`. One line per calendar event, and old past lines are dropped: see **Keeping the Events list short** in `todo-review-actions`.
  - **Emails:** Gmail threads and messages. The helpers read this section to find a card's email threads (the card index is built from it), so every Gmail link goes here and nowhere else. One line per thread, written `<Who or topic>: <thread link>`, 12 words or fewer, with no dates, statuses or history. A new message in a thread that is already listed changes nothing here; a different thread gets its own line. Check that the link is not listed before adding it. The history of a thread goes only in a dated card comment, and only when it says something the card does not show.
  - **Others:** everything else: websites, Trello card links, Claude chat links, videos, phone reminders, plans and notes without a type.
  - When an item could fit two sections, use the more specific one. When it is unclear, put it in Others. Never drop an item (the one exception: a person with no contact details, see People).
- **Instruction sections:** some cards carry their own section in the block, for example "Track in daily review (until the party):". Leave those exactly as they are, directly under the snooze lines and above People.
- **Keep each line's wording** when sorting: sorting only moves lines to the right section. The exceptions are the Documents, People and Emails line rules above: whenever the block is next written for a real reason, shorten any Documents line (12 words or fewer, counts and statuses go to a dated comment or the sheet), People line or Emails line that breaks its rule. No mass rewrite of old cards.
- **Duplicates:** one line per file. When two Drive files look like duplicates, ask the user ONE typed question before anything is deleted. Claude deletes only files it made itself; the user's own files are only flagged.

Rules:
- **Only ever edit text inside this block.** Everything outside it is the user's own notes. Never change, reformat, move or delete it.
- When updating a description, read the current description first, replace only the block, and write back everything else exactly as it was.
- If the card has no block yet, add it at the **bottom** of the description, below the user's notes, separated by a blank line.
- If a description already contains a block, update it. Never add a second one.
- Update `Last updated` every time you change the block with real news or a real change. the Full scan (`todo-review-scan`) uses it to know what counts as "new".
- `Snoozed until` in this block is the single source of truth for a snooze date. Never use the Trello due date for it: due dates are real deadlines. Every snooze line, including `Watching since`, is removed when the card wakes.
- `Woke on` is written only when a card is woken: by the prioritizer, by prep, or by the Full scan (`todo-review-scan`) for a wake that is still open. Quick mode only reads it (the `woken_today` flag) and removes it when the card is snoozed again.

## Stated done is the go-ahead
When the user says something is done (in "Other", as a chat message, or in an answer) and it clearly matches an unchecked checklist item, tick that item without asking (queue the tick, see **Write queue**). If the match is unclear, ask first with a typed yes/no question (see **Choices**). This applies in the single-card review too.

## Meetings when a card goes to Done
Applies every time a card is about to move to Done, however the user asked: the Mark done option, a typed `mark done` or `done`, the combined checklist question, or the same in `/todo card`. (The past-meeting question, option 1 "It happened, mark the card done", is its own question and stays as it is.)
- **Look only at what you already hold:** the card block the user saw (its `[event]` bullets) and the Events lines when the card was read in full. Never read the card or search the calendar just for this.
- **When it applies:** the block shows an upcoming meeting (a future date) with a calendar link, and nothing says the meeting has guests besides the user. Then, before queueing the move, the closing reply is ONE typed choice with two options (see **Choices**), and no yes/no question and no Skip: a first line that names what is at stake, `<Card name>: <Mon D> <title> meeting`, a blank line, the menu line `① Mark done and bin the meeting · ② Mark done, keep the meeting`, a blank line and the prompt line `Type 1–2, or just tell me what you have in mind.` Add `(and its travel event)` to the first line and to option 1 only when the card shows a travel event (an Events line that starts with `Travel:`); otherwise name just the meeting (the delete step still removes a matching travel event if it finds one). With several upcoming meetings, name them all on the first line and write `meetings` in both options. When checklist items are also open it is still ONE reply, with the first line `<Card name>: <Mon D> <title> meeting, open item: <item>` and the options `① Tick <item>, mark done and delete the meeting · ② Tick <item>, mark done but keep the meeting` (the checklist tick happens on both). Not wanting the card done at all is not an option: if the user types something else (`not yet`, `leave it`), do that, leave the card where it is and show its regular menu again.
- **No question:** when the user already said what to do with the meeting in the same message (`mark done and remove the meetings`, `mark done, keep the meeting`), do that. When the block shows no upcoming meeting, queue the move as before. When the meeting has guests besides the user, queue the move and put one note line at the top of the next card: `<card> is done! The <title> meeting stays on your calendar though, because it has guests.`
- **On 1:** queue the move to Done as usual. Show first, start after: the first batch of the turn holds only the next card (or the closing reply), sent with SendUserMessage, and then, in a second batch of the same turn, right after the first returns, start ONE background step (Agent tool, `run_in_background` true), not waited for. The turn's final text adds nothing. The step loads the Google Calendar tools itself (ToolSearch inside the step), deletes the meeting (the event ID is the first word of the decoded `eid` in its calendar link, on the user's primary calendar) and its travel event (title `Travel: <meeting title>`, the same day, found with `list_events`; see item 6 in `todo-review-meetings`), then reads the card (trelloReadCard `get`), removes the meeting's line from the Events list, sets `Last updated`, and adds one comment `**YYYY-MM-DD:** Removed meetings: <title> (<date>)`. Calendar changes are never queued. The step's report is read before the wrap-up, like the other at-once steps. If it fails, the next closing reply starts with `Couldn't remove the <title> meeting from your calendar: <reason>.` and the card stays in Done. If the Agent tool is not available, do the same steps in the same turn.
- **On 2:** queue the move only; the meeting's line stays as it is.

## Snoozing
To snooze a card, queue all of these (see **Write queue**); nothing is sent now:
1. Metadata: remove any `Woke on` line, set `Snoozed until: <date>` and `Snoozed from: <the list the card is in now>`, plus `Wake on reply from`, `Watching since` and `Snooze type: plain` as in **Every snooze wakes on a reply**. If the card has no metadata block yet, the flush creates it (see **Card metadata format**).
2. Move the card straight from its current list to the right Snoozed list for the date (see **Snoozed buckets**). Create a missing Snoozed list first.
3. No comment for a plain snooze: the metadata already says it. (See **Comments rule**.)

Do not change the card's due date, except when the review sets a missing one (see **Deadlines**) or the user picked a slot that starts with `Due date to`: then the due date is one more write in the same queue entry.

**Snooze fast path.** Use what you already hold: the description from the list reads and the list IDs. Do not re-list the board, do not re-read the card to "verify", do not run a check-in for a snooze pick or a clear typed snooze. The next card goes out at once, with no recap.

**Mark done fast path** ("Mark done" suggested action or "Mark it done 🎉"). Queue: the move to `Done`, plus a dated comment `**YYYY-MM-DD:** <reason>` ONLY when the user gave a reason (for example "Alex repaid in full"); no comment otherwise. Use the checklist state from the prep batch: only if it showed unchecked items, warn and ask first. No verify reads. A checklist item the user just reported done goes into the same entry. Before queueing the move, apply **Meetings when a card goes to Done**.

Kinds of snooze (metadata only differs):
- **Plain:** `Snoozed until: <date>`, plus the wake list, `Watching since` and `Snooze type: plain`.
- **Before the deadline:** `Snoozed until: <deadline minus 1 day>`, for cards with a deadline.
- **Until reply:** `Snoozed until: <follow-up date>` plus `Wake on reply from: <email(s)>` and `Watching since`; no `Snooze type: plain`.
- **Until the meeting day:** `Snoozed until: <date of the card's next future meeting>` (tomorrow or later); never later than 1 day before the deadline. If the meeting is today: `Snoozed until: <next working day after the meeting>` with the comment `**YYYY-MM-DD:** Snoozed until YYYY-MM-DD (after today's meeting: <meeting title>)`.

### Every snooze wakes on a reply
- The wake list (`Wake on reply from`) is every email under People in the card's metadata, comma-separated, minus the user's own address and automated senders (the part before the @ contains noreply, no-reply, donotreply, do-not-reply, notification, notifications, portal, mailer, automated or alerts). If nothing is left, write no `Wake on reply from` line. **The line holds only email addresses and `@domain` entries.** Never write a name or a description there (for example a first name, an organization name or `the council office`): `todo-discovery` searches Gmail with this list, and a name in it once made the search return nothing, so a reply from a listed address was never found. A person with no email on the card is left off the list. When you rewrite a card's existing wake line, turn any name in it into that person's address from the People lines, or drop it.
- **Watching since** goes in every snooze that has a wake list. It is a full UTC time with seconds (`2026-11-03T13:04:27Z`), never only a date or minutes (a reply or an auto-acknowledgement in the same minute must not be mistaken for a later one), and it is NOT the time of the snooze: a reply can arrive in the minutes between an email and the snooze, or after the card summary was written. It is the later of: (a) the time the user's last email on this card was sent in this review (read the sent message's time; if it is not available, read the clock right before sending); (b) the sent time of the newest message from someone else that the card showed the user (a `replied` bullet); (c) when neither exists, the time the card summary the user saw was written (its Card cache `written_at`, or the time the card was read live). Never use the time of the snooze itself. When the card is snoozed from a path that has none of these, use the time the card was read in this run.
- `Snooze type: plain` goes in the metadata of a snooze made when the card is NOT waiting on someone. Leave it out when the card is waiting (we emailed or asked and nothing came back), so the snooze still counts as waiting.
- **Delivery watch:** when the card is waiting for a delivery or shipment, the wake list also holds the seller's domain as `@seller.com`.
- **Same-domain replies (guidance, use judgement):** companies often answer from a different address than the one that wrote to us (a notification address writes, a support address replies). So when a card waits on an organization, also add its domain to the wake list as `@domain`, unless it is a popular shared mail service (gmail.com, googlemail.com, hotmail.com, outlook.com, live.com, yahoo.com, icloud.com, proton.me and similar). A `@domain` entry is a lead, not an automatic wake: `todo-discovery` STEP 2c reads the mail and decides whether it is about this card's task. Signs it is not related: a noreply or no-reply sender, marketing, promotions, newsletters, news digests, surveys, product announcements, or a topic unrelated to the card. A pure auto-acknowledgement (ticket or receipt confirmation, out-of-office) usually does not wake the card, but a support or assistant reply that answers what we wrote does. When unsure, err on the side of waking too much rather than too little: a wrongly woken card costs one skip, a missed reply can cost a deadline. Learn from the user's reactions the same way discovery learns from proposals (STEP 1d): a domain wake the user immediately skips or snoozes again without acting counts against that sender. For a delivery watch the seller's `@seller.com` stays as it is. Replies are found by `todo-discovery` STEP 2c and written to the **Wake hits** tab; the review and prep read that tab instead of searching Gmail for wakes. **Replies in known threads count from anyone:** a new message by someone other than the user in a thread that is already on the card (its hex ID is in the card's `thread_ids_hex`) also wakes the card, even when the sender is not on the wake list (for example the email was forwarded and a third person replied); discovery logs it with `matched_address` `thread`. The same automated-sender rule applies, and a pure auto-acknowledgement never wakes: it becomes a Card news row (needs_action `no`) that the review shows as news.

### The snooze date: the user's, or the recommended one
- A menu label that shows its date, or a typed length or date, is the user's choice.
- **A typed snooze with no length or date** (`snooze it`, `snooze`, `next week`): apply the recommended snooze at once (the one the card's Recommendation bullet names, normally 7 days), in the same pass, and never ask `Snooze until when?`. Step 3.5 note: `Snoozed 7d (<Mon D>).`
- **A length that runs past the deadline** (later than 1 day before it) **or past the card's next future meeting** (a meeting today is no limit): use the latest allowed date instead and say so in the Step 3.5 note (`Snoozed to Nov 9 instead, so it wakes up before the Nov 10 deadline.`). Never ask again.
- If no date fits at all (the latest allowed date is today or earlier), do not snooze: say so in one line and run the check-in without snooze options. Never go on to the next card while a snooze the user asked for was neither applied nor explained.
- Skip is not a snooze.

### Clear snooze (typed by the user)
- A typed snooze with a clear length or date counts as the user's choice: `snooze 3 days`, `until Friday`, `2 but make it Friday`. Use the number exactly (`3 days` is today plus 3 days, whatever weekday), unless it runs past the deadline or the next meeting (see above).
- It ends the card like a menu pick: queue (Snooze fast path), next card. No check-in and no recap. The same goes for a clear typed `mark done` when prep found no unchecked checklist items.
- **Typed together with other work** (`send the email and snooze 7 days`, `reply to Sam and mark done`): do the work first, then queue the snooze or mark done here and go straight to the next card. No check-in, and no date options after an email, because the user already chose.
- **A typed "it's done" or "the work is done"** that leaves nothing open (no unchecked checklist items, no reply awaited, no upcoming meeting) is a clear mark done: queue the move to Done (Mark done fast path), next card. No check-in. If checklist items remain, ask ONE combined question: `Tick <item> and send the card off to Done?` with `① Yes, both · ② Tick it, keep the card · ③ Skip`. A typed done on a card whose block shows an upcoming meeting is not a clear mark done: apply **Meetings when a card goes to Done**, which holds the question for that case (combined with the checklist question when both apply).
- Ask only when `mark done` is blocked by unchecked checklist items. A missing, vague or too long snooze is never asked about (see above).

## Snoozed buckets
Weeks run Monday to Sunday (in the user's time zone). Compare the card's `Snoozed until` with today:
- `Snoozed/Waiting this week`: on or before this Sunday.
- `Snoozed/Waiting next week`: from next Monday through next Sunday.
- `Snoozed/Waiting later`: anything after next Sunday.
`Snoozed from` keeps pointing to the list the card returns to when it wakes. The prioritizer does the rolling and waking. Quick mode does neither; Full mode only does what is left over (see `todo-review-scan`). A card that still has a `Snoozed until` line but sits in `TO DO` or `In Progress` was moved there by the user: treat it as woken, and clear the snooze lines the next time its metadata is written.

## Showing progress between cards (so the user always knows which card we're on)
In some places (e.g. the Chrome side panel) the writes after an answer show only as generic lines like "Write Trello card", and text between tool calls is collapsed. Without the rules below, the user sees "Working on it" and can't tell which card is next.
1. **One task per card.** Create one task per card with TaskCreate (all in one parallel batch) in the first turn after the first card is shown that has tool calls for another reason (an email, live prep, a sheet write), or at the wrap-up when there is none. Never in the turn that holds the reads before the first card: writing the tasks out delays that card. Keep each task short (the description repeats the subject). Subject: `Card X of N: <card name>`. activeForm: `Reviewing card X of N: <card name>`. Mark a card's task in_progress (TaskUpdate) when its message is shown and completed when it is handled (finishing option chosen, snoozed, skipped or marked done), but only inside a turn that has tool calls for another reason (an email, live prep, a sheet write). Never give the updates a turn of their own, and never add them to a turn that would otherwise have no calls: every turn from an answer to the next card is call-free (see **Speed rules**). The task list catches up in the next turn that has calls, or at the wrap-up (several updates in one batch), so it may lag a card or two.
2. **No transition line.** The next card's header already names the card (`X/N`) so a line like "Card X done. Next: ..." would only repeat it. A Skip, and a Skip chosen in the check-in, get no acknowledgement line either: the next card's header (`X/N`) shows that the review moved on.
3. **Slow turns.** Before any turn that will take noticeable time (a board re-read after 30+ minutes, live prep for a card with no cache row, a travel-time lookup, a long write batch), send `Preparing card Y of N: <card name>...` with SendUserMessage first, so the user sees what the wait is for. This is the only line that may come before a card.

## Step 3.2: Building the menu
Used at Step 3 of the core when a card block is written. The menu line, followed by the prompt line, ends the card's message (see **The card menu** in the core, including its label style). Build it like this. Every snooze label shows its day count and its real date, which counts as the user choosing that date. Write the day count N in `Snooze <N>d` as the number of days from today to the date:

   **Slot 1, the work:** the suggested action as a label of at most 8 words that says exactly what 1 does (`Email Sam: confirm last year is closed`, `Compare 3-4 small desks (Google Doc)`, `Mark done`). Detail goes into the block's bullets, never into the label. If the card has a trusted row in the **Review prep cache**, start from its `suggested_action` (see its mapping there); shape it with the saved learnings and the card's emails, calendar and activity. Special cases:
   - **A future meeting on the card went stale** (see **Meeting cleanup** in `todo-review-actions`): slot 1 is the fix, `Rebook <meeting>` or `Check the <place> booking`, with the draft or the lookup ready; when nothing is needed any more it is `Remove the <Mon D> meeting`. This comes before the special cases below, because the card's next step depends on it.
   - **Waiting on someone** (we already emailed or asked them and nothing has come back) with nothing else open: slot 1 is a nudge, `Email <Name> a nudge`, with the draft ready. The user can still pick 2 or 3 instead.
   - **The only thing still open is an upcoming meeting** (a future, not stale meeting in `Events:`, no unchecked checklist items, no reply awaited, no email to send, no missing travel event): slot 1 is a snooze to the meeting. If the earliest such meeting is tomorrow or later, it is `Snooze <N>d (<Mon D>, meeting day)`, so the card is awake the day of the meeting for a reminder and last-minute things. If the meeting is today, the card is already in front of the user, so it is `Snooze <N>d (<Mon D>, after the meeting)`, the next working day after the meeting (a Friday, Saturday or Sunday meeting gives Monday). Skip this if that date is later than 1 day before the card's deadline.
   - **The only thing still open is waiting for a date** (a delivery, a reply or a visit that can't be sped up) on a card with a deadline in the next 31 days: slot 1 is the snooze to the day before the deadline, `Snooze <N>d (<L as Mon D>)` (L is defined below), and slot 2 then takes the shorter snooze (see below) so no two slots say the same.
   - If the work doesn't finish the task, nothing else is needed: the card stays unsnoozed and comes back in every review.

   **Slots 2, 3 and 4, cards without a deadline in the next 31 days:** `Snooze 7d (<Mon D>)`, `Snooze 30d (<Mon D>)`, `Skip`.

   **A meeting on the card** (a future, not stale meeting in `Events:`, whether or not it is the only thing open): `Snooze 30d` is never shown, and the numbers close up. If the meeting is tomorrow or later, any snooze that would come back after the meeting day is left out too (the meeting-day snooze above is the exception: it is the meeting day itself). If the meeting is today, snoozes past tonight are fine. For a card whose only open item is tonight's meeting the menu is, for example, `1 Snooze 3d (Oct 26, after the meeting) · 2 Snooze 7d (Oct 30) · 3 Skip`.

   **Cards with a deadline in the next 31 days** (the deadline as defined in **Deadlines**, including a due date the review has just set; call the day before it the last day, L). Snooze 7d and Snooze 30d are never shown for these cards. Fill slots 2 and 3 like this, so that all four numbers show whenever possible:
   - **Slot 2:** `Snooze <N>d (<L as Mon D>)`. If slot 1 is already that snooze, slot 2 is `Snooze 3d (<Mon D>)`, only when that date is earlier than L (otherwise slot 2 is left out).
   - **Slot 3, movable deadlines only:** `Due date to <deadline plus 7 days as Mon D> + snooze <N>d (<that new date minus 1 day, as Mon D>)`. Picking it is the user's yes to move the Trello due date, and counts as the user choosing both dates. If slot 2 was left out, slot 3 still shows.
   - **Slot 3, fixed-date deadlines** (see **Deadlines**: a holiday, party, appointment, RSVP, trip): there is no `Due date to` pick, because moving the date would hide the real deadline. If slot 2 is not the plain snooze to L, slot 3 is `Snooze <N>d (<L as Mon D>)`; otherwise slot 3 is `Snooze 3d (<Mon D>)` when that date is earlier than L; otherwise slot 3 is left out. Never fill slot 3 with a pick that only repeats another slot.
   - **When the outside deadline is earlier than the card's due date** (the review did not change the due date, see **Deadlines**): slot 2 is `Due date to <outside deadline as Mon D> + snooze <N>d (<L of the outside deadline as Mon D>)` (this picks the real, earlier date, so it also applies to fixed-date deadlines), and slot 3 is `Snooze 3d (<Mon D>)`, only when that date is earlier than that L (otherwise slot 3 is left out). Slot 1 stays the work, or the plain snooze to that L when waiting is the only thing open, in which case slot 2 is the `Due date to ...` pick and slot 3 the short snooze.
   - **No room:** a snooze to L is only possible if L is later than today. If it is not, the snooze to L is left out. The `Due date to ... + snooze ...` pick stays whenever its own snooze date is later than today, for movable deadlines only.
   - **Picks that start with `Due date to`** count as the user's yes to write the Trello due date, and as the user choosing both dates.
   - **Slot 4** is `Skip`.
   - A slot that is left out is not written as a dash or any placeholder: the line just skips it and the numbers close up (see **The card menu**).
   - Typed text can still ask for something else (for example `2 but Friday`): check it against the deadline rules.

   Typed text beyond the number is the user's own action or a chat about this card, and "stop" ends the review (see **The card menu**).
