# Review prep (helper, paid plans only)

Does the slow, read-only prep for the daily review ahead of time and writes it to the **Review prep** tab of the Google Sheet "Life Automation Log", so the review (`todo-review`) starts fast. It also builds the daily brief and saves it to the **Brief** tab (STEP 5b), so the brief is ready to show the moment the user opens the review, and pre-writes every working card's block and menu options to the **Card cache** tab (STEP 5c), so the review mostly just shows them. It runs silently as a scheduled task 45 minutes before the review, after `todo-prioritizer` (75 minutes before) and `todo-discovery` (60 minutes before). Non-paid plans never run it: the review preps live. Cards that `todo-prioritizer` woke today are normal working cards (see STEP 2).

Never send, draft, label, archive or delete any email. Never create or change calendar events. Never write to Trello, with THREE exceptions: the metadata-only block in STEP 3b (no comments, moves, labels, snoozes, checklist changes, titles or due dates), the `Health` label with its one comment in STEP 3c, and waking a card on a reply in STEP 3e (one move and the block's snooze lines replaced by the `Woke on` line, nothing else). Never message anyone. Never create scheduled tasks; the only scheduled-task change allowed is aligning this task's own cron in STEP 0. The only things you may write are the **Review prep** tab (STEP 5), the **Brief** tab (STEP 5b) and the **Card cache** tab (STEP 5c), each rewritten every run, and the `Last prep` line (STEP 5b) and the `Expiring today` line (STEP 5c) of the settings file; read the other tabs only. Keep IDs and dates as text (prefix with an apostrophe). **Privacy:** the Review prep tab gets pointers, flags and codes only: no subjects, names, amounts or free text. The exceptions are the **Brief** tab and the **Card cache** tab, which hold text the user would read in the review anyway: card titles, short details in the review's format, and menu option labels, never email bodies, quoted email text or account numbers.

## STEP 0: Settings and schedule check
Load `todo-review` and `todo-review-rules` with the Skill tool in the same batch as the settings read: the review sections this skill points to by name (**Card metadata format**, **Card cache**, Step 3.1, Step 3.2, **Time format**) are in them. Read `/areas/life-automation.md`. If missing, or paused, say so in one line and stop. Use the saved time zone and the saved board and sheet names. Find the board by name in Trello and the sheet by title in Drive; never use stored IDs.
Mondays only: list_triggers (recurring, enabled; follow next_cursor) and find "Life Automation: review". This task (named "Life Automation: prep") must run exactly 45 minutes before it, same days. If its cron differs, update_trigger it (saved time zone, hour and minute computed minus 45) and continue.

## STEP 1: Context (read-only)
a) Read `/areas/life-automation-learnings.md`. Lines starting `Gmail discovery:` are exclusions; respect any line saying a topic must not be brought up unless asked.
b) Read these tabs: **Card index** (`card_id, title, list, people_emails, thread_ids_hex, last_updated, refreshed_date, events, link_domains`), **Card news** (`found_date, thread_id, last_msg_date, card_id, sender_domain, category, needs_action, notes`), **Proposals** (`found_date, thread_id, card_id, sender_domain, category, suggested_list, status, outcome_date, outcome_list, notes`). If the newest `refreshed_date` in Card index is older than yesterday, the prioritizer did not run: do your own Gmail search for every card's people instead of trusting Card news, and set the final status to `partial`.
c) Work out today's date in the saved time zone (python3 zoneinfo) and read the clock with one bash command (`date -u +%Y-%m-%dT%H:%M:%SZ`). Never write a time from your own estimate and never round it: a guessed `10:50:00Z` once showed the user a run time that never happened. Read the clock again right before the Review prep write and again right before the Brief write; each write uses its own fresh reading as `prepared_at`.

## STEP 2: Read the board
Read all lists except `Done` and `Proposed`. **Review order** (the order the review walks the cards): the working lists are `TO DO` and `In Progress`; start at `In Progress` and then `TO DO`; within a list, top to bottom by card position. Due dates do not change this order. Cards in the three Snoozed lists are not prepped as cards, but every one of them gets a Review prep row (STEP 3d), and their metadata is checked for stale FUTURE meetings (STEP 3 calendar check). Keep what STEP 3d and STEP 5b need from them: list, `Snoozed until`, `Wake on reply from`, `Watching since`, `Snooze type`, Trello due date and last activity. **Cap:** full prep for the first 35 working cards in review order; for the rest write a row with `reason_codes=no_prep_cap` and `suggested_action=none`, and count them as cap overflow. Keep each card's labels too (STEP 3c), and look up the board's `Health` label by name (trelloReadBoard list_labels). **Cards woken today.** `todo-prioritizer` (75 minutes before the review) already wakes the cards whose `Snoozed until` has arrived and moves them back to `TO DO` or `In Progress`, and writes the metadata line `Woke on: YYYY-MM-DD (date reached)` (with `, waiting on <Name(s)>` when the card was waiting on someone). A card whose `Woke on` date is today is a normal working card: full prep (STEP 3), a Review prep row and a Card cache row (STEP 5c) with the flag `woken_today`. When the `Woke on` line says `waiting on`, treat it as a card that was waiting on someone: if no reply came, the suggested_action is `nudge`, as for a snooze until reply.

## STEP 3: Per-card prep (read-only)
Use subagents in batches of about 5 cards if the Agent tool is available, otherwise batch independent tool calls. Run the subagents on a lighter, faster model (for example Haiku) when the Agent tool lets you choose one; the main run keeps the writes and the final judgment. For each card read the full card (description, comments), its checklists directly (trelloReadChecklist; the plain card read can show none), and its `--- 🤖 Claude metadata ---` block. Record:
- **deadline:** the earliest of the Trello due date and any hard external deadline you find (bill or statement due date, filing deadline, appointment), as YYYY-MM-DD, empty if none.
- **new_thread_ids_hex and news:** Gmail thread IDs (hex) involving the people in the card's metadata, newer than the block's `Last updated`. Take them from the Card news rows for this card_id with `last_msg_date` later than `Last updated`; do your own read-only Gmail search for the card's people only when the card is missing from Card index, Card index is stale (STEP 1b), or the card has `Wake on reply from` and the Wake hits tab has no `run` row from today (otherwise take its replies from the Wake hits tab, see reply_woke). Read each new thread with get_thread to judge whether it needs action; write the IDs and codes, and for the newest message the **gist** below. news=yes if any new thread exists.
- **gist:** for a card with a new reply or email (new_reply, woke_reply or new_email), what the newest message says, as facts: numbers, dates, yes or no, the question asked, at most 20 words, no quotes and no email text beyond that (for example `Dana: the report is attached and the deadline is Friday`). Write it at the start of the row's `notes` as `gist: <text>`. Never `read the email`.
- **calendar_change:** none, new (a new event involving the card's people since `Last updated`), moved or deleted (a future meeting listed in `Events:` no longer exists at that time; search Google Calendar for a moved version before saying deleted). Never flag past meetings for removal. If Google Calendar is not connected, write none.
- **reason_codes** (comma-separated, only those that apply): new_reply, new_email, calendar_changed, meeting_past_no_outcome (a connected meeting in the last 14 days whose line in `Events:` has no (done), (not done) or (didn't happen)), missing_travel (only when a home address is saved: a future in-person meeting within 14 days with no event titled like "Travel" ending at its start or up to 15 minutes before; judge in-person from title, location and thread), cleanup_candidate (something on the card is clearly no longer needed: a meeting that was cancelled or replaced, a file or link the card no longer uses; name it and the reason in one line `cleanup: <what> | <reason>`, up to 3 per card, never for past meetings that already happened; never delete anything, the review asks the user), checklist_outdated, title_outdated, description_outdated, linked_file_news (for linked Google Sheets, Docs or Slides: read comments with get_spreadsheet commentsIncluded=true and Drive read_file_content includeComments=true; new or changed threads since `Last updated` count; cap 10 linked files per run), deadline_soon (deadline within 7 days), waiting_7d, looks_done (the evidence shows the card's own task is already done: a payment receipt or confirmation, a delivery notice, or a reply that says it is handled; name it in one line `done: <what shows it>`), no_metadata, metadata_added, no_change.
- **suggested_update:** none, or a comma list of checklist, title, description, when developments made them outdated. Do not write what should change.
- **suggested_action** (one code): send_email, snooze_until_reply (waiting on someone after we asked or emailed and nothing came back), snooze_until_meeting (the ONLY open item is a future, not stale meeting, today or later, not later than 1 day before the card's deadline, with no unchecked checklist items, no reply awaited, no email to send, no missing travel event), schedule_meeting, update_card (checklist, title or description update only), mark_done (only when clearly finished, always with `looks_done`), nudge (waiting 7+ days with no reply), none, needs_review (anything unclear or unusual). Never decide a snooze date.
- **confidence:** high only when the evidence is direct (e.g. a reply that plainly answers the question); med if reasonable inference; low if guessing.
- **medical:** yes only when the card clearly concerns medical care (see STEP 3c), otherwise no. Used only for STEP 3c; it is not written to the sheet.
Cards without a metadata block: write `no_metadata`, still fill deadline and any news found; the first 5 are enriched in STEP 3b, and the live review handles the rest.

## STEP 3b: Add metadata to cards that have none (a Trello write)
Cards in `TO DO` and `In Progress` with no `--- 🤖 Claude metadata ---` block, in review order, **up to 5 per run**. Skip cards labelled `Health`, cards the learnings say not to touch, and cards with too little to search on (vague title, no description or comments).
- Search Gmail and Google Calendar (read-only) within 30 days before and after the card's creation, for the people or topic in the card.
- **Write only when the evidence is direct:** a person named in the card (name or email in the title, description or comments), or a Gmail, Calendar or Drive link already in the card, matches what you found, and the topic fits the card's title. If it is a guess, write nothing and leave `no_metadata` for the live review.
- **How to write:** read the current description first. Append the block at the BOTTOM, below the user's notes, with a blank line before it, using the review's **Card metadata format** (sections People, Documents, Events, Emails, Others in that order, each item in the section for what it is, empty sections left out, `Last updated` = today). Follow its line rules too: a People line is only for someone with an email or phone, written `Name <email>, role` with a role of at most 5 words and no history or status (leave out people with no contact details); a Documents line is `<What it is> (<kind>): <link>`, 12 words or fewer, with no dates, counts or statuses; one line per file; an Emails line is `<Who or topic>: <thread link>`, 12 words or fewer, one line per thread, no dates or history. One description update per card (trelloWriteCard update), all of them sent as parallel calls in one message. Never edit text outside the block, never touch the title, due date, list, labels or comments, and never write a second block.
- Give those cards the reason code `metadata_added` (not `no_metadata`); emails from before today are not "news" for them. Add `metadata_added=N` to the meta row notes.

## STEP 3c: Health label (a Trello write)
The board's `Health` label marks medical cards. For every working card (`TO DO` and `In Progress`) that does not have the label yet and whose STEP 3 prep says `medical=yes`, add it. **Medical means direct evidence of medical care** in the card's title, description, comments or People: a surgery, a hospital or clinic, a doctor, a prescription, a lab or pathology result, a medical test or an appointment with a care provider. A guess, a general wellness or fitness topic, or a passing mention gets no label. Rules:
- **Add the label only.** Never remove or change any other label, and never touch the title, due date, list or description.
- **Cap:** up to 10 cards per run, in review order. If the board has no `Health` label, skip this step and say so in the run record.
- **One comment per labeled card,** right after adding it: `**YYYY-MM-DD:** Health label added automatically` (today's date in the saved time zone, no reason given). The review reads this comment to show a one-line note on the card, and it is the audit trail. Add the label and its comment as parallel calls, all cards in one message.
- This run cannot ask the user: the label is silent and easy to remove. Count the cards in `health_labeled=N` in the meta row notes.
- A card labeled in this run is a changed card: its Card cache row (STEP 5c) is written fresh with the label bullet.

## STEP 3d: Snoozed cards (read-only)
The review skips reading the Snoozed lists when this step has done the work. For EVERY card in the three Snoozed lists compute, from what STEP 2 already read (no extra card reads):
- **wake_today:** `Snoozed until` is today or earlier (the user's date).
- **reply_woke:** the card has `Wake on reply from` and a real reply from one of those addresses was sent after the card's `Watching since` time (compare the real send times in UTC, never only dates; a card with no `Watching since` line falls back to the snooze day): read the **Wake hits** tab first: a row for this card_id whose `sent_utc` is after the card's `Watching since` is a reply (discovery already checked sender or thread, and time; a row with `matched_address` `thread` is a reply from someone who is not on the card, in a thread already on it, and counts the same). Also check Card news as in the 🆕 bullet of STEP 5b (get_thread; ignore the user's own messages, automated senders and auto-acknowledgements; a `@domain` entry is a lead that discovery has already judged: trust its Wake hits row, see **Same-domain replies** in `todo-review-rules`). If the Wake hits tab has no `run` row from today (discovery did not run), do one Gmail search over this card's wake list only. Put the reply's thread ID in `new_thread_ids_hex`.
- **reply_woke by your own note:** the card has a Card news row with category `self-note`, needs_action `yes`, whose thread the user sent after the card's `Watching since` time (no such line: on or after the snooze day). Mark it `reply_woke` as well, put the note's thread ID in `new_thread_ids_hex` and add reason code `woke_note`. This is the one case where the user's own message counts.
- **wrong_bucket:** the card sits in a Snoozed list that does not match its `Snoozed until` date (weeks run Monday to Sunday, see the review's **Snoozed buckets**); `notes` gets `bucket=this`, `bucket=next` or `bucket=later` (the right list).
- **stale_meeting:** a future meeting in `Events:` that no longer exists or is earlier than `Snoozed until` (the STEP 3 calendar check): set `calendar_change=deleted` as for other cards.
- Otherwise `no_change`. A card with `Snoozed until` in the future and nothing else is `no_change`.
Every snoozed row gets `notes` = `until=YYYY-MM-DD` (plus the bucket when needed). No names, titles or addresses. Do not wake or move a card for `wake_today` or `wrong_bucket`: the prioritizer does the date-based wakes and the weekly roll at 7:45; a card that still shows `wake_today` or `wrong_bucket` here means it did not run or a move failed, and the review then does it. A `reply_woke` card is the one wake you do yourself, in STEP 3e.

## STEP 3e: Wake cards on a reply (Trello writes)
For each snoozed card marked `reply_woke` in STEP 3d, do these two writes as parallel calls (all cards in one message), the same way the prioritizer wakes a card on a date:
- Remove only the lines `Snoozed until`, `Snoozed from`, `Wake on reply from`, `Watching since`, `Snooze type` and any older `Woke on` from the card's metadata block, and add the header line `Woke on: YYYY-MM-DD (reply from <Name(s)>)` (for a card with reason code `woke_note`: `Woke on: YYYY-MM-DD (your note)`) (today's date; names from the card's People lines that match the sender addresses, the addresses when no name is known) directly under `Last updated`. Write the rest of the description back exactly as it was and leave `Last updated` unchanged.
- Move the card to the list named in `Snoozed from` (`TO DO` when the line is missing or that list does not exist).
Retry a failed write once. If it still fails, leave the card as it is, keep it marked `reply_woke` and list it in the run record: the review then wakes it. After the move, the card's Review prep row becomes `item_type=card` in its new list (not a `snoozed` row), `news=yes`, `new_thread_ids_hex` = the reply thread, `reason_codes` includes `woke_reply`; it gets a Card cache row in STEP 5c like every other working card (written after the move, so it has the new list and the `woken_today` flag). Never wake a card for any other reason here.

## STEP 4: Proposals
Read the `Proposed` list (cards with their `--- 🤖 Claude proposal ---` blocks). One row per proposal (`item_type=proposal`, `item_id` = the card's object id). Fields: list = the block's Suggested list; deadline = Suggested due (empty if none); new_thread_ids_hex = the block's Thread ID; `proposal_suggestion`:
- **add** (default: a real task for the Suggested list);
- **merge** (only when the block's Possible match is a Trello card and the email clearly belongs on that card by people AND topic; put that card's object id in `merge_target_card_id`);
- **dismiss** (only when a `Gmail discovery:` learning applies, or the Proposals tab shows that the sender_domain or category group has at least 3 resolved rows (accepted, dismissed or merged) with at least 70% dismissed and the email has no amount, due date or direct personal request, or the user's own message is already the last one in the thread);
- **completed** (the thread shows the user already handled it, e.g. their reply is last and answers it, or the amount was paid).
`reason_codes` from: possible_match, learned_dismiss, learned_accept, already_handled, due_soon, personal_request, old_7d (Found 7+ days ago), no_signal. `confidence` as above. Suggestions only: never move, label, archive or change proposal cards.

## STEP 5: Write the cache
Compute all rows first. Then, in ONE update_values call (so the tab is never half written) after one batch_clear_values on `'Review prep'!A2:P500`, write from A2 these rows in this column order: `item_type, item_id, list, deadline, new_thread_ids_hex, calendar_change, news, suggested_update, suggested_action, proposal_suggestion, merge_target_card_id, reason_codes, confidence, prepared_at, prepared_date, notes`.
- **First row = the meta row:** `item_type=meta`, `item_id=run`, `news` = status (`ok`; `partial` if Card index was stale, any read failed or the cap overflowed; `failed` if the board read returned nothing), `prepared_at` = the `date -u` reading taken right before this write, as an ISO string (e.g. 2026-10-19T05:14:00Z; never a guess or a rounded time), `prepared_date` = today's date in the saved time zone (YYYY-MM-DD), `notes` = counts like `cards=31;proposals=4;snoozed=23;snoozed_meeting_checks=2;card_index_refreshed=YYYY-MM-DD;cap_overflow=0;health_labeled=1;errors=none` (no names or titles).
- Then all card rows in review order (`item_type=card`), then one row per snoozed card (`item_type=snoozed`, `item_id` = the card's object id, `list` = the Snoozed list it sits in, `deadline` = its Trello due date if any, `calendar_change`, `new_thread_ids_hex`, `reason_codes` and `notes` from STEP 3d, `suggested_action=none`), then the proposal rows (`item_type=proposal`). Fill `prepared_at` and `prepared_date` on every row. The tab holds up to 500 rows; if the board has more cards than fit, write the snoozed rows last and leave `snoozed=` out of the meta notes, so the review reads the Snoozed lists itself.
- If the board read failed, still replace the tab with only the meta row (status `failed`) so the review knows there is no prep today.

## STEP 5b: Build and save the brief
Build the daily brief the way the review's Step 2 would, from the rows you just computed and the cards you already read. Read nothing new except where noted. Follow the review skill's Step 2 layout exactly (sections, icons, one item per line, about 5 items per section and then "and K more"). Everything here is read-only. **Times and dates:** follow the review skill's **Time format**: convert every time and date from UTC to the saved time zone (take the date from the converted time), and write clock times as `H:MM AM` or `H:MM PM` (for example `10:30 AM`), never 24-hour.
- **Title line:** `Your brief for <Day Mon D>` in the saved time zone. Just this; the review shows it as it is, with no prepared time.
- **🆕:** one bullet per card row with `news=yes` or `calendar_change` new or moved (a neutral one-line summary from the thread you already read, with the card link and the Gmail thread link); one bullet per card the prioritizer woke today (its metadata has `Woke on` with today's date): `[card](link) is awake and back in <list> (snooze over)`; one bullet per card STEP 3e woke on a reply: `Reply from <Name>: <the gist, at most 12 words>. [card](link), in today's review`; one bullet per snoozed card whose `Snoozed until` is today or earlier and that is still in a Snoozed list (`[card](link), snooze ended, in today's review`); one bullet per snoozed card with `Wake on reply from` (plain or not) where a real reply from those addresses was sent after the card's `Watching since` time (no such line: after the snooze day): check the Card news tab first (rows for the card with a `last_msg_date` on or after the day of `Watching since`, then get_thread, comparing the real send times in UTC), and search Gmail only if the card has no usable rows; ignore messages from the user and from automated senders (noreply, portal, notifications and the like). Say who replied and what it says (the gist, at most 12 words), and put when the reply was sent at the end, in the saved time zone: `Reply from Dana: sent the full report, asks you to confirm the date. [card](link) (Oct 22, 12:00 AM)`. If there is nothing: `🆕 Nothing new since the last run`. **A reply or snooze-ended bullet never names a list and never says `wakes` or `the review wakes`** (the wake is a queued write, so the card may still sit in its Snoozed list when the brief is read): it says `in today's review`. **Every 🆕 bullet ends with its own time** in the saved time zone, `(<Mon D>, H:MM AM/PM)` for the email, reply or calendar change, or `(<Mon D>)` for a wake. (When this prep is the latest update, the review keeps these bullets and adds what is new since then; when the user reviewed after the prep, it replaces the section with its own. Do not add a baseline time.)
- **📥:** up to two lines, each shown only when its count is above zero, from the proposal rows. **New** = found today (the date found in the proposal block): `📥 N fresh task ideas from Gmail (found today)`. **Older** = found before today: `📥 K older task ideas still waiting for your verdict`. Singular and plural follow the count. No clock time, never `found 7+ days ago`, never `0 found`. Only if there are proposals.
- **📝 Notes to yourself:** one line in the same section as 📥, only if the count is above zero. Count the Card news rows with category `self-note`, `found_date` today (saved time zone), grouped by card. One card: `📝 1 note to yourself went onto an existing card: [<card title>](link)`; several: `📝 N notes to yourself found a home on existing cards: [A](link), [B](link)` (up to 3 names, then `and K more`). Add `(woke up)` after a card that STEP 3e woke on such a note. A note that became a proposal is counted in the 📥 line, never here. A 🆕 bullet for a card woken by a note reads `Your note, <Mon D>: <the user's own words, at most 12 words>. [card](link), in today's review`.
- **⏰ Due soon:** overdue, due today and due in the next 7 days from the `deadline` column, plus snoozed cards with a Trello due date on or before today. Leave out any card whose row has `looks_done` or `mark_done`, and any card now in `Done` or archived. A snoozed card says when it comes back as `(wakes tomorrow)` or `(wakes <Mon D>)`, never `snoozed until` and never `(wakes today)` (a card waking today appears in the review's walkthrough, so its line shows only its date). Date first, sorted by deadline. The label of each line says what it is and who it is from: for a bill or invoice, `[Pay <Sender> <amount>](link)`. When the item is a proposed task, or a card whose title does not say who a bill is from or how much it is (for example `Pay invoice TV-344`), build the label from the card's proposal block (From, Why) or its People and Emails lines, never just a reference number. Example: `- Overdue (Oct 21): [Pay Acme Utilities $104.94](link) (proposed task)`.
- **⏳ Waiting on:** snoozed cards with `Wake on reply from` and without `Snooze type: plain` (every snooze now also wakes on a reply, but only the ones where we are waiting on someone are listed here): who, card link, since the snooze date, follow-up date.
- **💤 Stale:** working cards with no activity for 7+ days (up to 5), or `💤 Stale: none`.
- **😴 Snoozed:** `😴 Snoozed: N this week · N next week · N later`, counted by list.
- **🧹:** `🧹 Stale future meetings: N on M cards` from rows with `calendar_change=deleted`. Only if there are any.
- **Leave out** the "prepared" time (it is never shown), the ▶️ line and the "Type /todo" line: the review adds those when it shows the brief.

Write it to the **Brief** tab of the log sheet. If the tab does not exist, add it first (Google Sheets update_spreadsheet, add a sheet named `Brief`) with the header row `line_no, kind, text, prepared_at, prepared_date`. Then, after one batch_clear_values on `'Brief'!A2:E200`, write ONE update_values from A2: first the meta row (`line_no=0`, `kind=meta`, `text` = the same status as the Review prep meta row, `prepared_at` from a fresh `date -u` reading right before this write, and `prepared_date` as in STEP 5), then one row per brief line in order (`line_no` 1, 2, 3 and so on, `kind=line`, `text` = the line exactly as it should be shown; an empty line is `kind=blank` with empty text). Fill `prepared_at` and `prepared_date` on every row. Keep every text cell as plain text (apostrophe prefix) so a line that starts with a dash is not read as a formula. If the board read failed, write only the meta row with status `failed`.

The meta row is the one place the review reads to decide whether to ask its Quick or full question, so it must be written first and correct.

**The `Last prep` line (a shortcut for the review, best effort).** In the same batch as the Brief write, also write one line to the settings file `/areas/life-automation.md`: `Last prep: <prepared_at> <status>` (the same `prepared_at` and status as the Brief meta row, for example `Last prep: 2026-11-05T06:15:02Z ok`). Replace the existing `Last prep` line (memory_str_replace, using the version from your settings read; on a version conflict read the file again once and retry once), or append it when there is none (memory_append). Some scheduled tasks cannot write that file; if the memory tools are missing, or the write is refused or fails, skip it silently: do not retry, do not mention it in the run record, and do not treat it as an error. The review falls back to reading the Brief meta row. When the board read failed, write the line with status `failed`.

## STEP 5c: Pre-write the cards (Card cache)
Write every working card's block and menu options ahead of time, so the review only has to show them. Follow the review skill's **The card menu**, **Card blocks**, **Card cache**, Step 3.1 (card block shape) and Step 3.2 (menu rules) exactly; this step is read-only apart from the sheet.
- **Which cards:** EVERY card in `TO DO` and `In Progress`, with no skips, so the review never has to prepare a card live in Quick mode. This includes the cards you woke in STEP 3e: compute their fingerprint after the move (the new list, `woken_today` in the flags, `Last updated` unchanged), and the reply gist bullet comes first in their `summary_md`. A card with suggested_action `needs_review` or confidence `low` is written too: when you are unsure, its Recommendation bullet is plain (the card's own next step if it is known, otherwise `Recommended: Work on <card name> because it is in <list>.`) and never an invented reason. A `no_prep_cap` card (not read in detail) gets a minimal block: the header line, the deadline bullet if any, and the same plain Recommendation bullet. A card whose row has a `gist:` note still gets its newest-message bullet first (the review cannot read Gmail in Quick mode).
- **Per card:** the fingerprint (exactly as the review's **Card cache** defines it, computed for the user's today; a card labeled in STEP 3c carries the flag `labeled_today`), `summary_md` (the card block without its menu line: `**X/N. [card name](link)** · list · deadline if any` and 1–2 bullets, each ending with the `[email]`, `[event]` or `[doc]` link of what it mentions (see **Links in bullets** in the review), then the **Recommendation bullet** of Step 3.1 as the last bullet (`Recommended: <option 1 with its date template filled at show time> because <reason>.`, with the wake clause when option 1 is a snooze, and for a delivery wait the seller domain written `@seller.com` in the wake list, see Step 3.1); use `X/N` literally, the review numbers the cards; no `→ Suggested` line; a card labeled in STEP 3c gets the bullet `Added the Health label, since this looks like a medical card.` before any due date bullet), `reminder` (the `cleanup: <what> | <reason>` lines of the card's cleanup_candidate, one per line, otherwise empty), `options_json` (the four menu slots from Step 3.2 as `[{"slot":1,"label":"<the work, at most 8 words>"},{"slot":2,"label":"Snooze 7d ({+7})"},{"slot":3,"label":"Snooze 30d ({+30})"},{"slot":4,"label":"Skip"}]` with date templates `{+7}`, `{+30}`, `{deadline-1}`, `{+14}`, `{meeting_day}`, `{after_meeting}`, `{follow_up}`, `{deadline}`, never finished dates), `written_at` (UTC), `written_date` (user's date), `source=prep`, `valid_until` (as the review's **Card cache** defines it). For a card with a future meeting, slot 3 is not `Snooze 30d`: use the review's meeting menu instead, with `{meeting_day}` for a meeting tomorrow or later and `{after_meeting}` for a meeting today, and never a date past the meeting day otherwise.
- **Newest message first:** a card with a `gist:` note gets as the FIRST bullet of `summary_md` `<Name> replied <Mon D, H:MM AM/PM>: <the gist> [email](link)` (Step 3.1 **Newest message bullet** in the review), and its Recommendation bullet uses those facts.
- **Respect the learnings:** a card the learnings say must not be brought up unless asked gets no summary details beyond its title.
- **Write:** if the tab does not exist, add it (update_spreadsheet, sheet named `Card cache`) with the header `card_id, fingerprint, summary_md, reminder, options_json, written_at, written_date, source, valid_until`. Then one batch_clear_values on `'Card cache'!A2:I500` and ONE update_values from A2 with one row per card. Keep every text cell as plain text (apostrophe prefix). Rows for cards you did not pre-write are left out (the review writes them live). If the board read failed, leave the tab as it is.
- **The `Expiring today` line (a hint for the review, best effort).** Right after the Card cache write (same batch), write one line to the settings file `/areas/life-automation.md`: `Expiring today: <user's date> <card_id>=<valid_until ISO UTC>, <card_id>=<valid_until ISO UTC>` listing every row you just wrote whose `valid_until` is later than now and earlier than the next local midnight (the midnight itself does not count), in time order; when there is none, `Expiring today: <user's date> none`. Same rules as the `Last prep` line: replace the existing line (memory_str_replace with the version from your settings read, one retry on a version conflict), append it when there is none, and skip it silently when the memory tools are missing or the write fails (never an error, never mentioned in the run record). Write no line when the board read failed. The review only uses it to read those cards early, so a wrong or missing line costs time, never correctness.
