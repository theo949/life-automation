# Daily Task Review: debug mode (helper)

Debug mode is ON only when the run was started with `/todo debug` or through `todo-logged`, which pass "Debug mode: ON". In every other run this whole section is ignored and nothing is logged. Purpose: find out exactly where the waiting time goes. **Debug mode must not change how the review runs**: same batching, same prefetch, same questions, no extra reads, no calls made one after another that would otherwise be parallel.

### What to log
Log every turn in which you make tool calls or send the user something, plus the moments the user answers. One row per turn:
`run_id, seq, ts_utc, step, card_id, calls, note, end_ts_utc, out_kb`
- `run_id`: the run's start time, `YYYYMMDD-HHMM` (user's time zone). `seq`: 0 is the `debug_start` row (step `load_settings`, note `debug_start`) with the **Debug start** timestamp (the first Bash call of the router's first batch); it costs no call. If `todo` passed **Settings start: <timestamp>** and **Router done: <timestamp>**, log Settings start next as seq 1 (step `load_settings`, note `settings read start`, no calls) and Router done as seq 2 (step `load_settings`, note `router done`, no calls), then number the rest 3, 4, 5 ... in order. If only **Router done** was passed, log it as seq 1 and number the rest from 2; if neither, number from 1. The gap from seq 0 to seq 1 is the writing of the router's first batch plus the tool search; the gap from seq 1 to seq 2 is the settings read when the app runs a batch's calls in order, and about 0 when it runs them together (say which one it was in the summary); the gap from the router row to the next row is this skill's load plus the writing of its first batch. Put `skill loaded, first batch` in that next row's note.
- `ts_utc`: from `date -u +%FT%T.%3NZ`. If there is no Bash tool, use the `current_time` tool and say once that timestamps are less precise.
- `step`, one of: `load_settings`, `brief`, `prep_read`, `status_read`, `proposal_show`, `proposal_answer`, `card_read`, `freshness`, `prefetch`, `pack`, `card_show`, `shown`, `ask`, `answer`, `answer_start`, `write`, `snooze`, `skip`, `mark_done`, `email`, `calendar`, `meeting_check`, `gmail_search`, `sheet_read`, `sheet_write`, `wake_check`, `wrapup`. Use the closest one.
- **Quick or full:** the question gets an `ask` row, and the first batch after the answer an `answer` row whose note says `mode quick` or `mode full`. A run that skipped the question (last update 20 minutes ago or less) puts `mode quick, no question` in the note of the `brief` row. This keeps the two modes comparable.
- **Wake decisions (step `wake_check`).** Each time you decide whether a snoozed card wakes or stays snoozed because of email (the freshness search hit in **Review prep cache**, the live wake check in **Waking cards**, both in `todo-review-scan`; logged in Full mode only), add one row per card with no extra call and no extra turn: put it in the notes and save it with the other rows. `card_id` is the card; `calls` is empty; `note` has at most 6 neutral codes separated by spaces: `src=freshness` or `src=cardnews` or `src=gmail`, `thread=<hex id>`, `inlist=yes|no` (sender is in the wake list), `in_window=yes|no` (newest message sent after W, the later of R and P), `newest_ours=yes|no` (the newest message in the thread is the user's or an automated sender's), `known=yes|no` (thread already in the Card index, the prep row or the card's Emails), then `decision=wake` or `decision=stay` and, for stay, `why=<one of: not_in_list, before_window, newest_ours, known_thread, own_or_automated, prep_row_no_change, not_checked>`. Also log one `wake_check` row with `decision=not_checked` for every snoozed card whose row was `no_change` but which has a Gmail hit from a wake-list sender. Never names, addresses or email text.
- `card_id`: the card's object id, or empty.
- `calls`: the tool names in this turn, joined with `+` (for example `trelloWriteCard+trelloWriteCard+trelloReadCard`). Count repeated names, e.g. `trelloWriteCard x2`.
- `note`: at most 6 neutral words (for example "cache row trusted", "live prep, no row"). For read turns add the size and count of what came back (for example `3 lists 41 cards 180KB`), since big results are a main source of waiting; sizes and counts only, never content. For every `card_show` row the note says where the card came from: `cache hit`, `fresh: changed`, `fresh: no row` or `fresh: old format`. **Never titles, email text, names, addresses or free text from the user.** For the brief turn put the number of chunks in the note (`brief, 5 chunks`). In Quick mode the `answer` row of the turn after the reads also says `shortcut yes`, or `shortcut no: <first failing condition>` (see **Quiet-board shortcut** in `todo-review-rules`). The Card cache rewrite and the Review prep refresh each get their own `sheet_write` row (note `card cache N rows`, `review prep N rows`), so a missing write shows in the log.

### How to take timestamps without slowing the review
- **Columns:** `run_id, seq, ts_utc, step, card_id, calls, note, end_ts_utc, out_kb`. If the Debug tab still has only the first 7 columns, add the two new header cells once (H1:I1) before the first append. Older rows keep those two cells empty.
- **Two stamps per batch.** In every turn that makes tool calls, the FIRST call is a Bash call `date -u +%FT%T.%3NZ` that also appends the row to the scratch file (draft nothing before it), and the LAST call is a second Bash `date -u +%FT%T.%3NZ`. Both go inside the same parallel batch as the turn's other calls, never in a turn of their own. **Exception (reply first, then background):** in a turn that removes a meeting on mark done or starts any other at-once background write, the first batch is ONLY the SendUserMessage with the reply: no stamp, no `answer_start` row, no other call, and nothing to deliberate about. Both stamps go in the second batch, the one that starts the background step, and the note of that row says `reply batch unstamped`. **Same for the brief:** in the Quick answer turn, batch 1 (the brief messages and the `Peeking` label) is unstamped too and holds nothing else; both stamps go in batch 2 (the peek batch), whose note says `brief alone, peek_start` and lists the order of its calls (board, cache, lists, skill, learnings). **What the stamps mean (checked on Nov 5):** in some environments both fire when the batch is sent, about 0.1 s apart even when the batch holds Trello reads, so they mark the moment the model finished writing the batch, not the moment the tools finished. In others (the browser chat) the calls of a batch may run in order, and then the last stamp is taken after the calls before it have finished, so the gap between the two stamps is tool time. `ts_utc` is the first stamp and `end_ts_utc` the last. The wait for the tools shows as part of the gap to the next batch's first stamp, together with the model's reading of the results and the writing of the next batch; the three cannot always be separated. The note of a batch that reads (for example the quick-mode batch with the brief chunks, the Card cache and the list reads) adds the count and size of what the reads returned (for example `2 lists 18 cards 140KB, cache 8 rows`). `out_kb` is the size in KB (one decimal) of everything written in that batch's calls (descriptions, comments, message text, sheet values); writing takes roughly 4.4 s per KB (measured on Oct 28), so it is a good guess for how long the model needed to write that batch.
- **When a card appears in a turn that has calls for another reason** (live prep, an email, the wrap-up), the `shown` row is logged by a Bash call placed as the LAST tool call of that turn, right before the card is written. That call is also the batch's end stamp: do not add a third Bash call. Turns that only move on to the next card get the `answer_start` row of the timed-walk bullet below.
- **Answers.** For every user answer that needs calls (an email, live prep, the work), the first batch after it is logged with step `answer` and the real step in `note`; its `ts_utc` is the moment the turn started. Call-free answers (skip, snooze, mark done) are handled by the next bullet. The numbers to watch for simple actions come from the user's own timing and the `sent HH:MM` notes.
- **Timed walk (debug mode only; replaces the call-free rule for the card loop).** To learn where the wait between a press and the next card goes, every answer turn that only moves on to the next card (skip, snooze, mark done, and the recap-and-card turns after them) starts with ONE Bash call, the first thing in the turn: `date -u +%FT%T.%3NZ` that also appends the row `answer_start` to the scratch file. Right after it comes the normal reply (recap, next card, menu); nothing else is added and nothing is checked. The row: `run_id, seq, ts_utc, step=answer_start, card_id=<the card just answered>, calls=Bash, note=<skip|snooze|mark_done> <cache hit|fresh: <why>> block <N>B skill <K>KB`, where N is the byte size of the card block about to be written (menu included) and K the size of this skill. The stamp is taken after the model has started and thought, so the gap between the user's press and this stamp is app time plus the model's thinking, and the gap from this stamp to the card on screen is one extra pass plus writing. These turns are slower than normal ones because of the extra pass; the summary says so. Debug mode changes nothing else about how the review runs. If the user's message carries a "Message sent at HH:MM" time, add `sent HH:MM` to the note of that row. The user may also report the clock seconds of a press and of the first text; add them to the note of that row as `press HH:MM:SS, text HH:MM:SS`.
- **The quick-or-full question gets its own `ask` row.** When the settings hold a `Last prep` line from today, the router sends the question alone in its second turn (no meta-row read; this skill is loaded in the turn after it, so log that turn's start from its first stamp) and the turn after the question reads the Brief tab; log the question turn as the `ask` row and note `fast path`. Otherwise the router reads only the Brief meta row in its second turn (a short batch: the read and this skill's load) and sends the question alone in its third turn; the fourth turn (Brief read, `todo-review` load, tool search) happens while the user reads (see **Quick or full** in `todo-review` and Step 1 of `todo`). Log the second turn as a `brief` row (note `meta row read, debug skill loaded`), the third turn as the `ask` row (its first stamp is the time the question was sent) and the fourth turn as a `brief` row (note `brief N rows, tools loaded`). This skill's own load is part of the second turn only in debug mode, so that turn is a little slower than in a normal run: say so in the summary. The `answer` row is the first call of the next batch.
- **The Peeking step (Quick mode).** To time the step behind the `🔎 Peeking at Trello…` label, the Quick batch that sends that label holds ONE more Bash call `date -u +%FT%T.%3NZ`, placed right after the label's SendUserMessage (in the same parallel batch, nothing else changes). Its value is `peek_start`; write it into the note of that batch's `answer` row as `peek_start <HH:MM:SS UTC>`. In the next turn (the reads are back) the first stamp gives `reads back after N s` (that stamp minus `peek_start`); put it in that row's note. The first `card_show` row after it adds `first card N s after peek_start` and, when that card needed live prep (`fresh: no row` or `fresh: changed`), says so in the same note. The same batch holds ONE more Bash call `date -u +%FT%T.%3NZ` as its LAST call (after the reads); its value is `reads_sent`. Write into the same note `tools T s` where T is `reads_sent` minus `peek_start`, and `Claude writing W s` where W is the later `reads back` stamp minus `reads_sent`. If `reads_sent` is less than 0.2 s after `peek_start`, the calls ran together and the split is not possible: write `split not possible`. These notes only use stamps that are taken inside the batches the review already makes, so the review runs exactly as without Debug mode.
- The first stamp is taken as soon as the turn starts, so the batch's own writing does not inflate it. The gap between the two stamps still mixes writing time and tool time, which is why `out_kb` is logged. A tool result still cannot be timestamped the moment it returns.
- Scratch file: `debug-<run_id>.tsv` in the working directory, one appended row per turn. It is the backup if the session dies. Also keep every row in your own notes as you go.

### Saving to the sheet
- Save to the **Debug** tab of the log sheet (create it with the header `run_id, seq, ts_utc, step, card_id, calls, note, end_ts_utc, out_kb` if it is missing) with one append_values call, from your notes (the scratch file is the backup).
- Save at the wrap-up, when the user says stop, and after every 5 cards. A periodic save goes in the same batch as that card's writes, so it costs no extra turn. Append only rows not saved yet.
- If saving fails, say so in one line and tell the user where the scratch file is. Never retry in a loop.

### The summary at the end
After the normal wrap-up (Step 5, or **Stopping the review**) and after the Card cache and Review prep writes, send one more message with SendUserMessage, computed from the rows in one Bash call over the scratch file (or by hand if there are few rows):
- `Debug summary (<run_id>)`, then a line: `Timings include logging overhead.`
- `Settings read:` the gap between the Settings start and Router done stamps in seconds, and whether the app ran the batch's calls in order (gap of seconds) or together (gap near 0).
- `Average from your answer to the next item on screen: X s (slowest Y s, [card link])`
- `Walk anatomy:` for each action type (skip, snooze, mark_done) the number of actions, the average gap from the `answer_start` stamp to the previous stamp, the share that were cache hits and the average card block size. Say that these turns include one extra pass for the stamp.
- `Slowest 3 turns:` one bullet each: step, calls, seconds, then the gap to the next batch and the estimated writing time (from `out_kb`); the rest is tools plus the model's reading, which cannot be split.
- `Time by step:` the top 4 steps by total seconds, each with its share in percent.
- `Peeking at Trello:` (Quick mode only) `reads back after A s (tools T s, Claude writing W s), first card on screen after B s` from the `peek_start` notes, and how many cards between them needed live prep. If the stamps are missing, say so.
- `Cards from cache:` N of M, and for the fresh ones how many were changed, had no row or had an old-format row.
- `Turns per answer:` the average number of tool turns between an answer and the next item shown. More than 2 means calls are running one after another.
- A line with the Debug tab link: `Full log: <sheet link>, tab Debug (run <run_id>)`.
- One plain sentence on the most likely cause of the slowest turn, marked as a guess when the rows don't prove it.
Debug mode ends with this message. The next plain `/todo` run is a normal run.
