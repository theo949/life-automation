# Daily Task Review: the Full scan (helper)

This helper is loaded with the Skill tool by `todo-review` when the user picks **Full review** (or when there is no usable saved brief), and by `todo-card` / `todo-review` when a linked Google file has to be checked. It is not started by the user. Load it once per run, as the first call after the user picks 2 (together with the ToolSearch call below). The core skill's conventions all still apply (no narration, typed menus, the Write queue, no recaps, 12-hour times). Full mode differs from Quick mode only by the scan below: from the closing lines of the brief on, both modes are the same and both allow every action.

**Tools:** one ToolSearch call with a comma-separated `select:` list for everything below that is not loaded yet (SendUserMessage; Google Sheets `get_values`, `update_values`, `append_values`, `batch_clear_values`, `get_spreadsheet`; the Trello read and write tools; Gmail `search_threads`, `get_thread`; Google Calendar `list_events`, `search_events`; Google Drive `search_files`, `read_file_content`), never one call per tool.

## Full mode, in order
Moments: R = `Last review check`, P = the saved brief's `prepared_at`, U = the later of the two (see **Reference point** in the core). The scan start S is P when P is later than R, otherwise the earlier of R and the Review prep tab's `prepared_at` (with no R: P).
1. **Turn A (one parallel batch, in this order):** (a) first, one SendUserMessage status line. If R is later than P: `Your last review was at <R>. Let me see what's new in Gmail, Calendar and Trello...`. If P is later than R, or there is no R: `Your last update was at <P> (auto daily run). Let me see what's new in Gmail, Calendar and Trello since then...`. Times as in **Time format**. With no usable saved brief: `No brief saved for today yet, so I'm cooking up a fresh one from Gmail, Calendar and Trello...` (the saved brief row was read in the core; **Building a fresh brief** below). (b) The reads, together: the **Review prep** tab, the **Card cache** tab, the **Card index** tab, the **Card news** tab (Google Sheets get_values), the `In Progress`, `TO DO` and `Proposed` list reads (by saved list ID), the three Snoozed lists only when the Review prep tab cannot stand in for them (see **Snoozed cards from the Review prep cache**), and the Gmail freshness search and the Calendar part of the check (see **The check for anything new**).
2. **Turn B (the reads are back, one parallel batch):** the checklists of all working cards (trelloReadChecklist), the opening of every thread the check found (get_thread by hex ID), the **Linked Google files** check for every working card that has a linked Sheets, Docs or Slides file, the reply-based wake checks (**Waking cards**), and the live reads of cards a prep row says need one. Wake cards and roll the Snoozed lists forward from what is left open (queued, see **Waking cards** and **Snoozed buckets**). Collect stale future meetings (**Meeting cleanup** in `todo-review-actions`) across ALL cards, Snoozed lists included.
3. **Turn C: the brief.** Send ONE SendUserMessage with the brief (see **The brief**), ending with the closing lines from **Quick or full**, item 4, in the core. As LAST calls of that same turn, after the message: the Step 2b batch (see **Live prep**), the write of the new R (see **Reference point**, Full), and, for a fresh brief, the write of the Brief tab. Then go on as the core says (item 5, then card 1).
If one part of the check cannot run (a connector is down), the other parts go on, and the 🆕 section ends with the line `Couldn't check <mail | calendar | linked files | Trello> (<short reason>).`

## The check for anything new
Four parts, run together, once, by you directly (never a subagent for it, never one part after another). It starts at S and only what happened after B is listed as new:
- **Gmail:** the one inbox-wide freshness search from **Review prep cache** below.
- **Calendar:** events created, moved or cancelled since S. Use the Calendar tool's updated-since filter if it has one; otherwise compare the events of the next 14 days with the `Events:` lines of the working cards.
- **Linked Google files:** for every working card with a linked Sheets, Docs or Slides file, run **Linked Google files** with S as the reference point instead of `Last updated` (comments read with the comments option on; never use the file's modified time as a shortcut).
- **Trello:** a working card changed since S if its list, latest comment date, due date, checklist done/total or metadata `Last updated` differs from its **Card cache** row (ignore the `flags`, the helpers' own comments such as `Health label added automatically` and Snoozed-list moves).
A card with a hit from any part gets live prep (its cached block is not reused); it is listed as news only if the change happened after B. If all four parts find nothing, no card gets live prep, nothing is delegated, and the 🆕 section is the single line `🆕 Nothing new since <B wording>` (see **The brief**).

## The brief
**Reusing the saved brief (usable: `prepared_date` is today and the status is `ok` or `partial`):** ONE message: the saved title line `Your brief for <Day Mon D>`; then the ONE 🆕 section built with B (see **Reference point** in the core): the header `🆕 New since <B wording>` (with no B: `🆕 New today`) and one bullet per new item (style below), or the single line `🆕 Nothing new since <B wording>`. `<B wording>` is `your review today at <H:MM AM/PM>` when B is a Full review today, `today's daily run at <H:MM AM/PM>` when B is a daily run today, `your last review on <Mon D>` when B is a Full review on an earlier day, `the daily run on <Mon D>` when B is a daily run on an earlier day. **When P is later than B, the saved brief's own 🆕 bullets are kept in this section**, each with its own time (drop any whose event happened before B or whose card is now in `Done` or archived; rewrite any `wakes` or `back in <list>` wording on a reply-woken or snooze-ended card to `in today's review`), followed by the bullets the live check found after P; when both are empty it is the single `Nothing new` line. **When B is P or later,** the saved brief's own 🆕 section is left out (the user already saw it). Either way only ONE 🆕 section and no "what moved" list. Then the saved lines, refreshed against the list reads you hold: drop every bullet in ⏰ Due soon, ⏳ Waiting on and 💤 Stale whose card is now in `Done`, archived or gone; write every snoozed card's return as `wakes tomorrow` or `wakes <Mon D>` (never `snoozed until`, never `wakes today`); remove any `(wakes ...)` note from a card that is now in `TO DO` or `In Progress`; a section that loses all its bullets collapses to its single line or is left out. Change nothing else in them. Then the closing lines (core). The user reads one brief, and nothing is shown twice. Add one 🧹 line if stale future meetings were found (the question comes before card 1).

**Building a fresh brief** (the saved brief is from an earlier day, has status `failed`, or the user typed "rebuild" or "refresh"): the status line of Turn A says so (`Your last brief is from yesterday. Building a fresh one from Gmail, Calendar and Trello...`, `from <Mon D>` when older than yesterday; `Freshening up your brief from Gmail, Calendar and Trello...` for a requested rebuild). Build the brief live from the reads (**Gather** below and the layout below; its 🆕 section covers the time since B), send it, then overwrite the Brief tab in the Step 2b batch: one batch_clear_values on `'Brief'!A2:E200`, one update_values (meta row with status `ok`, `prepared_at` now, `prepared_date` today). A fresh brief does not refresh the Review prep cache: the freshness check still covers the time since the prep.

**Layout.** Plain text only. Sections in this order, only these icons:
- 🆕 **New since <B wording>** (wording as in **Reusing the saved brief**): new replies (including woken cards) and changed cards since B.
- 📥 **Proposed:** up to two lines, each shown only when its count is above zero. New (found today): `📥 N fresh task ideas from Gmail (found today)`. Older (found before today): `📥 K older task ideas still waiting for your verdict`. Singular and plural follow the count; no clock time, never `0 found`. Only if the `Proposed` list has cards.
- 📝 **Notes to yourself:** one line in the same section as 📥, shown only when the count is above zero. Count the Card news rows with category `self-note`, `found_date` today (user's time zone), grouped by card. One card: `📝 1 note to yourself went onto an existing card: [<card title>](link)`; several: `📝 N notes to yourself found a home on existing cards: [A](link), [B](link)` (up to 3 names, then `and K more`). Add `(woke up)` after a card that this note woke from a Snoozed list. A note that became a proposal is counted in the 📥 line, never here.
- ⏰ **Due soon:** overdue, due today and due in the next 7 days (these repeat every day until done).
- ⏳ **Waiting on:** snoozed cards that have `Wake on reply from` and no `Snooze type: plain`.
- 💤 **Stale.**
- 😴 **Snoozed:** N this week · N next week · N later.
- 🧹 **Stale future meetings:** N on M cards (only if any were found).

Rules: the title is one line, `Your brief for <Day Mon D>`, with no prepared time. A section with several items has a header line (icon + short title), then one bullet per item directly under it, a blank line between sections. A section with nothing collapses to one line (`💤 Stale: none`). 😴, 💤 (when none) and 🧹 are single lines. **No time-of-day words** ("this morning", "today's brief", "tonight"): name the time as in `<B wording>` (`since your review today at 12:30 PM`) or leave the reference out. Only list items that happened after that time.
- **⏰ Due soon:** date first, then the card link and a short detail in brackets, sorted by deadline, today first: `- Today: [card](link) (dentist 10:30 AM)`, `- Fri Oct 16: [card](link) (wakes Oct 16)`. A bill or invoice shows who it is from and the amount (`[Pay Acme Utilities $104.94](link)`). A card still snoozed says `(wakes tomorrow)` or `(wakes <Mon D>)`; a card that is awake has no `wakes` note. Leave out a card that is now in `Done` or archived and a card whose task the evidence shows is already done (`looks_done`, a receipt, a payment confirmation, a delivery notice): the review asks about it at its card.
- **⏳ Waiting on:** `- Who, [card](link): since <date>, follow-up <date>` (or `last reply <date>`).
- **🆕:** one bullet per news item (a reply, a woken card, a card moved, a changed card), each with its link. A reply names who sent it and when: `- Reply from Dana, Oct 22, 12:00 AM: [card](link)`.
- Cap each section at about 5 bullets (show the 5 most urgent, end with `- and K more`). Every bullet is one short line with a link. No card details or options in the brief.
- **One-time notes** go as a single bullet under 🆕: "No home address saved, so I'm not adding travel events (add one with /todo settings)".


## Reference point (Full mode)
R, P, Q, U and B are defined in the core (**Reference point: your last review**). A Full run moves R: the new R is the moment the check starts (taken from the clock inside a call already running: Bash `date -u +%FT%TZ` or the current_time tool, never a turn of its own). Write it in the Step 2b batch of Turn C, after the brief is on screen, with memory_str_replace on the `Last review check` line (memory_append of the line when there is none). If the write fails, say nothing and carry on. The scheduled (unattended) review, the helpers and the single-card review never read or write R, so they can never hide news. A review the user stops early still counts: once the brief was shown, the news was seen.


- **What counts as new:** only what happened after B: an email or reply sent after B; a calendar event created, moved or cancelled after B; a new or changed comment on a linked Google file after B; a card changed in Trello after B (list, comment, due date, checklist, metadata) by anyone other than this review itself (ignore the review's own dated comments, metadata updates and list moves, the helpers' comments such as `Health label added automatically`, and Snoozed-list moves; a `Woke on` line is not a change by itself, the card counts as news when its snooze ended after B, see next); a card whose snooze ended after B (also when the prioritizer woke it: its `Woke on` date is after B's date), or that a reply woke after B. A card the previous review snoozed or closed shows up only when something new happened to it after B (a reply, for example), and then the line says so: `Wise replied at 12:22 PM: [card](link), in today's review` (never name a list and never write `wakes`: the wake is queued, so the card may still sit in its Snoozed list when the brief is read).
- **Never list:** something that happened before B, even if this run only found it now (such a card is still woken, quietly); a card that is now in `Done` or archived; a change the previous review made itself. Check every item against the card's current state from the list reads before it goes in the list.
- **Long gaps.** After several days away the list can be long. Order it: replies that woke a card first, then due-date and deadline changes, then everything else. Show at most 8 bullets when B is more than 3 days ago (5 otherwise) and end with `- and K more`.
- **The user wants the news, not where it came from.** Never mention the prep, the helpers or the previous review in the list, and never add a "handled earlier" line.


### Waking cards
- **The prioritizer does the date-based moves first.** At 7:45 AM `todo-prioritizer` wakes every card whose `Snoozed until` has arrived (it removes the snooze lines, moves the card back to its `Snoozed from` list and writes the metadata line `Woke on: YYYY-MM-DD (date reached)`, or `(date reached, waiting on <Name(s)>)` for a card that was waiting on someone; no comment) and rolls the Snoozed lists forward. By the time of the review those cards are already in `TO DO` or `In Progress`, and the prep rows show no `wake_today` or `wrong_bucket` for them. The review therefore does only what is left: (a) **reply-based wakes**, which need a live look at email, and (b) any date-based wake or roll that is still open because the prioritizer did not run or a move failed (a prep row says `wake_today` or `wrong_bucket`, or the list reads show the card in the wrong place), done as described below. **All of these writes go into the Write queue (the entry holds the changes, see the core) and are written at the end of the run.** A woken card is treated as already moved: prep it from the description and comments you already hold, with no flush of the queue, and count it in the N of the `▶️ N cards to go through` line (the list reads do not show it yet).
- **Which cards to check.** With the Snoozed list reads, check every card in them; with the prep rows (see **Snoozed cards from the Review prep cache**), check only the cards whose row says `wake_today`, `reply_woke` or `wrong_bucket`, each read live first. For each such card:
  - **Your own note.** Whether or not the card has `Wake on reply from`: take the Card news rows for this card's `card_id` with category `self-note` and needs_action `yes` and a `last_msg_date` on or after the day of `Watching since` (the snooze day when there is no such line). Open the thread (get_thread); it counts when the user sent it after the `Watching since` time (the snooze time is not stored: with no `Watching since`, a note sent on or after the snooze day counts). This is the one case where the user's own message wakes a card. Wake the card as for a reply (remove the snooze lines, move it to `In Progress`), with the metadata line `Woke on: YYYY-MM-DD (your note)`. It is listed under 🆕 as `Your note, <Mon D>: <the user's own words, at most 12 words>. [card](link)` only if sent after B. The 📝 line counts it.
  - If it has `Wake on reply from`, check for a reply sent after the card's `Watching since` time (a card with no such line falls back to the snooze day). **Use the Wake hits tab first:** a row for this card's `card_id` whose `sent_utc` is after `Watching since` is a reply that discovery already matched by sender or by thread (`matched_address` `thread`: a message from anyone in a thread already on the card) and UTC time; wake the card on it. Then use the Card news tab: take its rows for this card's `card_id` with a `last_msg_date` on or after the day of `Watching since` (the Card index covers the Snoozed lists), open each thread with get_thread, and count it only if a message sent after that time (compare the real send times in UTC, never only dates) came from one of those addresses, was not sent by the user and was not sent by an automated sender (see **Every snooze wakes on a reply** in the core; a `@domain` entry is a lead that discovery has already judged: trust its Wake hits row, see **Same-domain replies** in the core). Search Gmail for those addresses only when the Wake hits tab has no `run` row from today (discovery did not run) or the card has no usable Card news rows and no Wake hits (it is missing from the Card index, the index is stale, or there is no Card news tab); search the card's wake list only, and also read each of the card's known threads (`thread_ids_hex` in the Card index) for a new message sent after `Watching since` by someone other than the user (not automated, not a pure auto-acknowledgement), which wakes the card too. If a reply arrived, **wake the card**: remove the snooze lines (including `Watching since` and `Snooze type`), move it to `In Progress`, and note the exact time the reply was sent (converted to the user's time zone, see **Time format**). It is listed as news under 🆕 (`Reply from X, <Mon D>, <H:MM AM/PM>`) only if the reply was sent after B. A woken card gets the metadata line `Woke on: YYYY-MM-DD (reply from <Name>)` (see **Snoozing** in the core), never a comment.
  - If `Snoozed until` is today or earlier, wake it: remove the snooze lines and move it back to the list in `Snoozed from` (if that's missing, use `TO DO`), and write `Woke on: YYYY-MM-DD (date reached)`, or `(date reached, waiting on <Name>)` for a snooze until reply (no `Snooze type: plain`) that got no reply. Such a card comes back with the follow-up as the suggested action (e.g. "Nudge <person> by email"); a plain snooze just comes back. A card the prioritizer already woke tells you the same in its `Woke on` line. Remove `Watching since` and `Snooze type` with the other snooze lines.
- Cards in the Snoozed lists are skipped in the card walkthrough and left out of the brief, except: show them if they have a Trello due date on or before today, or if a new email or reply arrived for them (a snooze never hides a real deadline or real news).


### Snoozed buckets (rolling forward, Full mode)
The buckets are defined in the core (**Snoozed buckets**). In Full mode, after waking cards, check each card in the Snoozed lists (from the list reads, or from the prep rows) and queue the move of any card in the wrong bucket (on Monday everything in next week's list moves to this week's list, and cards in the later list move up once their date falls inside next week), with the comment `**YYYY-MM-DD:** Moved to <list> (snoozed until YYYY-MM-DD)`. Do not change the metadata and do not mention routine moves in the brief. Keep each list sorted by `Snoozed until`, soonest at the top. A card with a `Snoozed until` line that is not in a Snoozed list is moved to the right one and gets `Snoozed from: <its current list>`; mention it in the brief once. A card moving between Snoozed lists is still snoozed.


## Linked Google files (check for news)
Applies to every card, with or without metadata, that has a Google Sheets, Docs or Slides file linked: in its attachments, description, comments or the metadata `Documents:` section (docs.google.com or drive.google.com URLs). It is read-only prep. In Full mode it runs for every working card as part of the check; in Quick mode it runs only when the user asks about a linked file. It exists because a comment on a linked guest-list sheet ("Sam said they can't make it") can be missed by a review that only reads the card.

- **Reference point for "new":** the metadata `Last updated` date. If the card has no metadata, use the date of the latest dated Claude comment on the card, and if there is none, the card's creation date.
- **Always read with comments turned on.** Without the comments option the connectors return only cell or text content, never comments.
  - Sheets: Google Sheets `get_spreadsheet` with `commentsIncluded: true`. It returns each thread's author, create and update times, OPEN or RESOLVED status and the anchored cell. For the cell content and the quoted text of each comment, also use Google Drive `read_file_content` with `includeComments: true`.
  - Docs and Slides: Google Drive `read_file_content` with `includeComments: true`.
- **Don't use the file's modified time as a shortcut.** Comments may not change it, so always fetch the comments.
- **What counts as new:** a comment thread or reply created or updated after the reference point, and a thread resolved or reopened since then.
- **Show each new comment with its context:** the commented text or cell and the row it belongs to. A bare comment is not enough to act on.
- **Also compare status-style columns or fields** (e.g. confirmed, RSVP, status, done) with what the card's latest comment and description say. If a value changed since the card last reflected it, report it as news.
- **Leave a snapshot for next time:** when the review writes a comment on a card that has such a sheet, add a one-line summary of the key counts (e.g. "RSVP: 2 yes, 1 can't make it, 12 no reply") so the next review can compare against it.
- **Treat new comments and changed statuses as news:** count them in the 🆕 line of the brief and show them as the first bullet of the card summary. What to do about them (update the card, its checklist or title, reschedule, tell someone) goes into the suggested action or the menu options.
- **If a linked file can't be read** (no access, connector error), say so in the card summary ("Couldn't read comments on linked <file name>, please check manually"). Never skip it silently.
- Nothing is changed in the Google file, and nothing on the card changes without the user's yes.


## Review prep cache (the daily prep, paid plans)
The scheduled prep helper does the slow read-only prep ahead of time and writes it to the **Review prep** tab of the Google Sheet "Life Automation Log". Use it, so the cards open fast (Full mode only: Quick mode does not read this tab). On non-paid plans there is no prep helper, so the cache is never there: prep live, with no warning line.

- **Columns:** item_type (meta/card/snoozed/proposal), item_id (card object id), list, deadline, new_thread_ids_hex, calendar_change (none/new/moved/deleted), news, suggested_update, suggested_action, proposal_suggestion, merge_target_card_id, reason_codes, confidence, prepared_at (UTC), prepared_date (user's date), notes. It holds only pointers and codes, never free text. The pre-written card text lives in the **Card cache** tab (see **Card cache**).
- **When it is usable:** read the tab once in Turn A (Google Sheets get_values, in parallel with the other reads). Row 2 is the meta row: the cache is usable only if its `prepared_date` is today (user's time zone) and its status (in the `news` column) is `ok` or `partial`. Otherwise (paid plans only) say once, in one line in the brief, "No prep today (<reason>), prepping live", and prep live as described in **Live prep**. Never fail or wait because of it.
- **Trust rules, per card:** trust a card row (find it by `item_id` = the card's object id) unless one of these is true; then prep that card live: confidence `low`, suggested_action `needs_review`, reason code `no_prep_cap`, the card has `Wake on reply from`, the card has Trello activity later than `prepared_at`, or the card has no row. A card that contradicts its row always wins over the row.
- **What a trusted row saves:** skip the Gmail, Calendar and Drive searching for it (the row's `new_thread_ids_hex`, `calendar_change`, `reason_codes` and `suggested_update` already say what changed). Still use the card itself (description and comments from the list reads, checklists from the card prep batch, see **Speed rules** in the core), and still open each thread listed in `new_thread_ids_hex` by ID with get_thread.
- **One freshness check for the whole review:** the cache was written before the review, so after reading it run ONE inbox-wide Gmail search for threads newer than the meta row's `prepared_at`, and match the results against the Card index `people_emails`. Gmail's date filter works by whole days, so the search only narrows things down: **open every hit and count it only if a message in it was sent after `prepared_at`** (compare the real send times, both in UTC). A hit is also skipped when its thread is already in that card's Review prep row (`new_thread_ids_hex`) or already mentioned in the saved brief lines. The same search also covers the people on the wake lists of snoozed cards (the Card index covers the Snoozed lists): a real reply from one of them after `prepared_at` wakes that card, read live as in **Waking cards**. Any hit that passes marks that card "live prep" (its row is not trusted for email news) and counts as news since the brief. Repeat this single search at most once more in the review, never per card. Calendar changes after `prepared_at` are caught by the Calendar part of **The check for anything new** and by the card's own meeting re-check (Meeting cleanup), not by a new search per card.
- **Using the row's suggestions:** `suggested_action` picks slot 1 of the menu: send_email → `Email <Name>: <topic>`, snooze_until_reply and nudge → `Email <Name> a nudge`, snooze_until_meeting → `Snooze <N>d (<Mon D>, meeting day)`, schedule_meeting → `Book <meeting>`, update_card → `Update <what>`, mark_done → `Mark done`; none or needs_review means decide yourself from the card's next real step. The row never decides a snooze date: dates come from the rules in **Snoozing** and the menu. `reason_codes` and `suggested_update` drive the summary bullets (for example `missing_travel`, `meeting_past_no_outcome`, `checklist_outdated`, `deadline_soon`, `waiting_7d`, `looks_done`). If the card shows the suggestion is wrong, say so briefly and use your own.
- **Proposals:** `proposal_suggestion` (add, merge, dismiss, completed) picks the first option in Step 2c (`todo-review-actions`); `merge_target_card_id` is the card to merge into.
- **Snoozed cards from the Review prep cache.** The prep writes one row per snoozed card (`item_type=snoozed`): `item_id`, `list` (the Snoozed list it sits in), `reason_codes` and `notes` (`until=YYYY-MM-DD`, and `bucket=this|next|later` when the card sits in the wrong list; never names or addresses). Codes: `wake_today` (`Snoozed until` is today or earlier), `reply_woke` (a real reply from the wake list was sent after the card's `Watching since` time; its thread ID is in `new_thread_ids_hex`), `wrong_bucket`, `stale_meeting` (with `calendar_change=deleted`) and `no_change`. **When the cache is usable and the meta row's notes show `snoozed=N`, do not read the Snoozed lists.** Read live only each card whose row says `wake_today`, `reply_woke` or `wrong_bucket`, one read each, in the same parallel batch as the other Step 1 reads. Judge a card on its live state when it differs from its row (the user moved or edited it since), and then do the waking and rolling as in **Waking cards**. Cards with `no_change` are neither read nor changed. The brief's 😴 counts come from the saved brief. If the cache is not usable, or the meta row has no `snoozed` count (an older prep), read the three Snoozed lists directly as before, so a card that should wake is never missed.
- **Refreshing the Review prep tab after a review.** The review has already read and judged every card, so it updates the tab for the next run (the tab is otherwise written only by the prep). Do it in the wrap-up, in the same turn as the Card cache rewrite, one batch_clear_values plus one update_values, and only after the Write queue flush report confirmed that its Trello writes succeeded. Rules:
  - Keep the meta row's `prepared_at`, `prepared_date` and `status` exactly as they are (the tab is still the prep's snapshot for the freshness check). Only update `snoozed=N` in its notes.
  - Set `prepared_at` and `prepared_date` of every row you rewrite to now / today. That is what makes the trust rule accept them: a row is untrusted only if the card has Trello activity after the row's `prepared_at`.
  - A card the user woke or moved gets a row for its new list with `reason_codes` `no_change`. A card the review snoozed gets a `snoozed` row (or an updated one) with the new `until=` date. Cards marked done lose their row. A proposal that was answered loses its row. Everything else stays as it was.
  - Never write names, addresses or free text; the row format is the prep's.
  - If any of the writes failed, or the run was unattended, a single-card review (`/todo card`) or a debug run stopped early, do not write the tab. A failure here is skipped silently and never delays the wrap-up.
  - The Brief tab is written by the review only after a fresh brief (see **The brief**).


## Gather (Full mode, quietly)
- **List reads:** one read each for `In Progress`, `TO DO` and `Proposed`, in one parallel batch, never the whole board in one call, by saved list ID (the name check on each result is the validation). Never read `Done`. The Snoozed lists only when the Review prep tab cannot stand in for them. Keep every card's description, comments, labels, due date and list (see **Speed rules**). If a list read fails or comes back empty by mistake, read that list again once, so a card that should wake is never missed.
- `Proposed` cards (with their proposal blocks) stay out of the regular card order and the Snoozed handling. Count them for the brief and note how many were found today and how many before today.
- Wake cards and roll the rest forward (**Waking cards**, **Snoozed buckets**). Create any missing Snoozed list. Cards still in a Snoozed list stay out of the walkthrough but still get a Meeting cleanup check; when the prep rows stand in for the Snoozed lists, take the stale meetings from the rows with `calendar_change=deleted` or the code `stale_meeting`.
- For every card with an `Events:` list, check each future entry against **Meeting cleanup** and collect the stale ones for Step 2a. Ignore past meetings here (they are handled by **Past meetings** at the card).
- Work out each card's deadline (see **Deadlines**) and go through the rest in the Step 0 priority order.


### 1a. Cards that already have metadata (check for news)
- If the **Review prep cache** is usable and the card's row is trusted, take the news from the row (and open its listed threads by ID) instead of searching; the rest of this section applies to cards that need live prep.
- Only look for **new** emails and calendar events involving the people already listed in the card's metadata, since the block's `Last updated` date.
- **Email news comes from the Card news tab first** (when the sheet has one; it is filled by the discovery helper). Read the **Card news** tab of the Google Sheet "Life Automation Log". It holds every thread that involves a person on an open card (columns: found_date, thread_id, last_msg_date, card_id, sender_domain, category, needs_action, notes). Take the rows for this card's `card_id` whose `last_msg_date` is later than the block's `Last updated`, and open each thread with get_thread (thread_id is Gmail's hex ID). That is the card's email news. Run your own Gmail search for the card's people only when: the card is not in the **Card index** tab of the same sheet (new, or excluded), its Card index `refreshed_date` is more than 2 days old, there is no Card news tab or it is empty (non-paid plans before the first helper run), or the card has `Wake on reply from` (see **Snoozing**). Calendar checks are unchanged.
- Don't re-search old history, **except** re-check each future meeting already listed against Google Calendar (see **Meeting cleanup**). In the card walkthrough, also check each upcoming in-person meeting for a missing travel event (see **Meetings and travel**, item 8).
- For cards with a linked Google Sheets, Docs or Slides file, also run the **Linked Google files** check (new comments, changed statuses) since `Last updated`.
- Feed anything new into the Step 2 status brief.

### 1b. Cards without metadata (enrich gradually)
- If the card's Review prep row has the reason code `metadata_added`, the prep helper already wrote its metadata in the last prep: treat it as a card with metadata (1a), and say in the summary what was added (one bullet). This section is only for cards with no metadata and no `metadata_added` row.
- Enrich at most **3 cards per day**, picked in the Step 0 priority order. The board fills in over time.
- Do the enrichment as part of card prep (Step 2b), after the brief has been sent, not before it.
- Skip cards with too little info to search on (a vague title, no comments). Don't "burn" tokens on them; focus on easier matches.
- For each of the 3 cards, try to find:
  - Who the card is connected to. Look at emails in Gmail and meetings in the calendar. Try to understand the meaning of the card and look for related emails and messages, e.g. if the card is about taxes, find emails about taxes.
  - What meetings are connected to the card.
- **Search window for this first enrichment only:** emails and calendar events within 30 days of the card's creation, i.e. 30 days before and after. After that, the card follows 1a and only new activity since `Last updated` is checked.
- Keep the findings for Step 3. **Queue the metadata write** when the card is shown in Step 3 (prep stays read-only; see **Write queue**) and say what was added in the card summary, instead of asking for confirmation first. If nobody is there to answer (e.g. a scheduled run), write nothing.
- Write the metadata into the card's description using the **Card metadata format** in the core, with every item sorted into its section.


## Live prep (Step 2b, Full mode)
Right after the brief message, in the same turn (the message first), start the prep for ALL working cards, in parallel: one batch of trelloReadChecklist calls for every working card, then the fingerprint check against the **Card cache**. Cached cards whose fingerprint matches need nothing more; the rest get the prep below. Card blocks are shown one at a time as the user reaches each card, so nothing is sent for the cards yet. In the same parallel batch: the write of the new R (memory write that never delays a card) and, for a fresh brief, the Brief tab write.
- **Where the cache is usable, a trusted card needs only a light prep:** use the card from the list reads and its checklists, open the threads listed in its row, and build the block and menu from the row's `suggested_action`, `suggested_update` and `reason_codes`.
- **Full live prep per card is read-only and covers:** the full card and its deadline (including an outside deadline not yet in the due date and whether it is fixed or movable, see **Deadlines**); news since `Last updated` for the people in its metadata; new comments and changed statuses in any linked Google file; for cards without metadata, the enrichment findings (capped at 3 per day); the missing-travel-event check for upcoming in-person meetings; the lookup of past meetings with no recorded outcome; the **Cleanup check**; the **Card content check**; whether the card has a comment `Health label added automatically` dated today; whether the only thing still open is an upcoming meeting; the suggested action as the slot 1 label; the public-transport travel time for a suggested in-person meeting (only if a home address is saved); the card's block and menu, ready to send. **No email drafts**: they are written when the user picks the email option.
- **Parallel:** if the Agent tool is available and several cards need fresh prep, use subagents (one per card, or small batches) that return a ready-to-use prep note, on a lighter, faster model when the tool lets you choose; otherwise batch independent tool calls in a single message. Only the working cards are prepped, never the Snoozed lists. Proposed tasks need no prep.
- **Prep never changes anything:** no Trello writes, no emails sent, no calendar events created, no learnings saved. The one exception is the missing due date, queued when the card is shown (see **Deadlines**).
- **No per-card re-check.** Only if more than 30 minutes have passed since the list reads when a card's question is due, re-read that card's list once (trelloReadCard `list_by_list`) and put an `Update:` bullet into that card's block for any card that changed. If something the user just did on an earlier card affects a later one, redo only the affected part.
- Unattended runs (scheduled, nobody to answer) have no card-by-card part, so no prep either.
