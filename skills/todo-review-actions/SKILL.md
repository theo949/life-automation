# Daily Task Review: actions (helper)

This helper is loaded with the Skill tool by `todo-review` or `todo-card`, once per run, when a card needs more than a snooze, a skip or a mark done: an email, a meeting or travel event, a document or sign-in, a past-meeting or cleanup question, a card content check, or the triage of proposed tasks. It is not started by the user. Everything in the core skill still applies (typed menus with circled numbers, no recaps, the Write queue, the Comments rule, 12-hour times, no narration). The meeting rules (**Meetings and travel**, **Meeting cleanup**, **Keeping the Events list short**, Step 2a) are in `todo-review-meetings`: load it with the Skill tool (once) the first time a meeting is created, moved or removed, a stale meeting is asked about, or an Events line is written. Quick and Full reviews both allow every action in this file: the only difference is that Full mode has already scanned Gmail, Calendar and Linked Google files (`todo-review-scan`) and Quick mode has not.

**Load the tools in the same batch as the Skill call** (never a turn of its own): one ToolSearch call with a comma-separated `select:` list of what the action needs and is not loaded yet (Gmail `get_thread`, `search_threads`, `reply`, `send_message`; Google Calendar `list_events`, `create_event`, `update_event`, `delete_event`; Google Drive `search_files`, `read_file_content`, `create_file`; Google Sheets `get_values`). Never one ToolSearch call per tool.

**Menus in this file** (the past-meeting question, the cleanup question, the stale-meeting question, the proposal options, the email send question) are all typed in the style of **The card menu**: a circled number per option (①, ②, ③, ④), options joined by ` · `, a blank line, then the prompt line `Type 1–<N>, or just tell me what you have in mind.` with the real N. Where this file shows a menu as `1 A · 2 B`, write it that way.

## Write at once (emails, calendar, Google files)
Card changes are queued (see **Write queue**), but anything that has already left the system is not: a calendar or travel event that was created, moved or deleted, a Google file that was changed, a request or form that was submitted (approved emails are the one exception: they are queued and sent first at the wrap-up, see **Emails**). If the session ended before the flush, the card would not show that it happened and the action could be done twice. So at the moment of the action, start ONE background step (Agent tool, `run_in_background` true) that writes the dated comment (`**YYYY-MM-DD:** what happened`, written as the **Comments rule** allows: an email or an event always gets one) and the metadata update for it (the Emails or Events line, the new person in People, `Last updated`), as one description update read from the card first (trelloReadCard `get`, one call). Give the step the card ID, the exact comment text and the exact lines to add. **Show first, start after:** the reply the user is waiting for (the next card, the date options, a question) is sent with SendUserMessage ALONE in the first batch of the turn (no Agent call, no read, no debug stamp and no planning of the background step in that batch), and the background step is started in a second batch of the same turn, right after the first one returns, without waiting for the user. The calls of a batch only start once the model has finished writing the whole batch, so a long Agent prompt in the same batch would make the user wait for the reply (see **Show first, fetch after** in `todo-review`). The turn's final text then adds nothing. Do not wait for the step: the next card goes out at once, so the user never waits for these writes. The background step runs alongside the next card; if the next card is the same card, wait for it before writing to that card. The snooze, the list move, the due date and anything else for the card stay in the queue and are applied by the flush, which reads the card again. The flush report also confirms the at-once background writes. The report of an email step (sent or not, started at the wrap-up, see **Emails**) is read before the closing message says everything is saved: an email whose step has not reported yet is waited for (a minute at most), and one that failed is listed in the closing message as `Not sent: <Name>`. A write that failed is retried once by the flush and, if it still fails, listed in the closing message as `Not applied: <what>`. If the Agent tool is not available, write the comment and metadata in the same turn as the action, in parallel with it, as before.

## Emails
Emails are written when the user picks the email option or asks for one, never earlier. Prep only decides that slot 1 is `Email <Name>: <topic>` or `Email <Name> a nudge`.
1. **Read what is needed, once:** the latest thread on the card (the Emails line, or the thread link in the proposal; Gmail `get_thread` by its hex ID) and, for a new person, the card's People line. In Full mode the scan may already hold the thread: use it.
2. **Draft it.** Reply in the existing thread when there is one, otherwise a new email. Language: the recipient's language; if the user has a saved learning about language for a recipient or kind of recipient, follow it. Keep it short and in the user's voice (follow the saved learnings). Add the cc or changes the user typed with the number ("1 and cc Sam"). **Footer on every email Claude drafts**, on its own line at the very end, after the sign-off, in the email's language: `✨ Drafted with Life Automation, a Claude plugin` (translate it when the email is not in English).
3. **Show the full draft as the closing reply** (never sent before the user's yes): `✉️ **Draft to <Name> <email>** (reply in the existing thread | new email)`, `Subject: <subject>` for a new email, a blank line, the body with the footer, a blank line, the menu line `① Send it · ② Hold off`, a blank line and the prompt line `Type 1–2, or just tell me what you have in mind.` Anything typed that is not 1 or 2 is a change to the draft: apply it and show the whole draft again. 2 sends nothing, the card stays as it is and the card's regular menu comes back in the next closing reply.
4. **1 queues it; it is sent first at the wrap-up.** Nothing is sent now and nothing is worked out: put the email in the Write queue as an email entry of its own (the exact approved text with the footer, the recipient and cc, the thread or `new email`, and the card's lines to write: comment `**YYYY-MM-DD:** Emailed <Name>: <one line what and why>`, the thread on the Emails line only if it is not listed yet, as one short line `<Who or topic>: <thread link>`, and the person on People) and go on. The reply of this turn is short and has nothing to compute: it is the next card when the user already typed a snooze or a mark done with the 1, otherwise the date options of **After an email was sent**, with their lines copied from the card's own menu when it is on screen. It starts with this one line (in the language of the conversation, with nothing else about the send): `📨 Queued: email to <Name>. It flies out at the end of the review, so keep this window open until the wrap-up says it landed.` No Agent call, no Gmail call and no read in this turn. **At the wrap-up** (Step 5 in `todo-review`, `todo-card` Step 7), right after the wrap-up message and in the same batch as the flush, start ONE background step per emailed card (Agent tool, `run_in_background` true), before anything else in that batch is written. Give it the exact approved text, the recipient and cc, the thread (or `new email`) and ALL the queued changes of that card (the snooze metadata, list move, due date, comments, the Emailed comment and the lines above). The step loads the Gmail tool itself (ToolSearch inside the step), sends the email (Gmail `reply` in the thread, `send_message` for a new email), and then makes the card's writes in ONE description update read from the card first (it sets `Watching since` to the time of the send); the flush leaves that card out, so each card has one writer. The step reports whether the send worked. If it did not (Gmail refused, the tool was blocked, the step failed), the closing message lists `Not sent: <Name> (<reason>)`, the card gets no snooze, no `Watching since` and no `Wake on reply from`, the `Emailed` comment is not written, and the card keeps its other queued changes and goes back to its list. If the Agent tool is not available, send the email yourself in the wrap-up batch, in parallel with the flush.
5. Never send an email the user did not approve in this review. A draft made in prep is only a draft. Never message anyone except by an approved email.

## After an email was sent (or a request, form or appointment request was submitted, or a document is with someone else)
The card now waits on someone else, so it is snoozed until they reply, with a date **the user chooses**:
- **Metadata (queued):** `Snoozed until` (the chosen date), `Snoozed from` (the card's current list), `Wake on reply from` (the email address of the person contacted, never their name; add them to People if missing; for a seller or a service use `@domain`), `Watching since` (the UTC time the email was sent, written by the email step at the wrap-up, so a reply that arrives before the snooze is still caught; see **Watching since** in `todo-review-rules`), no `Snooze type` line (that makes it a snooze until reply). The card moves to the right Snoozed list (see **Snoozed buckets**). No separate snooze comment: the email comment already records it (see **Comments rule**).
- **The closing reply is the date options**, and replaces the separate date question (see **Emails**): the `📨 Queued` line from the **Emails** section and then any note (Step 3.5 in `todo-review`; a sent email is not repeated back beyond that one line), then the bullet `Recommended: Snooze 7d (<Mon D>) because you're waiting on <Name>. The card wakes up early if <Name> replies.`; a blank line; the line `① Snooze 7d (<Mon D>) · ② Snooze 3d (<Mon D>) · ③ Snooze 14d (<Mon D>) · ④ Skip`; a blank line; the prompt line. Leave out (and close up the numbers) any date later than 1 day before the card's deadline or after the next meeting on the card. Picking a date is the user's choice of that date: queue the snooze, send no further check-in. Skip leaves the card in its list (the email is already recorded).
- A booked or confirmed meeting is not waiting on anyone: do not snooze the card for it. If nothing else is open, the check-in offers the snooze to the meeting (meeting day, or after the meeting when it is today).
- If the user typed something themselves in the same message, do that first and give the date options after it, unless that message already held a snooze (a length or a date, or just `snooze`) or a mark done: then apply it as in **Clear snooze**, skip these date options and the check-in, and go straight to the next card.

## Other actions the user can pick or type
- **A meeting or appointment** ("book", "set up", a call at a time): create the Google Calendar event (check the slot with `list_events` first and flag a clash in a note), follow **Meetings and travel** for the travel event, and write the event at once (**Write at once**: the `Events:` line with the calendar link, `Last updated`, and the comment). If the meeting is with other people and the user wants them invited, the invitation goes only after the user's yes on the final details.
- **Documents:** find the attachments (Gmail `get_message`, Drive), translate to English (or the user's language), save to Drive (`create_file`) or link them on the card; the Documents line is written at once (it is a Google file change).
- **Linked Google files:** nothing is checked in Quick mode. If the user asks about a linked Sheets, Docs or Slides file, load `todo-review-scan` (once) and follow **Linked Google files** in it.
- **Waiting on someone:** the snooze until reply covers most cases. Offer a separate watcher (a scheduled Gmail check that logs replies on the card between reviews, paid plans only) only if it is time-sensitive. Create it only after the user agrees.
- **Reminders:** on paid plans, Claude scheduled tasks (phone notification). On non-paid plans, a Trello due date on the card instead. No Google Calendar events for plain reminders unless the user explicitly asks.
- **A task done by hand** (the user says they did it): follow **Stated done is the go-ahead** in the core.

## Past meetings (follow-up check)
This applies in the card-by-card walkthrough and the single-card review, in both modes, never in unattended runs. The lookup is read-only prep; the only thing that reaches the user is one question at the card.

- **What counts:** a meeting connected to the card that took place in the last 14 days (before today) and has **no recorded outcome**. Connected means it is listed in the card's `Events:` metadata, or (Full mode, from the calendar data the scan fetched) it is a Google Calendar event that involves the people listed in the card's metadata or clearly matches the card's topic. A meeting has a recorded outcome when its line in `Events:` ends with (done), (not done) or (didn't happen). Use the data you already hold; don't scan the whole calendar.
- **When it runs:** when you reach a card (Step 3) that has such a meeting, before the card's normal question. The lookup is part of the card prep, so it's ready when the card is shown.
- **Show it in the summary:** one bullet in the card summary: "Past meeting: <title>, <date and time>".
- **Ask first, with its own question**, typed (see **Choices**). The card's header line and bullets come first, and instead of the card's menu the closing reply ends with the question line `Did the <title> meeting actually happen?`, a blank line, the menu line, a blank line and the prompt line (`Type 1–4, or just tell me what you have in mind.`). The menu line is always the same four options: `① It happened and we're done, mark the card done · ② It happened, but there's more to do · ③ It never happened, move it to <when> · ④ Skip`. **Option 1 text:** when something else is still open on the card (unchecked checklist items from the prep batch, a reply awaited, another future meeting, any other open item in the card's bullets), it ends with `(still open: <what>)`, so the user decides knowingly with one tap. **Option 3 text:** `<when>` is the new time of the meeting, and it is shown only when the meeting can be moved: its `Events:` line has a calendar link, the event has no guests besides the user (moving it would notify them), and it was not found missing from the calendar. Then `<when>` is `today, <H:MM AM/PM>` (the meeting's own clock time) when that time is still more than 15 minutes ahead; otherwise the next working day (the days in the settings, Mon-Fri by default) at the same time, written `<Day>, <Mon D>, <H:MM AM/PM>`. When the meeting cannot be moved, the option reads `③ It didn't happen` with no `move it to`. After answer 1 the card is finished, so the next closing reply is the next card alone, with no regular menu. After answer 2 or 3 the next closing reply is the card's regular menu line and prompt line, rebuilt for what is left; the card's header and bullets are not repeated. Skip skips the whole card: it records nothing (the question comes back in the next review), shows no regular menu and no recap, and the next card is the closing reply. Anything else typed is the user's own instruction (see **Choices**) and always wins, for example another day or time for the move.
- **Act on the answer** (the card's normal question that follows is shaped by it). In every case, mark the outcome on the meeting's line in the card metadata, as `- YYYY-MM-DD HH:MM: <title> (done)`, `(not done)` or `(didn't happen)`, and update `Last updated`:
  - **Option 1, mark the card done:** mark the meeting line `(done)`, tick the card's unchecked checklist items (the user saw what was still open in the option text, so choosing it is the go-ahead for all of it; the combined question of **Stated done is the go-ahead** is not asked), and queue the move to `Done` (**Mark done fast path**, no comment: the move is the record). Then the next card, no recap and no regular menu.
  - **Option 2, happened, not done:** ask what is left (free text), add a dated comment with it, and make that remaining work the suggested action for the card.
  - **Option 3 with `move it to`:** move the calendar event to `<when>` with the same duration, and its travel event by the same shift (see `todo-review-meetings`), at once (calendar changes are not queued). Then the same bookkeeping as any event move: the old date's line is marked `(didn't happen)` and the new date gets its line (see **Keeping the Events list short**), and one dated comment `**YYYY-MM-DD:** Meeting <title> didn't happen, moved to <date and time>`. Then the card's regular menu, rebuilt for what is left. If the move fails (the event is gone or cannot be changed), say so in one line, add the dated comment `**YYYY-MM-DD:** Meeting <title> didn't happen`, and make rescheduling the suggested action.
  - **Option 3 without `move it to`:** add a dated comment (`**YYYY-MM-DD:** Meeting <title> didn't happen`) and make rescheduling the suggested action, as before. A meeting created later as a new calendar event gets its own line.
- Ask once per meeting. A meeting whose line is marked, or that the user already answered in this review, is never asked again.
- This check never removes the meeting by itself; a line with a recorded outcome is dropped later by **Keeping the Events list short**.

## Cleanup check (anything no longer needed)
This applies in the card-by-card walkthrough and the single-card review, in both modes, never in unattended runs. The lookup is read-only prep; the only thing that reaches the user is one question at the card.

- **What counts:** a future meeting, a linked file, or any line in the card's metadata (Events, Documents, Emails, Others, People) that the card itself shows is no longer needed, because the work it was for is done or it was replaced. Examples: a gift-list meeting when the list is already ready, a draft file replaced by the final one, a link to a form that was already submitted. The reason must come from the card, its comments, its checklist or its emails, never from a guess. Meetings that no longer exist on the calendar, or that fall before a snooze date, stay with **Meeting cleanup** (Step 2a, Full mode). Past meetings stay with **Past meetings**. Anything the user already answered "keep" for (a comment `Keeping <what> (user)` on the card) is never asked about again.
- **Prep:** the prep finds the candidates and notes each as `cleanup: <what> | <reason in a few words>` (saved in the `reminder` column of the Card cache, see **Card cache** in the core). The card's bullets never mention it, and never say "tell me if you want me to remove it".
- **Ask first, with its own question**, typed and inline (see **Choices**). The card's header line and bullets come first, and instead of the card's menu the closing reply ends with the question line `<what> is no longer needed: <reason>. Remove it?` (for a meeting, name its day and time), a blank line, the menu line `① Yes, remove it · ② No, keep it`, a blank line and the prompt line (`Type 1–2, or just tell me what you have in mind.`). After the answer, the next closing reply is the card's regular menu line and prompt line; the card's header and bullets are not repeated. If there are several candidates, ask about them one at a time, at most 3 per card.
- **Yes:** a meeting is removed from Google Calendar at once (calendar changes are not queued), together with its travel event, and its line leaves `Events:` in the card's queue entry. A file or link is only taken out of the card's metadata (queued): the file itself is never deleted, trashed or unshared. Queue the comment `**YYYY-MM-DD:** Removed <what> (no longer needed: <reason>)`. A removed meeting no longer counts as open for the regular menu.
- **No:** queue the comment `**YYYY-MM-DD:** Keeping <what> (user)`. The regular menu is built with the item still on the card.
- The regular menu is built after the answer, so it never offers or mentions removing the item.

## Card content check
This applies in the card-by-card walkthrough and the single-card review, in both modes, never in unattended runs. The check is read-only prep; changes need the user's yes. In Quick mode it compares only what the card itself shows (description, comments, checklists, `Events` and `Emails` lines); Full mode also compares what the scan found.

- **Read the card's checklists directly** (trelloReadChecklist), because the plain card read can show none.
- **Compare** each checklist item, the title and the description with what the review found (emails, calendar, comments, activity, linked files). If developments made any of them outdated (an item that is done or changed, a title or description that no longer fits), show it as a bullet in the card summary and put the update in slot 1 of the menu (or in a bullet when slot 1 is something else).
- **Titles that say too little.** A bill, invoice, fine or fee card whose title does not say who it is from and how much it is (for example `Pay invoice TV-344`) counts as an outdated title when the card's People and Emails lines (or its thread) give the sender and the amount. Show one bullet (`Title doesn't say who or how much: Pay Acme Utilities $104.94 would.`) and offer the rename as the update. Never rename without the user's yes.
- **Ask before changing.** Never leave them stale, and never change them silently.
- **Before marking any card done,** check its checklists. If items are unchecked, warn the user and ask before marking it done (a warning only, the user can override it).
- **Not wanted:** a checklist line after every action, and a rule never to delete checklists.

## Proposal block (cards in the Proposed list)
The discovery helper writes this block into the description of every card it adds to `Proposed`:

```
--- 🤖 Claude proposal ---
Found: YYYY-MM-DD
From: Name <email>
Gmail thread: <URL>
Thread ID: <id>
Why: <one line: what is needed from the user, and by when>
Suggested list: <TO DO or In Progress>
Suggested due: <YYYY-MM-DD or none>
Possible match: <Trello card link or none>
--- end ---
```

Rules:
- The review only reads this block, until the user accepts the proposal in Step 2c. Never edit text outside it.
- While a card is in `Proposed` its description may carry both the proposal block and a normal metadata block (the discovery helper writes both). When a proposal is accepted (Step 2c), remove the proposal block and keep the metadata block (update `Last updated`; add one if it is missing). After acceptance never leave both blocks in one description.
- Do not set the Trello due date on a proposed card until the user accepts it.

## Step 2c: Triage proposed tasks from Gmail
Only in interactive runs, in both modes, and only if the `Proposed` list has cards. It starts AFTER the last card has been answered (and the leftover-cards question), with no extra question; when there are no working cards it starts right after the brief (and Step 2a). Nothing waits on it earlier: the card walk comes first.

- **Skip what is already on the board.** Before showing anything, check every proposal's Thread ID (and its Gmail thread link, hex and decimal forms) against the descriptions of the cards from the Step 1 list reads (the working lists) and, for the Snoozed lists when they were not read (always in Quick mode), against the `thread_ids_hex` of the **Card index** tab, which covers them (read it with one Google Sheets get_values call in the batch that sends the closing lines of the brief, only when the Proposed list has cards; skip it when the Snoozed lists were read). If another card already holds that thread, the proposal is a duplicate (for example the user added it in an earlier run, or by hand): do not show it. Queue its archive with the comment `**YYYY-MM-DD:** Already on the board (<card name>)`, and count it as "already on the board" in the wrap-up. Never show the same proposal twice.
- **Order:** soonest `Suggested due` first (no due date last), then oldest `Found` first.
- **One proposal at a time, typed.** Each proposal is the closing reply of its turn (see **Choices**): `**Proposed X of M:** [title](card link) · due <Mon D> (overdue, if it is) · [email](thread link)`, a blank line, the menu line, a blank line and the prompt line. The title already says who it is from and how much, so do not repeat the sender or the amount. Add the sender only when the title lacks it (when the proposal's Why has an amount and the title does not, add the amount), and add a few words (at most 12) of what is needed only when the title does not make that clear (for example `needs a proof of address under 3 months old and your full address`). Leave out the suggested list unless it is `In Progress`, and never copy the proposal's Why sentence over. The FIRST proposal of the run starts with one line before it: `Last part: N new proposals from your email. If you add one, it goes onto the board when I save at the end, and you'll go through it in tomorrow's review.` As soon as the user answers, the next proposal is the closing reply of the next turn (the answer's writes are queued, see below). Repeat until all are done.
- **Which option goes first (the recommended one):** "Add" by default. In Full mode, if the Review prep cache read by `todo-review-scan` is usable and has a row for the proposal (`item_id` = its card object id), follow its `proposal_suggestion`: add, merge (into `merge_target_card_id`), dismiss or completed (= "Already completed"), and put that option first. Ignore a row with confidence `low`. The other options keep the order below, with no "(Recommended)" tag. The proposal block and the Gmail thread win if they contradict the row.
- **Options for each proposal** (drop "Merge" if `Possible match` is none; up to 5 options, Skip last; the numbers close up). The option labels are exactly the bold text below; the text after each label only says what it does and is never put on the menu line:
  - **"Add to <list>"**. Use the `Suggested list` and `Suggested due` from the proposal block (add `, due <Mon D>` to the label when there is one). Moves the card to <list>, sets the due date and links the Gmail thread. The card is written to the board at the wrap-up and comes up in tomorrow's review; it is not part of today's walkthrough.
  - **"Merge into <card name>"**. Adds the email to that card (comment and link) and archives this proposal.
  - **"Not a task, dismiss"**. Archives the proposal and avoids similar ones.
  - **"Already completed"**. Archives the proposal. It was a real task and the user already handled it, so similar ones are still proposed.
  - **"Skip"**. Changes nothing; the proposal comes back in tomorrow's review.
- Anything else typed is the user's own instruction for that proposal (e.g. "add to In Progress, due Friday"). Do what they asked, then write a closing reply with the note (if any, Step 3.5), a blank line, the line `① Next idea, please` (or `① Wrap it up` after the last one), a blank line and the prompt line `Type 1, or just tell me what you have in mind.`, as in the Hard rule.
- **Act on the answers** (in an interactive run each answer's writes go into the **Write queue**, not sent now; the lines below say what each entry holds):
  - **Add:** two writes, sent together as parallel calls in one message: (a) move the card from `Proposed` to the chosen list; (b) ONE description update that removes the proposal block and keeps the normal metadata block the discovery helper already wrote (update its `Last updated`; if the card has no metadata block, write one with `Last updated`, `People` with the sender and `Emails` with one line `<Who or topic>: <Gmail thread link>`). In the same update call set the Trello due date to `Suggested due`, only because the user chose that option. Keep the title unless they typed a change. No "Added from Gmail" comment: the `Emails` line already records the thread. Leave the position to the prioritizer.
  - **Merge:** send in parallel: the comment on the target card with the thread link and a one-line summary, the update of the target's metadata (add the thread to its `Emails` as one short line `<Who or topic>: <thread link>` only if the link is not listed yet, add the sender to its `People`, update `Last updated`), and the archive of the proposal with a comment `**YYYY-MM-DD:** Merged into <card name>`.
  - **Dismiss:** send in parallel the comment `**YYYY-MM-DD:** Dismissed (<sender>: <subject>)` and the archive of the card. If the user dismissed 2 or more proposals of the same sender or kind in this review, propose a `Gmail discovery:` learning in Step 5.
  - **Already completed:** add a comment `**YYYY-MM-DD:** Already completed (<sender>: <subject>)` and archive the card. The comment must start with the words "Already completed": the discovery helper reads it to tell this apart from a dismissal. It is not a dismissal: never count it toward a `Gmail discovery:` learning, never propose one because of it, and keep the card out of the Dismiss tally.
  - **Skip, or no answer:** change nothing. The proposal stays in `Proposed` and comes back in tomorrow's review. Skip is the only way to leave it for later, because a proposal is either a task (Add, Merge), not a task (Dismiss) or already handled (Already completed).
- **Queue the writes; they are saved at the wrap-up.** For Add, Merge, Dismiss and Already completed answers where the user typed nothing themselves, put all the writes into the **Write queue** and show the next proposal at once. After the last proposal answer there is no tool call: go straight to the learnings and the wrap-up (Step 5), whose flush saves everything together. Keep each queue entry short (card ID, target list, due date, what to remove or add): the flush step reads the card itself. The user answers each proposal once; if the run is stopped, the stop path flushes the queue. If the user typed anything themselves, do what they asked first.
- Keep a tally for the Step 5 wrap-up (added, merged, dismissed, already completed, already on the board, skipped).
- **Unattended runs:** no triage. Only count the proposals in the brief.
- When triage ends, go to the learnings and the wrap-up (Step 5). If there were no working cards, say so in one line first. The wrap-up counts the added proposals as `A added (on the board tomorrow)`.

## Step 4: Execute what the user chose
- **Emails:** see **Emails** and **After an email was sent**. Never send without the user's yes on the final text.
- **Trello:** dated comment (`**YYYY-MM-DD:** what happened / next`, under the **Comments rule**), checklist ticks, list moves, due dates for deadlines and follow-ups, renames: queued (see **Write queue**), except the at-once writes of **Write at once**.
- **Meetings:** when a meeting is created on Google Calendar, follow **Meetings and travel**.

- **Website sign-in:** when a task needs a sign-in on a website (a booking, a portal, a form), use the password manager, never a typed password. If the tools `request_credentials`, `autofill_credential` and `release_credentials` are available (the 1Password connector in the desktop link; load them with ToolSearch if they are deferred): (1) BEFORE opening the page, call `request_credentials` for the login with the site's root URL (for example `https://www.example.com`), a one-line reason and keywords (the site name and the card topic), and wait for the user's approval in the password manager; (2) open the page in **Claude in Chrome** (the approval works only there, not in the built-in browser); (3) call `autofill_credential`; (4) when the sign-in is finished, call `release_credentials`. Never type a password or enter one into a field yourself, and never create an account. If the tools are not available, the request is declined or fails, or the password manager has no entry for the site: say so in one line, ask the user to sign in in the browser, and go on after they confirm. A booking or payment still needs the user's yes before its final step.
