# Task discovery (helper)

Finds emails that need action from the user and adds each one as a card in the Trello list `Proposed`, so the review can triage them. It runs silently: on paid plans as a scheduled task 60 minutes before the review, during setup (first scan), and on non-paid plans inline at the start of `/todo`, after `todo-prioritizer`.

This run never asks questions. Never send, draft, label, archive or delete any email. Never touch cards outside `Proposed` (reading is fine). Never message anyone. The only change to a card is creating your own cards in `Proposed` and, on those cards only, adding the `Health` label (STEP 3b) and any label named by a `Label:` learning (STEP 3b); never set due dates or members, and never set any other label. In the sheet "Life Automation Log" you may write the **Proposals** tab (append and update only), append to the **Card news** tab, append to and clean up the **Wake hits** tab (STEP 2c) and the **Skipped** tab (STEP 3c), and read the **Card index** tab (written by the prioritizer; never write it). Do not touch other tabs (including **Review prep**). Keep IDs and dates as text (prefix with an apostrophe).

## STEP 0: Settings and schedule check
Load `todo-review-rules` with the Skill tool in the same batch as the settings read: the review's **Card metadata format** that this skill points to is in it. Read `/areas/life-automation.md`. If missing, or paused on a scheduled run, say so in one line and stop. If `setup_stage` in that file is `questions` or `connectors`, say in one line that setup has not reached the build step and stop (do not read email). Use the saved time zone for "today", the saved lookback, the board name and the sheet name. Find the board by name in Trello and the sheet by title in Drive. Never use stored IDs.
Mondays only, scheduled runs only: list_triggers (recurring, enabled; follow next_cursor) and find "Life Automation: review". This task (named "Life Automation: discovery") must run exactly 60 minutes before it, same days. If its cron differs, update_trigger it (saved time zone, hour and minute computed minus 60) and continue.

## STEP 1: Context
a) Read `/areas/life-automation-learnings.md`. Lines starting `Gmail discovery:` are exclusions (senders, subjects, topics never to propose). Also respect any line saying a topic must not be brought up unless asked. Lines starting `Gmail discovery include:` are rules the user approved: propose a matching thread even when it would otherwise be dropped as FYI or automated (the known-thread check and the cap still apply). Lines starting `Discovery miss:` (including self-notes the user confirmed) are emails the user said discovery should have caught (sender or sender type, how it arrived, why it was skipped, their own words). Read the 30 newest and use them as examples: when a thread has the same sender address or the same shape and would otherwise be skipped for the same reason, propose it and say in the Why line that it is similar to a past miss.
b) Find the list `Proposed` on the board. During setup's first scan the board and its lists may still be being built by setup: do STEP 2 and STEP 2b first (they do not need the board), then look the board and `Proposed` up by name again, retrying for up to a few minutes, before STEP 3. Never create the board or its lists during setup. Outside setup, if `Proposed` is missing, create it at the right end. Also look up the board's `Health` label by name (trelloReadBoard list_labels); if there is none, the Health part of STEP 3b is skipped. Read the learnings lines that start with `Label:` too (for example `Label: tasks with Sam get the family label`) and look up each named label on the board by name (the same list_labels call).
c) **Known threads.** Do NOT read all cards. Build the known set from every `thread_id` in the **Proposals** tab and the `thread_ids_hex` column of the **Card index** tab. **Email addresses:** search results can show addresses without dots, so take addresses only from the full thread read, and compare them lowercase with dots in the local part ignored (`pat.lee@example.com` equals `patlee@example.com`) against `people_emails`. Gmail's API gives hex thread IDs, but links stored on cards use the decimal form (`thread-f:<decimal>`; convert with `python3 -c "print(int('<hex>',16))"`). After STEP 2 produced the qualifying candidates, for each one not already known, run trelloSearch with the DECIMAL ID twice (plain, and with ` is:archived` appended) and once with the hex ID. Any hit means known: skip it. Also load the full **Card index** tab for STEP 2b (columns `card_id, title, list, people_emails, thread_ids_hex, last_updated, refreshed_date, events, link_domains`; the last two may be missing on an old index). If it is empty or its newest `refreshed_date` is more than 3 days old, say so in the final reply and, for this run only, read all open cards on the board (the read is very large: it is saved to a file, then use jq or grep), grep thread IDs and note open card titles and People.
d) **Learn from past proposals** (Proposals tab, columns `found_date, thread_id, card_id, sender_domain, category, suggested_list, status, outcome_date, outcome_list, notes`).
   1. Sync outcomes: for every row with status=open, read its card. If the card is open and in a list other than `Proposed`: status=accepted, outcome_list=that list, outcome_date=today. If it is archived while in `Proposed` and its thread ID appears on another card: status=merged. If it is archived and no other card has the thread ID: look at its comments. A comment starting "Already completed" means status=completed; otherwise status=dismissed. If still open in `Proposed`: leave open (after 14 days set status=ignored). Update the row in place and note the sync in the final reply.
   1b. **Self-notes the user turned into cards themselves.** Read the Skipped rows of the last 7 days with reason `self-note-no-intent` (also the old code `self-note-no-cue`). For each whose hex thread ID is in the `thread_ids_hex` of a card in the Card index (the user made a card from it), append one row to the Proposals tab unless a row with that thread_id and status `miss-candidate`, `miss-confirmed` or `miss-declined` already exists: found_date today, thread_id, card_id (the card from the index), sender_domain `self`, category `self-note`, suggested_list empty, status `miss-candidate`, empty outcome fields, notes empty. The review asks the user about it (see **Learnings** in `todo-review-rules`). This run never asks.
   2. Learned weighting (only rows with status accepted, dismissed or merged; ignore open, ignored and completed): group by `sender_domain` and by `category`; for free-mail senders (gmail.com, googlemail.com, outlook.com, hotmail.com, yahoo.com, icloud.com, abv.bg) group by the full sender address instead of the domain, so one personal sender never counts against another (the sheet's `sender_domain` column stays domain-only, so for free-mail senders count the resolved rows from the same address via each card's People line). If a group has at least 3 resolved rows and at least 70% are dismissed, treat it as low value: do NOT propose it, UNLESS the email has an amount or due date (bill, fine, fee, deadline) or is a direct personal request from a named person; count these under "skipped: learned". If a group has at least 3 resolved rows and at least 70% accepted, always propose it when it otherwise qualifies. Fewer than 3 rows: no change. Never use a single card's status to suppress anything. List each active learned rule (group, n, % dismissed or accepted) in the final reply. "completed" rows count as neither.
   3. Privacy: in the sheet write no subjects, names or amounts. `sender_domain` is the domain only; `category` is a generic word such as bill, appointment, personal-request, job, medical-portal-message, admin, reply-owed. For health or other sensitive items write sender_domain `[redacted]`.

## STEP 2: Search Gmail (read-only)
**Window (N days).** Read `plan type` from the settings. Paid (scheduled): `newer_than:3d` (covers weekends; the known set handles overlap). **First scan** (the Proposals tab is empty, or setup asked for it): use the saved lookback instead (1 week = `newer_than:7d`, 2 weeks = `newer_than:14d`, 1 month = `newer_than:30d`). Window guard (paid): if the newest `found_date` in the Proposals or Card news tab is more than 3 days old (the task did not run), widen the window to cover the gap. Non-paid (manual): there is no lookback setting. First scan = `newer_than:7d`. Later runs = the number of days since the newest `found_date` in the Proposals or Card news tab, at least 1 and at most 7 (`newer_than:Nd`).
**Searches.** Run these in parallel, all with `view` = `THREAD_VIEW_SUMMARY` and `pageSize` 50 (one page on non-paid plans, up to 3 pages on paid plans):
1. Primary: `in:inbox category:primary newer_than:Nd`. Read everything it returns.
2. Updates: `in:inbox category:updates newer_than:Nd (invoice OR bill OR payment OR due OR appointment OR deadline OR order OR receipt OR confirmation)`. Also add `OR from:<address or domain>` for up to 15 senders: sender domains that have `accepted` rows in the Proposals tab (skip `[redacted]`), and the sender addresses or domains named in the learnings lines starting `Gmail discovery include:` or `Discovery miss:`. Most newsletters and notifications in Updates are skipped this way on purpose: they are the bulk of a first scan and almost never tasks.
3. Sent: `in:sent newer_than:Nd`, only to see where the user already replied.
4. **Labeled mail** (optional): `label:Trello newer_than:30d` (any category, including promotions), only if the user has a Gmail label named `Trello`; if there is none, skip this part silently. A user's own Gmail filter may also put that label on mail that carries Claude's footer ("Drafted with Life Automation"), so the label alone is not a signal. Read each such thread in full: it counts as labeled by the user only if at least one message that carries the `Trello` label has no "Life Automation" (any case) anywhere in its text. Threads where only footer messages carry the label are not labeled threads: ignore them silently.
Never search Promotions, Social or Forums, except for labeled mail. The keywords are English: other languages work at the user's own risk. Read each candidate thread in full before judging, and never read a thread whose last message is the user's own (unless it is a note to self, see below).
Propose a task only if at least one is true: a request or question addressed to the user that needs their answer or action; a bill, invoice, fine or fee with an amount or due date; a deadline, form or document to submit; an appointment, meeting or delivery that needs preparation or a decision; a reply the user owes (the last message is from someone else, contains a question, and has waited 2+ days).
Do NOT propose: newsletters, promotions, marketing, receipts or confirmations needing no action, automated notifications (shipping, security alerts unless action is required), social notifications, FYI or CC-only threads (except the person-FYI rule below), threads where the user's own message is the last message (except self-sent threads, see below), threads in the known set, anything excluded by the learnings or the learned weighting.

**Self-sent threads.** A thread whose sender is the user and whose only recipient is the user (including a forward to themselves) is a note to self, not a finished conversation: the "own message is the last message" exclusion does not apply. There is no fixed list of cue words. Read the user's OWN words: the subject plus the text above the first forwarded or quoted line (never the forwarded text below it, and never the signature or phone number). Propose the thread when those words say the user means to do, read, watch, buy, apply to, look into or follow up on something. Any verb of intent counts, in any form, with typos (`appply to this`), and so does a short instruction next to a link or attachment (`Look into this` over a screenshot) or a question the user puts to themselves about what to do. Examples of intent, not a complete list: watch, read, shop, look into, set up, book, review, check, take a look, fill, sign, apply, buy, call, email, pay, try, compare, find out, research. Also use the learned cues below. Skip it (reason `self-note-no-intent`) when the user's own words hold no intent: a bare link, a screenshot or a forward with no words of their own (a YouTube share whose subject is the video's title still counts as `Watch ...` when the subject starts with Watch), a debug note. A cue inside a forwarded email's own text never counts. Category `self-note`. The title starts with a verb, for example `Watch: <video title>`, `Look into: <short topic>` or `Apply to: <company>`. **Confidence:** `normal` when a clear verb of intent is there; `low` when the only sign is a link or attachment with a few words of the user's own and no clear verb. Record in the proposal's Proposals row `notes` the one word or short phrase that triggered it (a generic word such as `apply`, never a name, title or link), so outcomes can be learned per cue.

**A self-note about something already on a card.** After a self-note passes the intent test above, compare it with the open cards in the Card index before making a proposal. It is a clear match when the note's link domain is in a card's `link_domains` together with a topic that fits the card's title, or when the note's topic (the words of the subject and the user's own words) clearly fits exactly one open card's title (for example a note "Look into this for shoulder pain" fits the card "fix the shoulder pain"). A snoozed card counts (the Card index covers the Snoozed lists). For a clear match do NOT create a proposal: append a row to **Card news** (STEP 3a) with category `self-note`, needs_action `yes`, card_id the matched card, notes `self-note on this card` (no subjects, names or amounts). A match by the thread ID alone (the thread is already on a card's Emails line) needs no row: it is simply known. If the topic fits two or more cards or none clearly, treat it as unmatched and create the proposal, naming the candidate cards in "Possible match". Never comment on, edit, move or wake the card here; the review wakes it (see `todo-review-scan`).

**Learned self-note cues.** From the Proposals tab rows with category `self-note` and status accepted or dismissed, group by the cue in `notes`. Three or more resolved rows with the same cue and at least 70% accepted: always propose a self-note with that cue, even at low confidence. Three or more and at least 70% dismissed: do not propose it (log `learned-low-value`). Fewer than 3: no change. List the active cue rules in the final reply.

**Person-FYI rule.** A direct email from an individual (not a no-reply address, newsletter, mailing list or promotion; not already on a card; the user's own message is not last) that would otherwise be dropped as FYI is still proposed when either signal applies. Signal A: Gmail flags it important AND it has links or attachments; propose it with `Confidence: low`. Signal B: the subject or the sender's own text contains one of these cues: read, look into, review, check, take a look, fill, sign; propose it with `Confidence: normal` (also when A applies). Quoted text, signatures and unsubscribe footers never count for B. Title: a verb plus the sender, for example `Read handouts from Pat Lee`. The Why line names the signal and quotes the cue word (for A: "flagged important with links").

**Labeled threads (`Trello` label).** The user puts the label on an email by hand to say it needs action, so it is the strongest signal there is. A labeled thread skips every "do not propose" rule above (own message last, FYI, automated, newsletter, promotion, learned low value, `Gmail discovery:` exclusions); only the known-thread check still applies. **One exception: a labeled thread that sits in Gmail's Promotions, Social or Forums tab is not proposed** (the label is probably an automatic filter, not the user's hand). Log it to the Skipped tab with reason `promo-labeled` and name it in the final reply. It may belong to a task that already exists, so it always goes through STEP 2b first. Category `labeled`; the Why line starts `You labeled this for Trello:` and then says what seems needed (if nothing can be told, say "no clear action found, check the email"); the title follows the usual title rules. Labeled threads come first when the cap bites. Never add or remove the label. A labeled thread you did not propose is named in the final reply with its reason (matched to a card, already known, over the cap).

**Cap:** paid plans: at most 10 new proposals per run, and at most 15 on the first scan. Non-paid plans: at most 8 per run, including the first scan. If more qualify, keep the most urgent (soonest deadline, then newest) and mention the overflow count in the final reply.

## STEP 2b: Match against existing cards
Before creating any proposal, compare each qualifying thread with the Card index. A CLEAR MATCH needs both: (a) the sender's email (or a recipient's, on a sent thread) is in the `people_emails` of exactly one open card, or in several cards but only one has a title covering the same topic; and (b) the thread's topic clearly fits that card's title. For a clear match: do NOT create a proposal; append a row to **Card news** (STEP 3a) with needs_action=yes. If the person matches but the topic is unclear, or the person is on several cards and none clearly fits, treat it as unmatched and create the proposal, naming the candidate cards (Trello links) in "Possible match". Threads with no person match are unmatched, except through the event match below. **Labeled threads (`Trello` label):** a clear match works as above (Card news, needs_action=yes, no new card). For anything unclear, lean toward a proposal: if the sender is on one or more open cards but the topic is not clearly the same, create the proposal and name every candidate card in "Possible match" so the user can merge it in the review; the user would rather archive a wrong proposal (which teaches discovery) than lose an email inside the wrong card. Never comment on, edit or move existing cards. Cards missing from the Card index can never be matched.

**Event match (appointments and bookings).** For a thread that is a reminder, confirmation, change or cancellation of an appointment, meeting or booking with a date and time, it is ALSO a clear match when an open card's `events` has an entry on the same date with a time within one hour of the email's time, or when the sender's domain is in that card's `link_domains` and the email's date equals one of that card's `events` dates. This needs no `people_emails` match: a booking system's address is usually not on the card. A person match whose topic is unclear counts as a clear match too when the email's date equals one of that card's `events` dates. For an event match, append a Card news row (STEP 3a) with category `appointment`: needs_action=no for a reminder or confirmation, needs_action=yes for a change, cancellation or anything the user must answer. Do not create a proposal. An appointment email that matches no card by these rules is still proposed as before, and its Possible match names the closest card by person or topic.

## STEP 3: Create proposals
For qualifying threads that were not a clear match. Before creating each, re-check `Proposed` for the same Thread ID. Create the card in `Proposed` with a short, imperative title and this exact block as the description.

**Titles.** The title must tell the user what it is at a glance, without opening the email:
- **A bill, invoice, fine or fee:** `Pay <Sender> <amount> (due <Mon D>)`, for example `Pay Acme Utilities $104.94 (due Oct 21)`. `<Sender>` is the company or person's name as the user knows it (not the payment service, not a no-reply address), `<amount>` has its currency symbol, and `<Mon D>` is the due date (leave out the whole bracket if there is none). Do this for every sender, including a clinic, therapist or other health sender: the user wants the sender and the amount in the title. The invoice or reference number (for example TV-344) goes into the Why line, never into the title.
- **Everything else:** a short, neutral, imperative title with the most useful detail, for example `Send the bank proof of address`. For anything other than a bill's sender and amount, keep sensitive details (diagnoses, medical or legal specifics, account numbers) out of the title.

```
--- 🤖 Claude proposal ---
Found: YYYY-MM-DD
From: Name <email>
Gmail thread: <URL>
Thread ID: <id>
Why: <one line: what is needed from the user, and by when; for an invoice include its number>
Suggested list: <TO DO or In Progress>
Suggested due: <YYYY-MM-DD or none>
Confidence: <normal or low; low only for the person-FYI rule's signal A and for self-notes with no clear verb>
Possible match: <Trello card link if an existing card clearly covers the same subject or people, else none>
--- end ---
```

Suggested list: `In Progress` if it is a conversation the user is already actively handling (they replied recently); otherwise `TO DO`. Do not set the card's due date or members.

Below the proposal block, in the same description, also write the normal metadata block, so accepting the proposal later needs no rewrite of it:

```
--- 🤖 Claude metadata ---
Last updated: YYYY-MM-DD
## People
- Name <email>, role (at most 5 words, if obvious)
## Emails
- Short neutral description (who, when, what): <Gmail thread URL>
--- end ---
```

Keep it neutral and short, the same facts as the proposal block (sender, thread). Follow the review's **Card metadata format** line rules: a People line only for someone with an email or phone, with a role of at most 5 words and no history or status; an Emails line is `<Who or topic>: <thread link>`, 12 words or fewer, one line per thread, no dates or history. Section titles are large markdown headings on their own line (`## People`, `## Emails`), never plain `People:` lines. The review removes the proposal block when the user adds the card and keeps this one.
After each card is created, append one row to the Proposals tab: found_date, thread_id (hex), card_id (the card's object id), sender_domain, category, suggested_list, status=open, empty outcome_date and outcome_list, and an empty notes field (for a `self-note`, the one generic cue word that triggered it). (The sheet keeps no subjects, names or amounts, see STEP 1d.3; the amount and sender in a card title live in Trello only.)

## STEP 3b: Health label
The board's `Health` label marks medical cards. For each proposal you just created, add the `Health` label (found in STEP 1b) when the email is clearly about medical care: it comes from a clinic, hospital, doctor, lab, pharmacy or medical portal, or it is about a surgery, a prescription, an appointment with a care provider, or a medical test or result. Direct evidence only: a guess, or an email that merely mentions a health topic (a newsletter, a gym, a general wellness subject), gets no label. Never remove or change any other label. Right after adding it, add the Trello comment `**YYYY-MM-DD:** Health label added (automatic)` (today's date in the saved time zone; the comment states no reason): the review reads this comment to show the user a one-line note on the card. Do not ask: this run cannot ask, and the label is easy to remove. If the board has no `Health` label, skip this step and mention it in the final reply. The sheet gets nothing about it.

**Learned labels.** For each proposal you just created, check the `Label:` learnings: when a rule's condition clearly holds for the thread (the named person is the sender or a recipient, or the named topic is what the email is about), add that rule's label with the same call style as `Health`. No comment, no question: it is silent and easy to remove. If the board has no label with that name, skip it and mention it in the final reply. Only proposals you create in this run are labeled; existing cards are never relabeled.

## STEP 2c: Wake hits (mechanical, before triage)
Snoozed cards wake on replies. This step finds those replies by rule, so no wake depends on triage judgement or on a Card news row existing. From the Card index, take every card in a Snoozed list whose metadata has `Wake on reply from` (read the card if the index does not hold its wake list and `Watching since`). Run ONE Gmail search over all those addresses together: `from:(addr1 OR addr2 OR ...) newer_than:3d` (split into several searches only if the query gets too long). **Only real email addresses go into the query** (entries that contain `@`, and `@domain` entries as before). Never put a name or a description from the wake list into the query (a first name, an organization name, `the front desk` and the like): a name inside `from:(...)` once made Gmail return nothing for that card, so a reply from its real address was never found. For each card whose wake list holds such a name, look up the matching address in the card's People lines and search that address instead. If a card's wake list has no usable address at all, skip it and list the card in the run record as `no usable wake address`, so it never fails silently. Open each result with get_thread and check each message: the sender is one of that card's wake addresses or is at one of its `@domain` entries (see the same-domain guidance below), the message was sent after that card's `Watching since` (compare the real UTC send time to the second, never only dates), it was not sent by the user, and it is not automated (the sender rule in `todo-review-rules` under **Every snooze wakes on a reply**; a pure auto-acknowledgement such as a ticket or receipt confirmation, an out-of-office or a "we received your message" reply usually does not wake the card, but a support or assistant reply that answers what we wrote does). **Same-domain guidance (use judgement, not a fixed rule):** a message from another address at a `@domain` entry's domain is a lead. Read it and decide whether it is about this card's task. Treat these as unrelated: noreply or no-reply senders, marketing, promotions, newsletters, news digests, surveys, product announcements, anything with no link to the card's topic. When unsure, err on the side of logging a wake hit rather than missing one. Put the `@domain` entry in `matched_address`. A domain message you judged unrelated gets a Skipped row (reason `other`). Learn as in STEP 1d: domains whose mail the user keeps dismissing or re-snoozing right after a wake count as low value for waking, like dismissed proposals. Append one row per qualifying message to the **Wake hits** tab (columns `found_at_utc, card_id, thread_id, message_id, sender, sent_utc, watching_since, matched_address`; times in UTC, IDs as text); skip a message whose message_id is already there. On every run also append one row with card_id `run` and thread_id `none`, so later skills can see the check ran. Never skip this step because a thread is already known or already in Card news. A thread found here still goes through STEP 2b and STEP 3a as usual. After appending, delete Wake hits rows whose found_at_utc is more than 7 days old (keep the header row).

## STEP 3a: Card news
For each clear match from STEP 2b, and also for non-qualifying threads (FYI, confirmations, receipts) that involve a person on an open card, append one row to the **Card news** tab (columns `found_date, thread_id, last_msg_date, card_id, sender_domain, category, needs_action, notes`): found_date (today), thread_id (hex), last_msg_date (date of the thread's last message, YYYY-MM-DD, in the saved time zone: convert the message's UTC time first), card_id (the matched card), sender_domain, category (generic word), needs_action (yes or no; for an appointment or booking email follow the event match rule in STEP 2b), notes (short, neutral: no subjects, names or amounts). Skip a row if one with the same thread_id and last_msg_date already exists. Cap 40 rows per run. Do not create Trello cards for these.

## STEP 3c: Skipped log
So a missed email can be explained afterwards, append one row to the **Skipped** tab (columns `found_date, thread_id, reason_code`) for every thread you read in full and did not propose and did not add to Card news. found_date is today, thread_id is hex, and reason_code is one of: `own-message-last`, `fyi-no-action`, `newsletter`, `automated`, `known-thread`, `learned-low-value`, `excluded-by-learning`, `self-note-no-intent`, `promo-labeled`, `other`. Skip a row if one with the same thread_id and reason_code already exists. No subjects, names or amounts. Threads in promotions, social and forums are never read, so they are not logged. Labeled threads are never logged here, except `promo-labeled` ones (all other labeled threads are reported in the final reply). After appending, delete the rows whose found_date is more than 7 days before today (keep the header row). Every thread you read in full that involves an address on an open card must end as a proposal, a Card news row (STEP 3a) or a Skipped row; never drop one silently. Add one line to the final reply: `Card-person threads: <read>, Card news <n>, Skipped <n>, Wake hits <n>.` If a run proposed or logged nothing and skipped nothing, write nothing to Card news and Skipped (STEP 2c still writes its `run` row).

## STEP 4: Final reply (the run record, 3-8 lines)
Threads scanned, proposals created (titles; mark low-confidence ones), labeled threads (N found; for each one not proposed, the card it was matched to or the reason), health labels added (N), skipped counts by reason (including "skipped: learned") and how many rows went to the Skipped tab, cap overflow, outcomes synced (N accepted, N dismissed, N merged, N completed) and any active learned rules, "matched to existing cards: N threads added to Card news (K need action)" with the titles of the matched cards, Card index age in days (or the fallback note), whether the schedule check ran (Mondays) and changed anything, any error. Also: "self-notes added to existing cards: N" with each note's verb or topic word and the card title (for example "look into" -> fix the shoulder pain). If nothing qualified: "No new tasks found." plus the outcome sync line if anything changed. On the first scan during setup, report the proposal count in one line so setup can show it.
